## A. Today's objective

Make the monitoring stack the last four batches designed **actually runnable**:
ship a self-contained `k8s/monitoring/` kustomization (Prometheus → Alertmanager
+ ntfy bridge → Grafana) that an operator applies with one `kubectl apply -k`,
each manifest **CI-gated by kustomize + kubeconform** so it can't rot — and wire
`record_backup_run` into the nightly backup CronJob so `openshiksha_backup_age_seconds`
stops reading "never". The artifacts already exist and are validated; this batch
packages them for deployment.

## B. Why this matters

OpenShiksha is **live in production** on a single DO/k3s droplet and is now
richly instrumented — but the instrumentation is inert. `/metrics` emits gauges
nothing scrapes; eight alert rules sit in a YAML file no Prometheus loads; a
Grafana dashboard JSON has no Grafana to load it into. The 2026-06-28 close-out
named exactly three operational follow-ups: **(1) deploy Prometheus +
Alertmanager so ALT-1/2/4 go live; (2) wire `record_backup_run` so prod
populates the freshness gauge; (3) wire `VITE_SENTRY_DSN` into the CI frontend
build.** Item (3) is **already done** — `ci-cd.yaml:530` passes
`VITE_SENTRY_DSN=${{ secrets.VITE_SENTRY_DSN }}` as a build-arg; it only awaits an
out-of-band DSN secret (operational, no code). So the genuine remaining work is
(1) and (2), and this batch delivers both as small, additive, reviewable PRs.

**Risk discipline — why a separate `k8s/monitoring/` kustomization, not the prod
overlay.** `deploy-prod` runs `kubectl apply -k k8s/overlays/prod` on **every push
to `qa`** (`ci-cd.yaml:618`). If the monitoring stack lived in the prod overlay,
merging it would **auto-deploy Prometheus + Alertmanager + Grafana onto the live
single-node droplet** with no operator opt-in — a real, resource-heavy production
change riding in on a docs-grade PR. Instead the stack lives in a **standalone
`k8s/monitoring/` directory that the prod overlay does not reference**, so
`kubectl apply -k overlays/prod` ignores it. The PRs only add **CI-validated
artifacts**; the operator runs `kubectl apply -k k8s/monitoring` deliberately,
when the droplet has headroom. This is the exact "drop-in artifact" philosophy
the prior four batches used — extended one step closer to live.

## D. Concrete implementation plan

### OACT-1 — Prometheus manifest + CI gate *(New / Infra — build first)*

**Create `k8s/monitoring/`** as a standalone kustomization (sibling of
`k8s/base`, **not** referenced by any overlay):

- `k8s/monitoring/kustomization.yaml` — `namespace: openshiksha-prod`,
  `resources: [prometheus.yaml]` (OACT-2/3 append to this list).
- `k8s/monitoring/prometheus.yaml`:
  - **ConfigMap `prometheus-config`** with `prometheus.yml`:
    - `scrape_configs`: one job `openshiksha-backend` targeting the existing
      `backend` Service (port 8000) at `/metrics`, with a `bearer_token` /
      `authorization` header carrying `METRICS_TOKEN` (the MET-1 gate requires
      it). Prefer a `bearer_token_file` mounted from the `openshiksha-secrets`
      Secret over an inline token. Scrape interval 30s.
    - `rule_files: ['/etc/prometheus/rules/openshiksha-alerts.yml']`.
    - `alerting.alertmanagers` left empty here (OACT-2 fills it).
  - **ConfigMap `prometheus-rules`** = the verbatim contents of
    `docs/ops/prometheus/openshiksha-alerts.yml` (the execute agent copies the
    file body into the ConfigMap; keep `docs/ops/...` as the source of truth and
    note the copy relationship in a comment so the `alerting-lint` job still
    validates the canonical file).
  - **Deployment `prometheus`** — `prom/prometheus:v2.54.1` (pin a real tag),
    mounts both ConfigMaps + an `emptyDir` for TSDB (`--storage.tsdb.retention.time=7d`
    keeps disk small on the droplet), `requests: 100m/256Mi`, `limits:
    500m/512Mi`, readiness/liveness on `/-/ready` / `/-/healthy`.
  - **Service `prometheus`** ClusterIP :9090.
- **CI:** extend the `k8s-manifests` job (`ci-cd.yaml:84`) — after the
  `qa prod` overlay loop, add `kubectl kustomize k8s/monitoring | kubeconform
  -strict -summary -ignore-missing-schemas -kubernetes-version 1.31.0 -`.

**Verify:** `kubectl kustomize k8s/monitoring` renders; kubeconform `-strict`
passes; `kubectl kustomize k8s/overlays/prod` output is **byte-for-byte
unchanged** (prove the overlay doesn't pull monitoring in). **What could go
wrong:** kubeconform `-strict` rejecting a mis-keyed field — that's the gate
working. The `METRICS_TOKEN` Secret key must exist in `openshiksha-secrets`
(document it in OACT-5; the manifest references it but the operator provisions it).

### OACT-4 — Wire `record_backup_run` into the backup CronJob *(Improve / Infra — independent)*

The `record_backup_run` management command and the `openshiksha_backup_age_seconds`
gauge already exist (`backend/.../management/commands/record_backup_run.py`,
`backend/.../core/metrics.py:145`) and are tested — but **nothing calls the
command in prod**, so the gauge always reads the no-data sentinel. The backup pod
runs the `openshiksha-backup` image (`postgres:15-alpine` + `mc`), which has **no
Django**, so it can't run the command itself.

**Restructure `k8s/overlays/prod/backup-cronjob.yaml`** to a two-phase pod:

- **initContainer `backup`** = the existing `openshiksha-backup:prod` container
  (same env), but `pg_backup.sh` additionally writes a result file to a shared
  `emptyDir` (`/work/result.env`) with `STATUS=success|failure`, `SIZE=<bytes>`,
  `KEY=<s3 object key>`. (Small edit to `scripts/backup/pg_backup.sh`.)
- **main container `record`** = `openshiksha-backend:prod`, mounts the same
  `emptyDir` + `DATABASE_URL`, runs a one-liner:
  `set -a; . /work/result.env; python manage.py record_backup_run --status "$STATUS" --size "$SIZE" --key "$KEY" || true`.
  The `|| true` guarantees the record step **can never fail the backup** — a
  missing gauge update is strictly better than a broken backup.

initContainers run to completion before the main container, giving the sequencing
for free (no parallel-container race).

**Verify:** `kubectl kustomize k8s/overlays/prod | kubeconform -strict` green;
existing `test_metrics_backup.py` still passes (command/gauge unchanged); confirm
the qa overlay output is unchanged (this file is prod-only already). **What could
go wrong:** the backend image's entrypoint/workdir — ensure the `record` container
overrides any default entrypoint with an explicit `command:`/`args:` so it runs
`manage.py` from the right dir. **This file auto-deploys on the next `qa` push** —
the `|| true` and the contained blast radius (only the nightly backup pod) keep it
safe, but call it out in the PR description.

detector and mounting it on the ceiling with a battery in it.
