# Daily Plan — 2026-06-13

## A. Today's objective

**Finish the Language Access teacher surface (LA-6) and add the locale-aware
date/number layer (LA-8).** After today a Hindi-medium teacher can run their
whole workflow — dashboard insights, authoring an assignment/problem set/
question, the question bank, the grading queue, and assignment detail — in
Hindi, with dates and counts formatted for the active locale instead of
hardcoded English.

## B. Why this matters

LA-1..5 (student + parent + public chrome) and LA-7 (localized emails) have
shipped. The **teacher surface is the last large English-only island** in the
product: only 4 of ~23 teacher `.tsx` files call `useT()` today (the in-flight
dashboard-panel work), the other ~19 — authoring, question bank, grading,
assignment detail — are still hardcoded English. Teachers are the gatekeepers:
a Hindi-medium teacher who can't author or grade in their language can't onboard
their students, so this directly unblocks adoption in exactly the CBSE/State-
Board schools the platform targets.

LA-8 matters because half-localized dates read *worse* than English (the LA-3
ledger lesson: "3 दिन में" beats "in 3 days में"). LA-3 already added the
`date-fns` `hi` locale for **relative** dates; LA-8 finishes the job for
**absolute** dates ("27 मई"), due-date labels, and numeric counts via a single
`Intl`-backed helper, so no surface invents its own ad-hoc formatting again —
the same "one repeatable guard/helper" pattern as the parity test and the perf
budget. It also back-fills the dates inside the LA-7 emails (noted as deferred
there).

Why this batch and not a new initiative: Language Access is the top active bet
with unblocked increments left (LA-6, LA-8, LA-9). LA-6 is the highest-leverage
remaining surface; LA-8 is foundation-hardening that every prior and future LA
surface reuses. LA-9 (third-language pilot) and LA-10 (authored-content
translation) stay queued — LA-10 explicitly needs product design before start.

## D. Concrete implementation plan

### PR 1 — LA-8: locale-aware date/number helper (Improve/hardening)

- **New file `frontend_modern/src/shared/i18n/format.ts`:**
  - `formatDate(value: string | Date, locale: 'en'|'hi', opts?: Intl.DateTimeFormatOptions)`
    using `new Intl.DateTimeFormat(locale === 'hi' ? 'hi-IN' : 'en-IN', opts)`.
    Default to a medium style ("27 मई 2026" / "May 27, 2026"); accept `opts`
    overrides for short/long. Guard invalid dates (return the raw string, never
    throw).
  - `formatNumber(value: number, locale)` via `Intl.NumberFormat` (Devanagari
    digits are **not** wanted for K-12 product counts — keep Latin digits; use
    `'en-IN'`/`'hi-IN'` grouping only). Document that choice in a code comment so
    a later session doesn't "fix" it to Devanagari digits.
  - A `useFormat()` hook that reads the active locale from the i18n context and
    returns bound `formatDate`/`formatNumber` (mirrors `useT()`), so callers do
    `const { formatDate } = useFormat()`.
- **Swap ad-hoc absolute-date rendering** to the helper on the cards that
  currently hardcode `toLocaleDateString()`/`split('T')` formatting — grep
  `toLocaleDateString\|toISOString().split\|new Date(` under
  `frontend_modern/src/features/` and convert the **absolute** date displays on
  student `AssignmentCard` and teacher `CreateAssignmentPage` due-date chips.
  Leave relative dates alone (date-fns `hi` already handles those from LA-3).
- **Verify:** new `format.test.ts` — en vs hi medium date, opts override, invalid
  input passthrough, number grouping; one card test asserting the hi date string
  renders. `npm run lint && npx tsc --noEmit && npx vitest run`; `npm run build`
  entry-chunk guard (Intl is native — zero bundle cost; confirm no date-fns
  format import sneaks into the entry chunk).
- **Risk:** low — `Intl` is built-in and well-supported. Only behavioral change
  is date *string format*; keep it visually equivalent in English (spot-check the
  card before/after).

## F. Legacy analysis & improvement opportunities

- **Legacy (Django 1.11) had no teacher i18n** — server-rendered English
  templates, no language preference, no `Intl`. Pure "improve"; nothing to port.
- **What we keep from legacy vocabulary:** Indian teachers say "assignment",
  "submit", "marks", "question bank" in English in the classroom — the Glossary
  transliterates these (असाइनमेंट, प्रश्न बैंक) rather than forcing Sanskritized
  forms, so the Hindi UI reads like a Hindi-medium teacher actually talks.
- **Modern advantage:** centralized strings + a native `Intl` layer mean every
  teacher surface localizes for the cost of key extraction, and the same
  `formatDate`/`formatNumber` helper carries forward to LA-9's regional language
  and back into the LA-7 emails — capability that compounds instead of being
  re-solved per surface.
