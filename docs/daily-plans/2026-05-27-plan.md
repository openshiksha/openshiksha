> **Context**: The last three sessions shipped a dense run of AI features — Natural Language Explanations (PR #92), LLM Question Generation (PR #94), and Teacher Weekly Class Summary Reports (PR #95) are all merged to `modernization`. ## B. Why This Matters

A learning platform with no real questions cannot be piloted with a real school. Everything built so far — grading, proficiency, SRS, explanations, weekly reports — is downstream of *content*. Right now those systems run on demo data and one-off LLM generations, which means:

- **No teacher can build a real assignment** from a curated, verified question bank.
- **Proficiency/analytics are meaningless** without a stable, curriculum-aligned question corpus.
- **The AI features can't be evaluated** against real student work on real questions.

The legacy Cabinet holds 679 questions that were authored, reviewed, and used in production by real teachers. They are the most valuable asset in the legacy system and the cheapest way to make the modern platform real. Importing them turns OpenShiksha from a feature showcase into a usable product.

This was planned as P8-prep on 2026-05-26 (Priority 3) but **was not completed** — the fields were never added and no command exists. Today we finish it properly and go further: not just the prep, but a working importer.

### Priority 2: P8b — `import_cabinet_questions` management command

**File**: `backend/openshiksha/apps/core/management/commands/import_cabinet_questions.py` (new)

**Invocation**:
```bash
python manage.py import_cabinet_questions --source /path/to/openshiksha-cabinet/questions [--dry-run] [--mapping mapping.json]
```

**What it does**:

1. **Read** Cabinet question JSON files from `--source` (a local clone of `openshiksha-cabinet`). Each legacy question is a JSON blob with subparts.

2. **Convert legacy format → modern schema** (the core value of this command):

   | Legacy (Cabinet) | Modern (`QuestionSubpart`) | Conversion |
   |---|---|---|
   | `_{var}_` token syntax | `{{var}}` | regex `_\{(\w+)\}_` → `{{\1}}` (matches Croupier's Jinja-style substitution) |
   | `pow(base, exp)` | `base**exp` | regex/AST rewrite of `pow(x, y)` → `(x)**(y)` |
   | `options: {"1": "...", "2": "..."}` | `options: [{"key": "A", "text": "..."}]` | integer keys 1–4 → A–D |
   | `answer: "2"` (option index) | `correct_answer: {"type": "mcq", "answer": "B"}` | map index → letter |
   | `solution` | `solution_text` | direct (after token conversion) |
   | `hint` | `hint_text` | direct (after token conversion) |
   | `constraints: {"x": {"min":1,"max":10,"step":1}}` | `variable_constraints` | direct passthrough (already compatible) |

3. **Match legacy subject/chapter IDs to modern DB records** via an optional `--mapping` JSON file (legacy MySQL ID → modern name). If no mapping is provided, **create placeholder `Subject`/`Chapter` records** named `Imported: <legacy_id>` so the import never hard-fails on missing taxonomy — placeholders can be reconciled later.

4. **Idempotent upsert**: tag each imported question with a `cabinet_legacy_id` (stored in the question's `tags` M2M as `cabinet:<id>`, or a dedicated nullable field if cleaner). Re-running the command updates rather than duplicates. **Decision (autonomous):** use a `QuestionTag` of form `cabinet:<legacy_id>` to avoid a second migration this session; revisit a dedicated field if dedup proves fragile.

5. **`--dry-run`**: parse and convert everything, print a summary table (N questions, N subparts, N new subjects/chapters created, N skipped with reasons) but write nothing.

**Robustness**:
- Wrap each question in try/except; a single malformed question logs a warning and is skipped, not fatal.
- Print a final report: imported / updated / skipped counts.
- `--limit N` flag for testing against a small batch first.

**Note on data availability**: The 679-question Cabinet repo is a separate GitHub repo not present in this working tree. The command is built and unit-tested against **synthetic fixture JSON** that mirrors the legacy format (committed under `apps/core/tests/fixtures/cabinet_sample/`). The actual bulk import is run manually once the Cabinet repo is cloned locally — the command is the deliverable, the 679-row run is an operational follow-up.

### Dependencies / Blockers

- **No blocker for fields + command + display** — all buildable against fixtures today.
- **Bulk run blocked on** a local clone of `openshiksha-cabinet` and (ideally) the legacy MySQL ID→name mapping. Both are operational, not code, and the placeholder path means the command works without the mapping.

### What Could Go Wrong

- **`pow()` rewrite edge cases**: nested `pow(pow(x,2),3)` or `pow` with expressions as args. Use a proper tokenizer/AST pass rather than naive regex for the power conversion; fall back to leaving the expression untouched + logging if rewrite is ambiguous.
- **Option count ≠ 4**: some legacy MCQs may have 2, 3, or 5 options. Map dynamically (1→A, 2→B, …) rather than assuming exactly four.
- **Token collisions**: a question containing a literal underscore-brace sequence that isn't a variable. Constrain the regex to `_\{[a-zA-Z_]\w*\}_` (valid identifier only).
- **Placeholder sprawl**: importing without a mapping creates many `Imported: <id>` subjects. Acceptable — clearly labeled, reconcilable, and the alternative (hard-fail) is worse.

## F. Legacy Analysis & Improvement Opportunities

### Cabinet Question Storage (today's focus)

**Legacy**: Questions lived in the **Cabinet microservice** — an external HTTP filesystem service. The Django app fetched question content live from Cabinet at grading and rendering time (`cabinet/client.py`). Each question was a JSON blob with:
- `_{var}_` substitution tokens
- `pow(base, exp)` Python-2 math notation
- Integer-keyed options (`{"1": ..., "2": ...}`)
- `solution` and `hint` free-text fields
- `constraints` for variable randomization

**What was good**: Centralized content, editable independently of code, rich metadata (solutions + hints), built-in randomization via constraints.

**What was limited**:
- **Runtime coupling** — grading and rendering required a live HTTP call to Cabinet; if Cabinet was down, the platform couldn't serve or grade questions.
- **No offline/seed capability** — couldn't run the stack without Cabinet.
- **Python-2 idioms** (`pow()`, integer keys) baked into the content.

**Modern improvement**:
- Content lives **directly in the Django DB** (`question_text`, `options`, `correct_answer`, and now `solution_text`/`hint_text`) — no microservice dependency, offline grading, seedable.
- `{{var}}` Jinja-style tokens align with the modern Croupier.
- A/B/C/D option keys match the modern MCQ grader.
- The import is a **one-time migration**, not a runtime dependency — strictly better operationally.
- **Bonus**: `solution_text` now also serves LLM-generated solutions and is surfaced to students inline — a capability the legacy platform never had (solutions were teacher-only in the answer key).
