# OpenShiksha Daily Plan — 2026-05-23

> **Context**: Yesterday shipped Activity Streaks (StudentStreak model + signal + badge), Question Content Search (subpart text + tag search), and Remedial Auto-Creation (grade < 30% → targeted problem set, PR #84, 318 tests). The three remaining gaps: SRS drill sessions don't update proficiency or streaks; questions can't carry images; and remedial assignments are class-wide instead of per-student.

---

## A. Today's Objective

Wire SRS drill completions into the proficiency engine and streak system so that a student who practices daily via drills actually sees their proficiency improve and their streak count — closing the feedback loop that makes spaced repetition feel rewarding rather than invisible.

---

## B. Why This Matters

- **SRS → Proficiency Gap**: Students completing drill sessions via the SRS Practice Drill Page get SM-2 schedule updates (next review date moves out) but their `StudentProficiency` score stays unchanged. A student who drills algebra every day and masters it still shows 45% in the proficiency bar. This is demotivating and factually wrong. Every drill session answer is graded with `_grade_subpart()` — the data is already there; it just doesn't create Tick records or queue `update_proficiency`.

- **SRS → Streak Gap**: The streak signal fires on Submission `submitted_at`. Drill sessions never create a Submission — they're pure SM-2 updates. A student who studies via drills instead of assignments gets no streak credit, which discourages the study habit the SRS system is designed to build. This should take 10 lines to fix.

- **Question Images**: Real-world K-12 questions for science, geography, and math frequently reference diagrams. Without image support on QuestionSubpart, teachers cannot author any question that needs a figure — roughly 30–40% of CBSE science questions include diagrams. The modern architecture stores question content in the DB; adding a nullable `image_url` field is non-breaking and unblocks this entire category.

- **Per-Student Remedials**: Yesterday's remedial system creates an Assignment for the entire SubjectRoom when any student fails. Student B who scored 80% sees "Remedial Practice" in their dashboard because Student A scored 20% — confusing and noisy. The fix is structural: create per-student assignments (a new Assignment row per failing student, sharing one ProblemSet) rather than a single class-wide assignment.

### Priority 1: SRS Drill → Proficiency + Streak Integration

**PR target**: `feat/2026-05-23-srs-proficiency-streak`

#### Background

`mark_reviewed` in `backend/openshiksha/apps/ai/views.py` (line 456) currently:
1. Grades answers via `_grade_subpart()` — score computed ✅
2. Updates SM-2 fields on `SpacedRepetitionEntry` — schedule updated ✅
3. Returns the updated entry — done ✅

Missing:
- No `Tick` records created → `update_proficiency` has nothing new to aggregate
- No `streak.record_activity()` called → daily drills don't count

#### Step 1 — Create Tick records in `mark_reviewed`

After line 551 (`entry.save(...)`), before building the response, add:

```python
# --- Side effects: proficiency engine and streak ---

# (a) Create Tick records for each graded subpart so proficiency can update
if answers is not None and subparts:
    from openshiksha.apps.edge.models import Tick
    from openshiksha.apps.core.models import SubjectRoom

    # Find a SubjectRoom for this student + chapter so Tick has a subject_room FK
    subject_room = (
        SubjectRoom.objects.filter(
            classrooms__students=entry.student,
            subject=entry.knowledge_node.chapter.subject,
        )
        .order_by("-id")
        .first()
    )
    if subject_room:
        ticks = []
        for subpart in subparts:
            student_answer = answers.get(str(subpart.id))
            if student_answer is None or student_answer == "":
                continue
            fraction = _grade_subpart(
                question_type=subpart.question.question_type,
                student_answer=student_answer,
                correct_answer=subpart.correct_answer or {},
                student_id=request.user.id,
                subpart_id=subpart.id,
                original_options=subpart.options,
                variable_constraints=subpart.variable_constraints,
            )
            ticks.append(
                Tick(
                    student=entry.student,
                    question_subpart=subpart,
                    submission=None,   # SRS drills have no Submission row
                    subject_room=subject_room,
                    mark=fraction,
                )
            )
        if ticks:
            Tick.objects.bulk_create(ticks)
            # Queue proficiency update downstream
            from openshiksha.apps.edge.tasks import update_proficiency
            update_proficiency.delay(entry.student_id, subject_room.id)
```

**Design note**: `Tick.submission` is nullable — check the model to confirm; if not, make it nullable in this PR. SRS drills are a separate activity source from normal submissions; the `submission=None` makes this explicit. This also means `SubjectRoomQuestionMistake` aggregates will include drill errors — desirable behaviour.

#### Step 2 — Call `streak.record_activity()` after SM-2 update

After the `entry.save(...)` call:

```python

from openshiksha.apps.core.models import StudentStreak
streak_obj, _ = StudentStreak.objects.get_or_create(student=entry.student)
streak_obj.record_activity(timezone.localdate())
```

This is 2 lines. The same `record_activity()` idempotency guard (same-day no-op) prevents double-counting if a student does multiple drill sessions in one day.

Check `Tick` model in `backend/openshiksha/apps/edge/models.py`. If `submission` FK is non-nullable, add `null=True, blank=True`. Create migration: `makemigrations edge --name="make_tick_submission_nullable"`. Non-breaking — existing rows are unaffected.

#### What Could Go Wrong

- **`SubjectRoom` lookup ambiguity**: A student in two SubjectRooms for the same subject (e.g., transferred) — we take `order_by("-id").first()` which gives the most recent. Acceptable for Phase 1.
- **`Tick.submission` non-nullable**: If the DB constraint rejects `submission=None`, the `bulk_create` will throw. Verify the model and add migration before this code.
- **Double grade computation**: The score is already computed above (lines 490-510). The Tick-creation block re-calls `_grade_subpart()` for each subpart. This doubles computation. Optimization: cache the per-subpart fraction in a dict during the first grading pass and reuse it in the Tick loop. Worth doing to avoid the double call.

**Better approach** — refactor the grading loop to build both the score and the Tick list in one pass:

```python
per_subpart_fractions = {}  # subpart.id → fraction
for subpart in subparts:
    fraction = _grade_subpart(...)
    per_subpart_fractions[subpart.id] = fraction
    correct_sum += fraction
    total += 1

# Then build Ticks using per_subpart_fractions
ticks = [
    Tick(student=..., question_subpart=sp, ..., mark=per_subpart_fractions[sp.id])
    for sp in subparts
]
```

This avoids calling `_grade_subpart` twice and keeps the view cleaner.

### Priority 3: Per-Student Remedial Assignments

**PR target**: `feat/2026-05-23-per-student-remedials`

**Classification**: Improve (yesterday's Port was class-level; this makes it student-level)

#### Problem with current implementation

`_create_remedial_assignment` in `tasks.py` creates one `Assignment` pointing to `subject_room=orig.subject_room`. This Assignment is visible to ALL students in the class. The idempotency check uses `submissions__student=submission.student` but that checks if the student has a _Submission_ for the remedial — which hasn't been created yet.

The fix: instead of one class-wide Assignment, create one Assignment per failing student, scoped to that student.

#### Approach: Add `target_student` FK to Assignment

**File**: `backend/openshiksha/apps/core/models.py`, `Assignment` class

```python
target_student = models.ForeignKey(
    "User",
    on_delete=models.CASCADE,
    null=True,
    blank=True,
    related_name="targeted_assignments",
    limit_choices_to={"role__in": ["student", "open_student"]},
    help_text="If set, only this student sees this assignment (used for remedials). Null = class-wide.",
)
```

Migration: `makemigrations core --name="add_assignment_target_student"`. Non-breaking — all existing assignments have `target_student=None` (class-wide, unchanged behaviour).

#### Update `_create_remedial_assignment`

```python
# Idempotency: check if remedial for THIS student on THIS source assignment already exists
if Assignment.objects.filter(
    problem_set__is_remedial=True,
    problem_set__source_assignment=submission.assignment,
    target_student=submission.student,
).exists():
    return

# ... (same ProblemSet creation as before) ...

Assignment.objects.create(
    problem_set=remedial_ps,
    subject_room=orig.subject_room,
    due_at=due,
    created_by=orig.created_by,
    target_student=submission.student,   # ← scope to this student only

```

#### Update API filter in `AssignmentViewSet`

**File**: `backend/openshiksha/apps/api/views/core.py`, `AssignmentViewSet.get_queryset()`

Students should only see:
- Class-wide assignments (`target_student=None`)
- Assignments targeted specifically to them

```python
if user.role in (UserRole.STUDENT, UserRole.OPEN_STUDENT):
    qs = qs.filter(subject_room__classrooms__students=user).filter(
        models.Q(target_student=None) | models.Q(target_student=user)
    )
```

This is the critical filter — without it, `target_student` has no effect on the frontend.

#### Update `ProblemSetAdmin` / `AssignmentAdmin`

Add `target_student` to `AssignmentAdmin` list display and fieldsets for visibility.

#### Update tests in `test_remedial.py`

- `test_remedial_only_visible_to_failing_student` — passing student should NOT see remedial in their assignment list
- `test_remedial_idempotent_per_student` — two students fail the same assignment → two separate remedial Assignments

#### What Could Go Wrong

- **SubjectRoom scope**: The remedial Assignment still has `subject_room=orig.subject_room`. If the student is removed from the SubjectRoom, the `target_student` filter still returns the assignment but they can't navigate to the room. For Phase 1, acceptable — a teacher-driven edge case.
- **Existing remedials**: Remedials created yesterday (before `target_student` existed) have `target_student=None` → they're class-wide. After this migration, those old remedials will still show to all students. This is a one-time inconsistency; acceptable since there's no production data yet (all test data).
- **`number` uniqueness on ProblemSet**: The `unique_together = [("subject_room", "number")]` constraint on ProblemSet means if two students fail the same assignment at the same time, two concurrent `_create_remedial_assignment` calls might both try to use `max(number) + 1` and collide. Use `select_for_update()` on the `max(number)` query, or switch to a UUID-based slug. For Phase 1, since `CELERY_TASK_ALWAYS_EAGER=True` in dev, this is synchronous and safe; flag for production hardening.

## F. Legacy Analysis & Improvement Opportunities

### SRS Drill Integration (Priority 1)

**Legacy**: No SRS system existed. The legacy platform was purely assignment-driven — teachers assigned, students submitted. There was no independent practice mechanic. The SM-2 engine, drill UI, and knowledge node system are all new.

**Modern gap**: We built a complete SRS system but left it isolated from the proficiency and gamification layers. This is a typical "build feature in isolation" mistake — the feature works end-to-end but doesn't affect any of the numbers students care about (proficiency score, streak count). Today's fix creates the missing bridges.

**Design principle**: Every student action that involves answering a question should flow through the same downstream pipeline — `Tick → update_proficiency → StudentProficiency`. The grading task enforces this for normal submissions. The SRS drill path bypassed it. Today we enforce the invariant consistently.

### Question Images (Priority 2)

**Legacy**: Cabinet stored images as base64-encoded binary files on the Cabinet filesystem. The legacy `sphinx/` question authoring UI had an image upload widget that called `build_image()` on the Cabinet API. Images were referenced in `QuestionSubpart` by a Cabinet-assigned ID, and the frontend called a Cabinet endpoint to get a signed URL for display.

**Modern improvement**: The legacy Cabinet image approach required the Cabinet microservice to be running for any question with an image to display — a tight coupling that broke offline use. The modern approach uses URL references: teachers paste a publicly accessible URL (or, Phase 2, upload via a Django media endpoint). This works offline if the URL is on the same server and simplifies the architecture significantly. The trade-off is that legacy Cabinet images need an import path to extract and re-host as URLs — this is part of the future Cabinet import task.

### Per-Student Remedials (Priority 3)

**Legacy**: The `grader/` remedial system created remedials with a `GenericFK` that could target either a `SubjectRoom` (class-wide) or a `User` (student-specific). The teacher could configure this per-school. The modern MVP (PR #84) only supports class-wide (simpler model). Today's improvement adds student-targeting cleanly via a `target_student` FK — matching the per-student mode of the legacy system but without the complexity of `GenericFK`.

**Legacy limitation**: Legacy remedials were full copies of the original problem set (all questions). The modern version already improves on this by targeting only wrong questions. Today's per-student work builds on that: each student gets a problem set with only their wrong questions, not a shared "class remedial" with everyone's wrong questions combined.
