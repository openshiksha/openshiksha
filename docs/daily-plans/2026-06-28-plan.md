# OpenShiksha — Daily Plan, 2026-06-28

> The top initiative is **Production Observability & Operational Readiness**
> ([`docs/initiatives/2026-production-observability.md`](../initiatives/2026-production-observability.md)).
> Batch 1 (OBS-1..5) made a prod incident **seeable**, Batch 2 (MET-1..5) made the
> system **measurable**, Batch 3 (BAK-1..5) made the data **recoverable**. This
> plan scopes the **final** batch — **Batch 4 — Uptime & alerting** — which makes
> the system **self-announcing**: an operator is *pushed* a notification when
> something is wrong, instead of having to go look. This batch closes the
> initiative's North Star.

## A. Today's objective

Advance Production Observability into **Batch 4 — Uptime & alerting**: turn the
signals the last three batches produced (probe health, the gated `/metrics`
gauges, the `openshiksha_backup_age_seconds` freshness gauge) into **pushed
alerts** an operator actually receives — plus a **standalone in-cluster uptime
probe** that works even before a Prometheus is deployed. Everything is additive,
optional, and validated; nothing changes dev/CI/qa behaviour.

## B. Why this matters

The platform is **live in production** and now richly instrumented, but the
instrumentation is **pull-only and passive**: the Batch-2 `/metrics` and the
Batch-3 Grafana dashboard require an operator to *go look*, and **no Prometheus
or Alertmanager is even deployed in `k8s/`** (the dashboard JSON and metric
catalogue are drop-in artifacts for an operator who stands one up). A backup that
silently stops, a grade queue that silently backs up, a pod whose readiness flips
to 503 — today **nobody is told**. The North Star of this initiative is *"a
clean-checkout operator can see, within minutes, that something is wrong"* — and
"within minutes" means **push, not poll**. Batch 4 delivers the missing half:
alert rules expressed against the metrics we already emit, a routing path to a
channel the team already uses (**ntfy**, already wired for build notifications),
and a dependency-free uptime probe so the most basic "is the site up?" signal
exists **even with no monitoring stack at all**. With this, the operability spine
(observable → measurable → recoverable → **alerting**) is complete and the
initiative reaches its North Star.

## D. Concrete implementation plan

### ALT-1 — Prometheus alerting-rules artifact _(New / Docs)_ — **foundation**
- **File:** `docs/ops/prometheus/openshiksha-alerts.yml` — a standard Prometheus
  rule file (`groups:` → `rules:` with `alert:`/`expr:`/`for:`/`labels.severity`/
  `annotations.summary`+`description`). Sibling in spirit to the existing
  `docs/ops/grafana/openshiksha-overview.json`; an operator points
  `rule_files:` at it.
- **Alerts (all against metrics that already exist** — verified in
  `backend/openshiksha/apps/core/metrics.py`**):**
  - `OpenShikshaBackupStale` — `openshiksha_backup_age_seconds > 129600` (36 h)
    `for: 10m`, severity `critical`. (Gauge omitted when no backup history ⇒ pair
    with `OpenShikshaBackupNeverRun`: `absent(openshiksha_backup_last_success_timestamp)`
    `for: 6h` so a *total* outage that emits no gauge still fires — this is the
    honest-empty-case lesson from BAK-4 turned into an alert.)
  - `OpenShikshaGradeQueueBacklog` — `openshiksha_submissions_pending_grading > 50`
    `for: 30m`, severity `warning`.
  - `OpenShikshaCeleryFailureRate` — ratio of
    `openshiksha_celery_tasks{status="FAILURE"}` to total over the 24 h window
    above a threshold, severity `warning`. (Honest no-op under the default Redis
    result backend — document that this alert only has data when MET-3's
    `django-db` backend is active.)
  - `OpenShikshaCeleryOldestPending` —
    `openshiksha_celery_oldest_pending_seconds > 900` `for: 15m`, severity `warning`.
  - `OpenShikshaHighHTTPErrorRate` —
    `sum(rate(openshiksha_http_requests_total{status_class="5xx"}[5m])) /
    sum(rate(openshiksha_http_requests_total[5m])) > 0.05` `for: 10m`,
    severity `critical`.
  - `OpenShikshaHighLatencyP95` — `histogram_quantile(0.95,
    sum(rate(openshiksha_http_request_duration_seconds_bucket[5m])) by (le)) > 1.5`
    `for: 10m`, severity `warning`. (Verify the exact metric/bucket name against
    MET-4's `openshiksha_http_request_duration_seconds` histogram before
    committing the expr.)
  - `OpenShikshaTargetDown` — `up{job="openshiksha-backend"} == 0` `for: 5m`,
    severity `critical` (scrape-target down ⇒ `/metrics` unreachable).
- **Verify:** `promtool check rules docs/ops/prometheus/openshiksha-alerts.yml`
  passes (install `prometheus` locally or run in the ALT-4 CI job). Cross-check
  **every** metric/label name against `apps/core/metrics.py` and `docs/ops/metrics.md`
  so no alert references a metric that doesn't exist.
- **What could go wrong:** an expr referencing a renamed/absent metric (mitigated
  by the name cross-check + `promtool`); over-tight thresholds that page on
  normal load (start conservative, document them as a starting point in ALT-5,
  same "operator tunes" framing as the Grafana starter).

### ALT-2 — Alertmanager config + ntfy bridge _(New)_ — independent of ALT-1
- **`docs/ops/alertmanager/alertmanager.yml`** — minimal Alertmanager config: a
  `route` (group by `alertname`/`severity`, sane `group_wait`/`repeat_interval`)
  to a single `webhook_configs` receiver pointed at the bridge's URL; a comment
  block showing how to add an `email_configs` receiver as an alternative. No
  secrets in the file (the ntfy topic/URL is injected via the bridge's env).
- **`scripts/ops/alert_to_ntfy.py`** — a tiny, dependency-light bridge
  (stdlib `http.server` + `urllib.request`, **no new pip dep**) that accepts an
  Alertmanager webhook POST and, for each alert, POSTs a **one-line** message to
  `ALERT_NTFY_URL` with `Title`/`Tags`/`Priority` headers derived from
  `severity` (critical ⇒ high priority + `rotating_light`; warning ⇒ default +
  `warning`). Firing vs resolved reflected in the title.
- **Why a bridge:** ntfy isn't a native Alertmanager receiver (Alertmanager posts
  its own JSON schema); the ~60-line bridge is the standard glue and is trivially
  **unit-testable** — that's what makes this "tested config," not just YAML.
- **Tests (`pytest`, e.g. `scripts/ops/tests/test_alert_to_ntfy.py` or under
  `backend` tests):** feed a representative Alertmanager webhook payload (firing,
  one critical + one warning) to the **formatter function** (factor the
  payload→(title, body, headers) mapping out of the HTTP handler) and assert the
  one-line title/tags/priority mapping; assert a `resolved` payload formats as a
  resolution. No real network — the POST is the seam, the formatter is pure.
- **Verify:** `amtool check-config docs/ops/alertmanager/alertmanager.yml` passes
  (ALT-4 runs it in CI); `python -m py_compile scripts/ops/alert_to_ntfy.py`;
  the formatter unit tests pass.
- **What could go wrong:** leaking the ntfy URL into logs (read from env, never
  echo); multi-line messages (the memory/notify convention is **single line** —
  enforce in the formatter); making the bridge a heavyweight service (keep it a
  single stdlib file, documented as a sidecar/one-off, not a new always-on dep).

### ALT-3 — Standalone in-cluster uptime probe CronJob _(New)_ — prod-overlay-only
- **`scripts/ops/uptime_probe.sh`** (`set -euo pipefail`): curl
  `${PROBE_BASE_URL}/healthz/` and `${PROBE_BASE_URL}/readyz/` (in-cluster
  Service DNS, e.g. `http://backend:8000`); on any non-200 (or curl failure),
  POST a single-line alert to `ALERT_NTFY_URL` (`Title: OpenShiksha DOWN`,
  high priority, `rotating_light` tag) including which endpoint failed + the
  status code; exit non-zero so the Job is marked failed (feeds Batch-2 Celery/Job
  visibility too). Success path is silent (no per-run spam). Never echo secrets.
- **`k8s/overlays/prod/uptime-probe-cronjob.yaml`** — `batch/v1 CronJob`
  (`schedule: "*/5 * * * *"`, `concurrencyPolicy: Forbid`,
  `successful/failedJobsHistoryLimit: 3`, `backoffLimit: 1`,
  `restartPolicy: OnFailure`), running a **curl-capable image** (reuse
  `Dockerfile.backup`'s `postgres:15-alpine` base which has `curl`/`wget`, **or**
  a pinned `curlimages/curl` — prefer reusing an already-published image to avoid
  a new CI publish target; decide at build time and note it). Env: `PROBE_BASE_URL`
  from the ConfigMap, `ALERT_NTFY_URL` from `openshiksha-secrets`. Referenced
  **only** from `k8s/overlays/prod/kustomization.yaml` `resources:` (the same
  prod-overlay-only pattern as `backup-cronjob.yaml`) so qa/dev kustomize output
  is unchanged.
- **Secret docs:** append `ALERT_NTFY_URL` (and note `PROBE_BASE_URL` is a
  non-secret ConfigMap value) to `k8s/base/secret.example.yaml`, empty, with a
  comment (the ntfy topic URL; server-side only).
- **Verify:** `shellcheck scripts/ops/uptime_probe.sh` clean; a **local** run
  against `docker compose` (point `PROBE_BASE_URL` at the dev backend, set
  `ALERT_NTFY_URL` to a scratch ntfy topic, confirm a forced 503 pushes exactly
  one message); `kustomize build k8s/overlays/prod | kubeconform -strict` passes
  and `kustomize build k8s/overlays/qa` is **byte-for-byte unchanged** (diff to
  prove it).
- **What could go wrong:** a transient blip paging every 5 min (acceptable for a
  floor probe; ALT-1's `for:` windows debounce the Prometheus path — note the
  trade-off in ALT-5); breaking the kubeconform gate (run locally first); baking
  a secret into the manifest (use `secretKeyRef`).

### ALT-4 — CI validation of the alerting artifacts _(Improve / Infra)_ — depends on ALT-1+ALT-2
- **`.github/workflows/ci-cd.yaml`** — a small additive job `alerting-lint`
  (mirrors the existing `kustomize|kubeconform` manifest-gate job #459): install
  pinned `prometheus`/`alertmanager` release tarballs (for `promtool`/`amtool`),
  run `promtool check rules docs/ops/prometheus/openshiksha-alerts.yml` and
  `amtool check-config docs/ops/alertmanager/alertmanager.yml`. Optionally
  `promtool test rules` with a tiny unit-test fixture asserting
  `OpenShikshaBackupStale` fires at 37 h and not at 1 h.
- **Why:** the Grafana JSON and now the alert rules are config-as-code referencing
  live metric names; without a gate they rot the first time a metric is renamed.
  This makes Batch 4 self-defending, matching the kubeconform-gate discipline.
- **Verify:** the new job is green on the PR; deliberately break a rule
  (bad `expr`) locally → `promtool` fails (negative check, not committed).
- **What could go wrong:** flaky tool downloads (pin versions + cache); job
  runtime creep (it's a couple of static binaries — keep it lean and parallel to
  existing jobs).

## F. Legacy analysis & improvement opportunities

Alerting/uptime is **greenfield** — the Django 1.11 monolith (now under `legacy/`)
had no metrics, no alert rules, and no uptime monitoring; an outage was discovered
by a user complaint. There is nothing to port. The improvement is the whole point
of the initiative: convert the passive, pull-only instrumentation the last three
batches built into **pushed alerts**, and provide a floor-level uptime alarm that
works **before** any monitoring stack exists — so the very first prod incident
after launch announces itself instead of waiting to be noticed.
