> **Context**: PR #64 merged yesterday — the full student practice loop is now live end-to-end. Students can log in, see assignments, read LaTeX-rendered questions, auto-save answers, submit, and get graded. Teacher dashboard and assignment creation UI are in place. ## A. Today's Objective

Surface the platform's analytical data to users — teacher assignment analytics and student proficiency views — and begin teacher question authoring so the platform can run without admin panel intervention.

---

## B. Why This Matters

The end-to-end loop is functional, but right now the data it generates goes nowhere visible. Every submission is graded, every tick is recorded, StudentProficiency is updated — and none of it surfaces to the users who need it. Teachers can't tell if students are completing assignments or struggling. Students finish assignments and see nothing about how they're doing over time. This is the gap between "technically working" and "useful product." Closing it makes the platform genuinely compelling.

Additionally, teachers currently depend on Django admin to create questions — a hard blocker for any real teacher onboarding. Without question authoring, the platform's content is frozen at whatever seed data or admin-created content exists.

### Priority 1: Teacher Assignment Analytics

**Problem**: `TeacherDashboard.tsx` currently shows only subject rooms + a "New Assignment" button. Teachers have no visibility into existing assignments — who submitted, what scores they got, or how many students completed the work.

**Backend (already exists):**
- `GET /api/assignments/` — returns teacher's assignments (from `assigned_by=user` filter)
- `GET /api/assignments/{id}/submissions/` — returns all submissions for that assignment with student info

The `AssignmentSerializer` exposes: `id`, `subject_room`, `problem_set`, `due_at`, `created_at`. It does **not** yet expose `submission_count` or `avg_score`. These need to be added as annotated fields.

**Backend changes:**

Add `SerializerMethodField`s to `AssignmentSerializer` in `serializers/core.py`:

```python
class AssignmentSerializer(serializers.ModelSerializer):
    submission_count = serializers.SerializerMethodField()
    avg_score = serializers.SerializerMethodField()
    student_count = serializers.SerializerMethodField()

    def get_submission_count(self, obj):
        return obj.submissions.count()

    def get_avg_score(self, obj):
        scores = list(obj.submissions.exclude(score=None).values_list('score', flat=True))
        if not scores:
            return None
        return round(sum(scores) / len(scores), 1)

    def get_student_count(self, obj):
        return obj.subject_room.students.count()
```

**Performance note**: This adds 3 queries per assignment in the list view. For a teacher with 10 assignments, that's 30 extra queries. Fine for now. If this becomes a problem, use `annotate()` on the queryset in `get_queryset()` for teacher role — add as a follow-up optimization note.

**Frontend changes:**

`TeacherDashboard.tsx` — add an "Assignments" section below the subject rooms list:

```
Teacher Dashboard
├── Subject Rooms (existing)
│   └── [room cards]
└── Assignments  ← NEW
    └── [assignment rows: problem set name | subject room | due | X/Y submitted | avg score]
```

New hook: `useTeacherAssignments.ts`
```typescript

// Response includes submission_count, avg_score, student_count
```

**Assignment row UI:**
```

Due Apr 8                                 12/24 submitted  •  Avg: 74%
```
- Completion bar (e.g., half-filled progress bar if 12/24 submitted)
- Overdue styling if `due_at` < now
- Click → navigates to `/teacher/assignments/{id}` (stub page for now, shows submission list)

**Files to create/modify:**

**Backend:**

New endpoint: `GET /api/proficiency/` (or add to `StudentProficiency` as a ViewSet)

Add `StudentProficiencyViewSet` in `views/core.py`:
```python
from openshiksha.apps.edge.models import StudentProficiency

class StudentProficiencyViewSet(viewsets.ReadOnlyModelViewSet):
    permission_classes = [permissions.IsAuthenticated, IsStudent]

    def get_queryset(self):
        return StudentProficiency.objects.filter(
            student=self.request.user
        ).select_related('subject', 'chapter', 'subject_room__classroom')
```

Serializer exposes: `subject_name`, `chapter_name`, `classroom_display`, `score`, `attempts`, `rank` (percentile rank within class).

### Priority 3: Question Authoring UI (Phase 1)

**Problem**: Teachers must use Django admin to create questions. This is the biggest real-world blocker for teacher onboarding. No teacher in a school setting will use Django admin.

**Scope for Phase 1:**
- Create a `Question` with one or more `QuestionSubpart`s
- Fields: chapter (picker), subject (inferred from chapter), difficulty (1–5), question type per subpart, question text, MCQ options (add/remove rows), correct answer, tags (multi-select)
- No image upload (Phase 2)
- No variable substitution/randomization (that's Croupier — later)

**Backend changes:**

Make `QuestionViewSet` writable for teachers:

```python
class QuestionViewSet(viewsets.ModelViewSet):  # was ReadOnlyModelViewSet
    def get_permissions(self):
        if self.action in ['create', 'update', 'partial_update', 'destroy']:
            return [IsAuthenticated(), IsTeacher()]
        return [IsAuthenticated()]

    def perform_create(self, serializer):
        serializer.save(created_by=self.request.user)
```

`QuestionSerializer` needs write support:
- Accept nested `subparts` for create (use `writable_nested` or manual `create()` override)
- `Chapter` picker: expose `GET /api/chapters/?subject=<id>` or use existing chapter list

Also need:
- `GET /api/chapters/` endpoint (currently not exposed)
- `GET /api/subjects/` endpoint (currently not exposed)
- Both are simple `ReadOnlyModelViewSet` wrapping `Chapter` and `Subject` models

**Frontend:**

New route: `/teacher/questions/new`

## F. Legacy Analysis & Improvement Opportunities

### Teacher analytics (legacy had none)
- **Legacy did**: Teachers could see assignment submission status via Django admin — a list of `Submission` objects filtered by assignment. No aggregated stats (rates, avg scores, distributions). No teacher-facing UI.
- **What was limited**: Admin panel is not a teacher tool. No visual analytics at all.
- **How we improve**: Native teacher dashboard analytics — submission rates, avg scores, progress bars per assignment — built as first-class features, not admin hacks. Future: per-student breakdown, question-level mistake analysis from `SubjectRoomQuestionMistake`.

### Student proficiency display (legacy existed but was limited)
- **Legacy did**: `edge/models.py` had `StudentProficiency` (same concept). Legacy displayed a proficiency score per subject on a student profile page. Basic text display, no per-chapter breakdown, no history/trends.
- **What was limited**: Single subject-level score gives no actionable insight. Students couldn't tell *which chapter* they needed to focus on.
- **How we improve**: Per-chapter proficiency with visual progress bars, grouped by subject, showing attempt counts. Future: trend line (score over time), `LearningGap` integration (highlight chapters with `GapSeverity.SEVERE`).

### Question authoring (Sphinx legacy)
- **Legacy did**: `sphinx/` app — a Django-admin-like UI for teachers to create questions. Stored content in Cabinet (external filesystem). Had support for variable constraints (croupier-compatible), image upload, multi-subpart, MCQ options, and tagging.
- **What was good**: Teachers could author without admin access. Variable constraints enabled randomization.
- **What was limited**: Tightly coupled to Cabinet. No live LaTeX preview. Form-based, clunky.
- **How we improve**: React form with **live KaTeX preview** as the teacher types (render `question_text` in real-time). Content stored directly in DB (no Cabinet dependency). Phase 2: variable constraints, image upload.
