# Daily Plan — 2026-06-11

## A. Today's objective

**Promote and launch the new top initiative: [Language Access — i18n en/हिंदी](../initiatives/2026-language-access.md).**
Ship the first batch (LA-1..5): an i18n foundation with a one-tap language
switcher, a durable `preferred_language` on the user, the student core loop's
chrome in Hindi, AI-generated content (explanations + parent summaries) in the
reader's language, and a CI guard that keeps the two locales from drifting.

## B. Why this matters

ASA closed this morning and the board had **no active bet**. The en/hi toggle
is the **last open item on the ROADMAP**, and it has the same shape ASA just
spent three batches fixing: the backend has supported `language="hi"` on
`/ai/explanations/` and parent summaries since those features shipped —
prompted to answer in Devanagari — but **no UI can ask for it**. Meanwhile the
frontend has zero i18n infrastructure of any kind.

For a K-12 platform in India this is mission-core, not polish: most students
and parents are more comfortable in Hindi or a regional language. A parent who
can't read "Your child completed 4 of 6 assignments" in their language can't
engage; the legacy platform never even attempted this. The framework also has
to make language #3 a content task, not an engineering task (LA-9 proves that
later).

Why not the other seeds: `/ai/predictions/` surface is an explicitly deferred
product call (1 surface, not initiative-sized); Widget Studio is paused
pending product discovery an autonomous run can't supply; the AI-tutor branch
is a ~5,000-line rebase — the opposite of atomic. Mobile/PWA-offline remains
the next-strongest seed and stays in the backlog.

## D. Concrete implementation plan

### PR 1 — LA-1: i18n foundation, switcher, auth pilot (New)

- **New module `frontend_modern/src/shared/i18n/`:**
  - `locales/en.ts` and `locales/hi.ts` — flat `Record<string, string>`
    dictionaries (TS modules, not JSON, for typo-checking via a shared key
    union type). Start with only the keys the pilot + switcher need.
  - `I18nProvider.tsx` — React context holding `locale: 'en' | 'hi'` +
    `setLocale`. `en` is bundled eagerly; `hi` is loaded with a dynamic
    `import('./locales/hi')` so the entry chunk doesn't grow (Performance
    Budget guard at 160 kB — current entry 93 kB; **do not add i18next**,
    decision recorded in the initiative doc, principle 2).
  - `useT.ts` — `const t = useT(); t('login.title')`, with `{var}`
    interpolation (`t('greeting', {name})`), fallback to the `en` string when
    a `hi` key is missing, and a dev-only `console.warn` on missing keys.
  - On locale change: persist to `localStorage('os_lang')`, set
    `document.documentElement.lang`, and (for `hi`) ensure a
    Devanagari-capable font stack — append `"Noto Sans Devanagari"` to the
    Tailwind font-family for `[lang="hi"]` or via a CSS variable. **Verify
    Devanagari actually renders** in the browser, don't assume Inter covers it.
- **Switcher UI:** compact "EN | हिं" toggle in
  [Navbar.tsx](frontend_modern/src/features/layout/Navbar.tsx) (desktop) and
  the mobile account drawer — V2 tokens, `aria-pressed`/`aria-label`.
- **Pilot migration:** [LoginPage.tsx](frontend_modern/src/features/auth/LoginPage.tsx)
  + [AuthLayout.tsx](frontend_modern/src/features/auth/AuthLayout.tsx) strings
  move to `t()` keys with real Hindi values (use the initiative Glossary
  register; list new Hindi strings under a "translation review" heading in
  the PR body).
- **Wire provider** in `App.tsx` above the router.
- **Verify:** new `i18n.test.tsx` (interpolation, fallback + dev warn,
  persistence, `<html lang>` sync), extend `LoginPage.test.tsx` (renders in
  hi via provider wrapper, switcher toggles). `npm run lint && npx tsc
  --noEmit && npx vitest run`; check `npm run build` entry-chunk size guard.
- **Risk:** font rendering on Windows/Android (spot-check); keep the module
  tiny — no plural rules until something needs them.

## F. Legacy analysis & improvement opportunities

- **Legacy (Django 1.11) was English-only.** Server-rendered templates,
  hardcoded strings, no `USE_I18N` discipline, no user language preference —
  for a platform whose stated audience includes CBSE/State-Board schools
  where English is a second language. This initiative is pure "improve":
  there is nothing to port.
- **What legacy got right that we keep:** domain vocabulary. Indian
  classrooms genuinely say "assignment", "submit", "marks" in English —
  the Glossary transliterates these rather than forcing Sanskritized
  translations nobody uses. Hindi UI should read like a Hindi-speaking
  teacher talks, not like a government form.
- **Modern advantage:** because the SPA centralizes strings and the AI layer
  already parameterizes `language`, we get Hindi AI explanations — something
  legacy couldn't have done at any engineering cost. The same `language`
  plumbing later carries regional languages (LA-9) and localized emails (LA-7).
