## A. Today's objective

English-only teacher surfaces (LA-6e), closing LA-6 and LA-8.** After this batch
the entire teacher product — including the big `CreateQuestionPage`, the question

## B. Why this matters

LA-6a–d localized the dashboard, create-assignment, build-problem-set, and the
AI grading queue. But a Hindi-medium teacher still hits raw English the moment
they **author a question** (`CreateQuestionPage`, the single most-used authoring
screen, 1131 lines), **browse the question bank**, **record an open-response
rubric**, **preview/diff a problem set**, or **share a classroom join code**.
These are core daily actions — leaving them English-only means LA-6 is *almost*
done in a way the user actually feels. Closing the remainder is what lets us mark
the teacher surface truly localized.

LA-8 is the foundation half. It was planned first precisely because 6a–d's date
labels were supposed to consume it; instead 6a–d shipped with whatever ad-hoc
formatting they had, and several 6e surfaces (snapshot timestamps, version
history, due-date chips) render absolute dates that will read as half-English
("May 27 में"-style mismatch — the LA-3 ledger lesson) unless we add the helper
now. A single `Intl`-backed `formatDate`/`formatNumber` keyed to the active
locale solves it once for every surface — today's 6e cards, the 6a–d cards
(back-fill), and LA-9 later — instead of each screen inventing its own.

Why this batch and not a new initiative: Language Access is the top active bet
and these are its last *unblocked* increments. After today only **LA-9**
(third-language pilot) and **LA-10** (authored-content translation, blocked on
product design) remain — and the post-LA seed (Mobile shell / PWA-offline) is
already named.

## D. Concrete implementation plan

### PR 1 — LA-8: locale-aware date/number helper (Improve/hardening)

- **New file `frontend_modern/src/shared/i18n/format.ts`:**
  - `formatDate(value: string | Date, locale: 'en' | 'hi', opts?: Intl.DateTimeFormatOptions)`
    using `new Intl.DateTimeFormat(locale === 'hi' ? 'hi-IN' : 'en-IN', opts)`.
    Default medium style (`{ day: 'numeric', month: 'short', year: 'numeric' }`
    → "27 मई 2026" / "27 May 2026"); accept `opts` overrides. **Guard invalid
    dates** — `Number.isNaN(d.getTime())` → return the raw input string, never throw.
  - `formatNumber(value: number, locale)` via `Intl.NumberFormat`. **Keep Latin
    digits** (`'en-IN'`/`'hi-IN'` give Indian grouping but Latin numerals — what
    we want for K-12 counts). Add a code comment: *do not "fix" to Devanagari
    digits — product decision.*
  - `useFormat()` hook reading the active locale from i18n context, returning
    bound `formatDate`/`formatNumber` (mirrors `useT()`/`useI18n()`), so callers
    do `const { formatDate } = useFormat()`.
  - Export from `frontend_modern/src/shared/i18n/index.ts`.
- **Swap ad-hoc absolute dates to the helper:** grep
  `toLocaleDateString\|toISOString().split\|\.split('T')` under
  `frontend_modern/src/features/` and convert the **absolute** date displays on
  the student `AssignmentCard` due-date and the teacher `CreateAssignmentPage`
  due-date chip (the surfaces the prior plan named). **Leave relative dates
  alone** — date-fns `hi` (LA-3) already handles "3 दिन में".
- **Verify:** new `format.test.ts` — en vs hi medium date, an `opts` override,
  invalid-input passthrough, number grouping; one card test asserting the hi date
  string renders. `npm run lint && npx tsc --noEmit && npx vitest run`;
  `npm run build` — confirm `Intl` adds nothing to the entry chunk and no eager
  `date-fns/format` import leaks in (160 kB guard).
- **What could go wrong:** the only behavioral change is date *string format* —
  spot-check the English card reads visually equivalent before/after (use
  `'27 May 2026'` order, not `'May 27, 2026'`, to match Indian convention; if the
  prior English was `Month DD, YYYY` and you want zero visual churn in English,
  pass an `opts` that preserves it — document the choice).

## F. Legacy analysis & improvement opportunities

- **Legacy (Django 1.11) had no teacher i18n** and no `Intl` — server-rendered
  English templates, no language preference. Pure "improve"; nothing to port.
- **Vocabulary we keep:** Indian teachers say "question bank", "rubric",
  "version", "assignment" in English in the classroom — the Glossary
  transliterates (प्रश्न बैंक, रूब्रिक, संस्करण) rather than Sanskritizing, so the
  Hindi UI reads the way a Hindi-medium teacher actually speaks.
- **Modern advantage:** centralized strings + a native `Intl` layer mean every
  remaining surface localizes for the cost of key extraction, and the one
  `formatDate`/`formatNumber` helper carries forward to LA-9 and back into the
  LA-7 emails — capability that compounds instead of being re-solved per screen.
