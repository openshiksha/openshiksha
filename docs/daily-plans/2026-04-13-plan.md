class QuestionMistakeSerializer(serializers.ModelSerializer):
    question_text = serializers.SerializerMethodField()
    question_type = serializers.SerializerMethodField()
    question_id = serializers.IntegerField(source="question.id", read_only=True)

#### Step 2 — Backend: `QuestionMistakeViewSet`

```python
class QuestionMistakeViewSet(viewsets.ReadOnlyModelViewSet):
    """
    Read-only view of question-level mistake aggregates for a teacher's subject rooms.

    GET /api/question-mistakes/?subject_room=<id>
    Returns questions ordered by regression (hardest first).
    Only returns results for subject rooms where the requesting teacher is assigned.

    Permissions: teacher only.
    """

    serializer_class = QuestionMistakeSerializer
    permission_classes = [permissions.IsAuthenticated, IsTeacher]

    def get_queryset(self):
        qs = (
            SubjectRoomQuestionMistake.objects.filter(
                subject_room__teacher=self.request.user
            )
            .select_related(
                "question",
                "subject_room",
            )
            .prefetch_related("question__subparts")
            .order_by("-regression")
        )
        subject_room_id = self.request.query_params.get("subject_room")
        if subject_room_id:
            qs = qs.filter(subject_room_id=subject_room_id)
        return qs
```

Add import: `from openshiksha.apps.edge.models import SubjectRoomQuestionMistake` (alongside existing edge imports, or alongside model imports already in the file).

  question_type: string;

  updated_at: string;

const fetchQuestionMistakes = async (subjectRoomId: number): Promise<QuestionMistake[]> => {

#### Step 3 — Variable constraints panel per subpart

**Panel behavior:**
- Auto-detect `{{var}}` tokens in `question_text` using a regex: `/\{\{(\w+)\}\}/g`
- For each detected token, show a row with `name` (read-only, from token), `min`, `max`, `integer` toggle
- Warn if the `correct_answer` string contains a `{{var}}` token not in `variable_constraints`
- Show a live preview: sample values for student 1 and student 2 (call `substitute_variables_for_student` logic in the browser — pure JS, no API call needed)

**Implementation approach**: Extract detected variable names from `question_text`, auto-populate the constraint map with defaults (`min: 1, max: 10, integer: true`) when a new token appears. Let teachers edit min/max/integer inline.

```tsx
// Utility: extract variable tokens from text
const extractTokens = (text: string): string[] => {
  const re = /\{\{(\w+)\}\}/g;
  const names = new Set<string>();
  let match;
  while ((match = re.exec(text)) !== null) names.add(match[1]);
  return Array.from(names).sort();
};
```

#### Step 4 — Pass variable_constraints in submit payload

In the form submission handler, ensure each subpart object in the request body includes `variable_constraints`. Since the write serializer already accepts it, the only change needed is including it in the payload:

```typescript
const subparts = subpartStates.map((s) => ({
  index: ...,
  question_text: s.question_text,
  options: s.options,
  correct_answer: s.correct_answer,
  variable_constraints: Object.keys(s.variable_constraints).length > 0
    ? s.variable_constraints
    : null,
}));
```

Setting it to `null` when empty preserves the nullable field semantics from the model.

#### Step 5 — Add a live preview widget

Below the variable constraints table, show a small "Preview" box:

- Generate sample values for student IDs 1 and 2 (deterministic per `sha256(student_id:subpart_index:vars)`)
- Substitute tokens in `question_text` with sampled values
- Show "Student A sees: Solve 3x + 7 = 25" and "Student B sees: Solve 6x + 2 = 44"

This is pure browser-side computation (no API call). Port the `sample_variable_values` logic to TypeScript:

```typescript
// Minimal seeded RNG for preview (xorshift32)
const previewRng = (seed: number) => {
  let s = seed | 1;
  return () => {
    s ^= s << 13; s ^= s >> 17; s ^= s << 5;
    return (s >>> 0) / 4294967296;
  };
};

const sampleForPreview = (constraints: Record<string, {min:number;max:number;integer:boolean}>, studentNum: number) => {
  const values: Record<string, number> = {};
  // Simplified: use Math.random seeded via student-specific offset
  // (exact sha256 not needed for UI preview — determinism is a backend concern)
  const rng = previewRng(studentNum * 31337);
  for (const [name, spec] of Object.entries(constraints)) {
    const raw = rng() * (spec.max - spec.min) + spec.min;
    values[name] = spec.integer ? Math.round(raw) : parseFloat(raw.toFixed(2));
  }
  return values;
};
```

Note: The preview RNG doesn't need to match the backend exactly — it just needs to show teachers that different students get different values. The backend's SHA256-seeded RNG is authoritative at grading time.

- **Only for numeric/fill_blank**: MCQ options can technically contain `{{var}}` tokens (they're substituted by `substitute_variables_for_student`), but the authoring UI should only auto-show the variable panel for numeric/fill_blank to avoid overcomplicating the MCQ flow.
- **Round-trip**: After saving a variable question, loading it back in the edit view should pre-populate the constraint table. The read serializer (`QuestionSubpartSerializer`) includes `variable_constraints` in fields. Check that the question-edit flow reads it back.

## F. Legacy Analysis & Improvement Opportunities

### Teacher Analytics (Priority 1)

**Legacy**: No per-question difficulty analytics existed for teachers. The closest was the overall assignment score and the number of times a problem set was used. Teachers had no visibility into which specific questions students failed at most.

**Modern improvement**: `SubjectRoomQuestionMistake.regression` is the cumulative marks lost per question per subject room. This is a more meaningful signal than "question was answered wrong N times" — it weights by how much the question is worth. The "Hardest Questions" panel surfaces this directly. Future improvement: add a `mistake_rate` (regression / total_possible_marks) field to normalize across different assignment sizes.

### Learning Path (Priority 2)

**Legacy**: No learning path existed. Students received assignments manually chosen by teachers. There was no adaptive sequencing or spaced repetition.

**Modern improvement**: The AI engine builds LearningPath + LearningPathStep records from StudentMastery gaps, using KnowledgeNode dependencies for ordering. The SM-2 spaced repetition scheduler marks steps for review when they decay. Surfacing this to students closes the loop: the backend knows what they should study; now students can see it. Future improvement: make steps clickable (link to a relevant assignment or problem set for that chapter).

### Variable Constraints Authoring (Priority 3)

**Legacy**: Variable definitions were stored in Cabinet (external HTTP service) and had no authoring UI — teachers edited Cabinet JSON directly via the legacy CMS. The Sphinx authoring tool showed a static form with no variable preview.

**Modern improvement**: Variables are stored in `QuestionSubpart.variable_constraints` (JSONField, in-DB). The authoring UI can auto-detect tokens from the question text, provide a type-safe form for setting ranges, and show a live preview with different student values. This reduces teacher authoring errors (mismatched token names, invalid ranges) before questions reach students.
