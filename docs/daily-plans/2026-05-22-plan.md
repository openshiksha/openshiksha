## B. Why This Matters

- **Activity Streaks (P1)**: The SRS drill mode means students can practice independently. Streaks are the retention mechanic that makes them come back daily. Duolingo's core retention loop is built on this single mechanic — streaks create a loss-aversion signal ("I don't want to break my streak") that drives daily use far more reliably than any content quality improvement alone. The infrastructure is nearly ready: `signals.py` is registered, `Submission.submitted_at` is indexed, `apps.py` imports signals. Adding `StudentStreak` is the missing model.

- **Question Content Search (P2)**: The teacher question bank page (`QuestionBankPage.tsx`) is live but search only covers chapter/subject names. Teachers can't find questions by content — a search for "quadratic" or "photosynthesis" returns nothing unless a chapter is literally named that. This is a one-line config change that makes the question bank dramatically more useful as it grows.

- **Remedial Assignment Auto-Creation (P3)**: The grading pipeline (`grade_submission` Celery task) already calculates per-student scores. When a student scores < 30%, nothing happens. The legacy grader auto-created remedial assignments for failing students — this is one of the few legacy features that directly improved learning outcomes. Without it, struggling students simply get a bad score and nothing changes. With it, the platform automatically creates targeted practice for exactly the questions they got wrong. This closes the formative-assessment loop.

#### Step 1 — Backend: `StudentStreak` model

**File**: `backend/openshiksha/apps/core/models.py` (append after `Submission`)

```python
class StudentStreak(models.Model):
    """
    Daily activity streak for a student.

    Incremented by a post_save signal on Submission when submitted_at is set.
    One row per student — updated in-place. Append-only StreakEvent log can
    be added later if streak history becomes a product requirement.
    """

    student = models.OneToOneField(
        "User",
        on_delete=models.CASCADE,
        related_name="streak",
        limit_choices_to={"role__in": ["student", "open_student"]},
    )
    current_streak = models.PositiveIntegerField(default=0)
    longest_streak = models.PositiveIntegerField(default=0)
    last_activity_date = models.DateField(null=True, blank=True)
    updated_at = models.DateTimeField(auto_now=True)

    class Meta:
        db_table = "student_streaks"

    def __str__(self):
        return f"Streak({self.student_id}): {self.current_streak}d"

    def record_activity(self, activity_date):
        """
        Record activity for a given date and update streak counters.

        Rules:
        - Same day as last_activity_date → no-op (already counted)
        - Next consecutive day → current_streak += 1
        - Gap of 1+ days → current_streak resets to 1
        """
        from datetime import timedelta

        if self.last_activity_date is None:
            self.current_streak = 1
        elif activity_date == self.last_activity_date:
            return
        elif activity_date == self.last_activity_date + timedelta(days=1):
            self.current_streak += 1
        else:
            self.current_streak = 1

        self.last_activity_date = activity_date
        if self.current_streak > self.longest_streak:
            self.longest_streak = self.current_streak
        self.save(update_fields=["current_streak", "longest_streak", "last_activity_date", "updated_at"])
```

Design rationale:
- OneToOneField keeps it O(1) to look up streak for any student — no aggregation query.
- `record_activity()` is a method on the model (not in the signal or view) so it can be tested in isolation and reused by other activity sources (e.g., SRS drill sessions in Phase 2).
- `update_fields` avoids a full row write — safe under concurrent access because the signal guard ensures only one `submitted_at` update per submission.

**File**: `backend/openshiksha/apps/core/signals.py`

Add a second receiver after the existing grading signal:

```python
@receiver(post_save, sender="core.Submission")
def update_student_streak(sender, instance, update_fields, **kwargs):
    """
    When a student submits (submitted_at set), record activity on their streak.
    Only fires on explicit submitted_at update (mirrors grading signal guard).
    """
    if not instance.submitted_at:
        return
    if update_fields is not None and "submitted_at" not in update_fields:
        return

    from openshiksha.apps.core.models import StudentStreak

    streak, _ = StudentStreak.objects.get_or_create(student_id=instance.student_id)
    streak.record_activity(instance.submitted_at.date())
```

Note: The existing `trigger_grading_on_submit` signal already has the guard logic. This new signal mirrors the same guard so both fire on exactly the same condition — `submitted_at` being explicitly saved.

The `apps.py` `ready()` already imports `signals.py`, so no `apps.py` change needed.

#### What Could Go Wrong

- **Signal guard parity**: The new streak signal must mirror the grading signal's `update_fields` guard exactly. If the guard is wrong, the streak might fire on every Submission update (including autosave calls). Test by saving a Submission without `update_fields` and confirming no streak is created.
- **Timezone confusion**: `instance.submitted_at.date()` gives UTC date. A student submitting at 11 PM IST gets credit for yesterday (UTC). Acceptable for Phase 1. Phase 2: use `django.utils.timezone.localdate()` with the school's configured timezone.
- **`get_or_create` race**: Unlikely — `unique_together [assignment, student]` on Submission prevents two simultaneous submits for the same student-assignment pair. If it becomes an issue, wrap signal in `select_for_update`.

#### Step 2 — Backend: Remedial creation helper

**File**: `backend/openshiksha/apps/core/tasks.py`

Add helper function (not a Celery task itself — called by `grade_submission`):

```python
def _create_remedial_assignment(submission_id):
    """
    Creates a remedial ProblemSet + Assignment for a student who scored < REMEDIAL_THRESHOLD.

    Targets only the specific questions the student answered incorrectly.
    Idempotent: if a remedial already exists for this submission's assignment + student, skips.
    """
    from openshiksha.apps.core.models import (
        Assignment, ProblemSet, Submission, Tick
    )

    REMEDIAL_THRESHOLD = 0.30

    submission = Submission.objects.select_related(
        "assignment__problem_set__subject_room", "student"
    ).get(pk=submission_id)

    if submission.score is None or submission.score >= REMEDIAL_THRESHOLD:
        return  # no remedial needed

    # Idempotency check
    if Assignment.objects.filter(
        problem_set__is_remedial=True,
        problem_set__source_assignment=submission.assignment,
        subject_room=submission.assignment.subject_room,
    ).filter(submissions__student=submission.student).exists():
        return

    # Find which questions the student got wrong
    wrong_question_ids = list(
        Tick.objects.filter(
            submission=submission,
            is_correct=False,
        )
        .values_list("subpart__question_id", flat=True)
        .distinct()
    )

    if not wrong_question_ids:
        return  # all ticks correct — shouldn't happen if score < 30% but be safe

    orig = submission.assignment
    remedial_ps = ProblemSet.objects.create(
        title=f"Remedial: {orig.problem_set.title}",
        subject_room=orig.subject_room,
        is_remedial=True,
        source_assignment=orig,
        created_by=orig.created_by,
    )
    remedial_ps.questions.set(wrong_question_ids)

    from datetime import timedelta
    from django.utils import timezone

    due = timezone.now() + timedelta(days=3)
    Assignment.objects.create(
        problem_set=remedial_ps,
        subject_room=orig.subject_room,
        due_date=due,
        created_by=orig.created_by,
    )

    logger.info(
        f"Created remedial assignment for student {submission.student_id} "
        f"(submission {submission_id}, {len(wrong_question_ids)} wrong questions)"
    )
```

#### What Could Go Wrong

- **`Tick` records not yet created when helper runs**: `grade_submission` creates Tick records, then saves the score. If the helper runs before Tick records are committed (e.g., in a transaction that hasn't flushed), `wrong_question_ids` will be empty. Fix: call `_create_remedial_assignment` only after `submission.save()` and outside any open transaction. If using `ATOMIC_REQUESTS=True`, the save commits before the function returns.
- **Remedial for student who is not in the SubjectRoom anymore**: Possible if a student was removed from a classroom mid-year. The `Assignment.subject_room` FK is still valid (the original assignment exists), so the remedial assignment is created but won't be visible to the student if they've left the room. Acceptable edge case for Phase 1.
- **ProblemSet.questions fan-out**: If a student got 0 questions right on a 20-question assignment, the remedial has 20 questions — same as the original. Consider capping at 10 questions for remedials. For Phase 1, no cap; keep it simple.
- **Due date 3 days out is arbitrary**: Use the original assignment's remaining due window if it's > 3 days, else 3 days. Phase 1: fixed 3 days.

## F. Legacy Analysis & Improvement Opportunities

### Activity Streaks (Priority 1)

**Legacy**: No gamification existed. The platform was entirely task-driven — teachers assigned, students submitted. No engagement mechanic rewarded daily use. Students had no reason to open the app unless they had a due assignment.

**Modern improvement**: Streaks shift the platform from "homework submission tool" to "daily learning habit." Phase 1 (today) is minimal: current streak + best streak + fire emoji badge. The infrastructure is designed for extension:
- Phase 2: Streak freeze (one grace day) — prevents streak anxiety from becoming a dropout signal
- Phase 3: Streak milestones (7-day badge, 30-day badge, classroom leaderboard) — social proof and identity ("I'm a daily learner")
- Phase 4: Connect to SRS drill sessions (a drill session also counts as activity) — makes streaks achievable even when no assignment is due

### Question Content Search (Priority 2)

**Legacy**: Cabinet stored all questions; teachers browsed by chapter/subject. No free-text search existed. Finding "the question about photosynthesis" required knowing it was Chapter 3, Std 9 Biology.

**Modern improvement**: As the question bank grows (from seed data → teacher-authored → imported legacy questions), search becomes the primary navigation mechanism. Subpart text search is the minimum viable version. Future: tag-based filtering UI, difficulty facets, "similar questions" AI endpoint.

### Remedial Assignments (Priority 3)

**Legacy**: `grader/` auto-created remedial assignments using `GenericFK` — the remedial could target a `SubjectRoom` (class-wide remedial) or a single `User` (student-specific). Modern system uses FK directly (no GenericFK), which is cleaner. Legacy remedial created a copy of the _full_ problem set; modern version will only include the wrong questions — a significant improvement that reduces student workload and focuses practice on actual gaps.

Legacy threshold was 30% (hardcoded in `grader/`). Modern version keeps the same threshold but makes it a named constant (`REMEDIAL_THRESHOLD = 0.30`) so it can be configured per-school in Phase 2.
