## B. Why this matters

The new initiative — [Interactive Widgets
Framework](../initiatives/interactive-widgets-framework.md) — was promoted
to **#1 active** on 2026-06-04 because:

1. The V2 design system is essentially closed (see
   [`STATUS.md`](../initiatives/STATUS.md)).
2. M7-11 shipped the sandbox host as a generic primitive *precisely* so this
   initiative can harden it into a reusable runtime instead of throwing it
   away.
3. The legacy platform marketed "interactive widgets" but delivered exactly
   one (jQuery + raw HTML). A real framework is the unlock for net-new
   educational content at scale — and the strongest possible signal to
   newcomers that this is a project they can build *real* things in.

IW-1 is intentionally *plumbing-only*: the framework's first day should be
about shipping the contract (types, host, runtime) and proving the loop with
the smallest possible reference, **not** writing rich widgets yet. Rich
widgets land in IW-2 + IW-4 + IW-6 on a foundation that already works.

## C. Today's batch — 3 shippable PRs

Ordered **lowest-risk-first**. Items 1 + 2 are independent (different file
groups) and can ship in either order. Item 3 depends on item 2.

### PR 1 — `IW-1a` Protocol types
- **Files (new):**
  `frontend_modern/src/widgets/_sdk/protocol.ts`
- **What:** Define the typed `postMessage` union used by host ↔ runtime:
  `HostMessage = InitMessage` and `WidgetMessage = ReadyMessage |
  ResizeMessage | ValueMessage | ErrorMessage`. Include narrow type guards
  (`isReadyMessage(msg)` etc.) and a single `WIDGET_PROTOCOL_VERSION` const.
- **Why first:** Pure types; zero runtime impact; lands the contract IW-1b
  and IW-1c need. Reviewable on its own.
- **DoD:** `npm run type-check`, `npm run lint` green. No new tests required;
  the consumers in IW-1b/c will exercise it.

### PR 2 — `IW-1b` Host module
- **Files:**
  - **New** `frontend_modern/src/widgets/_sdk/host.ts` — exports
    `buildHostSrcDoc({ kind, config, variables, imageBase })` and a
    `createHostBridge(iframe, handlers)` that wires `event.source`-guarded
    listeners for the typed messages from PR 1.
  - **Modified** `frontend_modern/src/shared/ui/InteractiveWidget.tsx` —
    delegate srcdoc construction + message handling to `_sdk/host.ts`. **The
    public `InteractiveWidgetProps` shape (`html`, `fallbackText`,
    `minHeight`, `className`) stays unchanged so the existing thermo
    rendering path is byte-for-byte equivalent.**
  - **New** `frontend_modern/src/widgets/_sdk/host.test.ts` — vitest
    coverage for: srcdoc contains `sandbox="allow-scripts"` *without*
    `allow-same-origin`, never includes `dangerouslySetInnerHTML`-style
    flow, and `createHostBridge` ignores messages whose `event.source` isn't
    the bound iframe.
- **DoD:** Type-check / lint / vitest / build green. The existing thermo
  question (`44/22`) renders unchanged when manually verified at `/student/
  browse/practice/<chapter>` against the demo data. Sandbox attrs **never
  include `allow-same-origin`** — assert in the test.

### PR 3 — `IW-1c` Runtime + hello-widget + showcase

- **Files:**

## D. Concrete implementation plan

**Shared rules for every item:**

- **Compose, don't refactor.** The M7-11 host already enforces the security
  model (sandbox without `allow-same-origin`; source-guarded messages;
  srcdoc not innerHTML). PRs 1 + 2 + 3 *factor* that logic into the SDK
  shape; they don't change it. If a refactor temptation grows mid-PR, split
  it into a follow-up rather than ballooning the increment.
- **Backwards-compatible host props.** `InteractiveWidgetProps` stays
  `{ html, fallbackText, minHeight, className }` for IW-1. The new
  registry-driven `{ kind, config, variables, imageBase }` *path* is added
  alongside via a new prop shape only after IW-2 ships the `defineWidget`
  API — that swap is its own PR.
- **No backend changes.** IW-1 is frontend-only. The data-model migration
  (`widget_kind` + `widget_config` on `QuestionSubpart`) is IW-3.
- **V2 tokens inside the sandbox.** PR 3's runtime CSS must use the brand
  palette (`#FF6F00` anchor) and Fraunces+Inter. Inline `<style>` is fine
  for now (the runtime is built into the srcdoc); a shared
  `widget-runtime.css` is an IW-1 follow-up if convenient.
- **Tests.** Vitest for the host module (PR 2) + the protocol guards
  (PR 1, optional). Playwright is not needed for IW-1; M6-03 visual
  baselines will catch any host-shell regressions once seeded (#207).
