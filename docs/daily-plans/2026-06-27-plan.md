# OpenShiksha — Daily Plan, 2026-06-27

## A. Today's objective

Advance the top active initiative — **Production Observability & Operational
Readiness** — into **Batch 2: Metrics & dashboards**. Batch 1 (OBS-1..5) made a
prod incident *seeable* (readiness drain, Sentry, request correlation,
build-info, frontend crash reporting). Batch 2 makes prod *measurable*: a gated
Prometheus `/metrics` endpoint exposing runtime, business, async-task, and HTTP
signals, plus a starter Grafana dashboard + scrape runbook — all **additive and
env-gated** so dev/CI behaviour is byte-for-byte unchanged.

## B. Why this matters

Sentry tells us *that* something threw; metrics tell us *how the system is
trending* — grade-queue depth climbing, request latency creeping, Celery
failures spiking — **before** they become an incident. OpenShiksha is live in
prod (DO droplet, k3s) with **zero** time-series telemetry: `prometheus` appears
nowhere in `backend/requirements.txt`, there is no `/metrics` endpoint, and no
dashboard. This batch closes that gap with small, low-risk, independently
shippable PRs squarely in the plan/execute lane, and it unblocks Batch 4
(alerting needs a metric to alert on). Initiative doc:
[`docs/initiatives/2026-production-observability.md`](../initiatives/2026-production-observability.md).

## D. Concrete implementation plan

### MET-1 — `prometheus-client` dep + gated `/metrics` endpoint _(New)_ — **foundation**
- **Dep:** add `prometheus-client==0.21.*` (pin a current 0.21.x) to
  [backend/requirements.txt](../../backend/requirements.txt). **Choose
  `prometheus-client`, NOT `django-prometheus`** — `django-prometheus`
  auto-patches middleware/DB/cache and is always-on, which violates the
  "additive & env-gated, no always-on heavy agent" operability bar.
  `prometheus-client` is a thin exposition lib we mount and gate ourselves.
- **Endpoint:** add a top-level `metrics(request)` view (sibling to `readyz` —
  put the implementation in a new `backend/openshiksha/apps/core/metrics.py` and
  mount it from [urls.py](../../backend/openshiksha/urls.py) as
  `path("metrics/", metrics_view, name="metrics")`, mirroring how `readyz` is
  imported there). Behaviour:
  - When `settings.METRICS_ENABLED` is **falsy** → return `HttpResponse(status=404)`
    (endpoint is invisible — byte-for-byte today's behaviour).
  - When enabled **and** `METRICS_TOKEN` is set → require
    `Authorization: Bearer <token>`; mismatch/absent → `403`.
  - When enabled (token ok / no token configured) → return
    `prometheus_client.generate_latest()` with content-type
    `CONTENT_TYPE_LATEST`, status 200.
  - `@csrf_exempt`, auth-free at the DRF layer (it does its own token check),
    DB-free in MET-1 itself.
- **Settings:** read `METRICS_ENABLED` (default `False`) and `METRICS_TOKEN`
  (default `""`) in [settings/base.py](../../backend/openshiksha/settings/base.py)
  from env via the existing env-reading pattern. Default OFF everywhere; the prod
  overlay/secret turns it on in-cluster only.
- **Process-model note (verified):** prod runs a **single daphne ASGI process**
  (`CMD ["daphne", ...]` in [backend/Dockerfile.prod](../../backend/Dockerfile.prod)),
  so the default in-process registry is correct — **no `PROMETHEUS_MULTIPROC_DIR`
  needed.** Add a one-line comment in `metrics.py` recording this assumption so a
  future move to multi-worker gunicorn flags the multiprocess requirement.
- **Exposure note (verified):** the ingress
  ([k8s/base/ingress.yaml](../../k8s/base/ingress.yaml)) only routes `/api`,
  `/django-admin`, `/static` to the backend and `/` to the frontend — so
  `/metrics` is **not publicly routable**; it is reachable only in-cluster via the
  `backend:8000` Service. The token gate is defense-in-depth. (Document in MET-5;
  do **not** add an ingress path for `/metrics`.)
- **Verify (`pytest`):** disabled (default) → `/metrics` returns **404**; enabled
  + no token → 200 `text/plain; version=0.0.4` containing `# HELP`/`# TYPE`;
  enabled + token set, wrong/absent bearer → 403, correct bearer → 200. Assert the
  default-OFF no-op path explicitly (the operability bar's gated-off test).
- **What could go wrong:** don't import `prometheus_client` at settings-module
  import time in a way that breaks when the dep is briefly absent — import inside
  the view / metrics module. Keep the disabled path a literal 404 (no registry
  touch) so it's truly zero-cost.

### MET-2 — Business & queue-depth gauges (on-scrape collector) _(New)_
- **Collector:** in `apps/core/metrics.py` add a `class BusinessMetricsCollector`
  implementing `collect()` (the `prometheus_client` custom-collector protocol)
  that runs **read-only** ORM counts at scrape time and yields `GaugeMetricFamily`
  values. Register it on the default registry **only when `METRICS_ENABLED`** (so
  no DB work happens on scrape when the feature is off — and it's off by default).
  Gauges (names `openshiksha_*`):
  - `openshiksha_assignments_active_total` — assignments past `assigned`/before
    `due` (reuse the same active-window logic the dashboards/`AssignmentViewSet`
    use; grep `due` / `assigned` on the `Assignment` model so the metric matches
    the product definition).
  - `openshiksha_submissions_pending_grading_total` — the **grade-queue depth**
    (submissions submitted but not yet graded; reuse the ungraded predicate the
    grading pipeline reads).
  - `openshiksha_users_total{role=...}` — counts grouped by the role field.
  - `openshiksha_classrooms_total`, `openshiksha_subjectrooms_total`.
- **Why on-scrape (not event counters):** gauges computed lazily on each scrape
  are stateless, need no cross-process aggregation, and can't drift — the right
  pattern for "current size of X" business signals. Keep each query a single
  indexed `COUNT` (no N+1); cap to a handful so a scrape stays cheap.
- **Legacy reference:** none — greenfield telemetry.
- **Verify (`pytest`):** with `METRICS_ENABLED=True`, seed a couple of
  assignments/submissions/users via factories, scrape `/metrics`, assert the
  `openshiksha_assignments_active_total` / `_submissions_pending_grading_total`
  families appear with the expected values; assert the collector is **not**
  registered (no `openshiksha_*` lines, no DB hit) when disabled.
- **What could go wrong:** an expensive count on a large table on every scrape —
  keep them single COUNTs on indexed columns; don't join. Don't register the
  collector twice (guard against duplicate registration on module re-import in
  tests — register in the same gated path as MET-1, or use a module-level
  idempotent guard).

### MET-3 — Async-task health gauges from `TaskResult` (on-scrape) _(New)_
- **Why from the DB, not in-worker:** Celery runs as a **separate worker
  process** ([k8s/base/celery.yaml](../../k8s/base/celery.yaml)); in-worker
  `Counter`/`Histogram` objects live in that process and can't be scraped from the
  daphne web process without a pushgateway or a second exporter (out of scope —
  see the initiative's "no always-on heavy agent" bar). Instead derive task health
  on-scrape from the **already-installed** `django_celery_results` `TaskResult`
  table (`django-celery-results==2.6.0` in requirements; confirm
  `CELERY_RESULT_BACKEND`/`django-db` is the active backend before relying on it —
  if results aren't persisted, ship MET-3 as a documented no-op gauge set rather
  than a wrong number).
- **Collector:** extend the MET-2 collector (or a sibling `TaskMetricsCollector`)
  with gauges over a recent window (e.g. last 24h, windowed by `date_done`):
  - `openshiksha_celery_tasks_total{status=...}` — counts by `TaskResult.status`
    (SUCCESS/FAILURE/STARTED/RETRY/PENDING) in the window.
  - `openshiksha_celery_oldest_pending_seconds` — age of the oldest non-terminal
    task (or `0` when none) — the async analogue of grade-queue staleness.
- **Verify (`pytest`):** insert synthetic `TaskResult` rows (SUCCESS + FAILURE),
  scrape, assert the `{status="failure"}` gauge reflects the seeded count; assert
  the family is absent when `METRICS_ENABLED` is off. Use the ORM to create rows;
  no real Celery run in tests.
- **What could go wrong:** if `django_celery_results` isn't the configured result
  backend in prod, the table is empty and the gauge silently reads 0 — guard by
  checking the backend setting and documenting the dependency in MET-5. Window the
  query (`date_done >= now-24h`) so the table scan stays bounded.

### MET-4 — HTTP request metrics middleware (gated) _(New)_
- **Middleware:** add `MetricsMiddleware` to
  [apps/core/middleware.py](../../backend/openshiksha/apps/core/middleware.py)
  (next to `RequestIDMiddleware`). It records, **only when `METRICS_ENABLED`**:
  - `openshiksha_http_requests_total{method,status_class}` (Counter) and
  - `openshiksha_http_request_duration_seconds` (Histogram, sensible buckets),
    measured around `get_response`. Label by `method` and `status_class`
    (`2xx/3xx/4xx/5xx`) — **not** raw path (avoid unbounded cardinality); use the
    resolved route `name`/view if cheap, else status-class only.
  - When disabled, `__call__` is a pure pass-through (no metric objects touched,
    no measurable overhead). Place it in `MIDDLEWARE` **after** `RequestIDMiddleware`
    so request-id context is already set.
- **Verify (`pytest`):** with metrics enabled, hit any view through the test
  client, scrape `/metrics`, assert `openshiksha_http_requests_total` increased
  and a duration sample was observed; with metrics disabled, assert the middleware
  adds **no** `openshiksha_http_*` families (gated-off path).
- **What could go wrong:** path-label cardinality explosion (per-id URLs) — label
  on method/status-class (+ optional route name), never raw path. Counter/Histogram
  must be module-level singletons (define once at import; don't recreate per
  request) to avoid `Duplicated timeseries` registry errors.

## F. Legacy analysis & improvement opportunities

Observability/metrics is **greenfield** — the Django 1.11 monolith (now under
`legacy/`) had no Prometheus exposition, no business gauges, and no async-task
health surface; failures were diagnosed by SSH + `grep`. There is nothing to
port. The improvement over both legacy *and* today's modern stack is a
**measurable** system: trend lines on the signals that actually predict an
OpenShiksha incident (grade-queue depth, Celery failure rate, request latency),
computed cheaply on-scrape and gated off by default.
