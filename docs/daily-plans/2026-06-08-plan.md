# OpenShiksha Daily Plan — 2026-06-08

## A. Today's objective

Promote and ship **Authoring Integrity & Versioning — Phase 1** (per-assignment
content snapshots): freeze what each assignment contains at assign time, grade
and serve from that frozen copy, and signal edit-safety in the teacher UI. The
most important outcome: **editing a problem set or question can never silently
re-grade or re-write work that is already assigned** — proven by a golden
regression test — which also **unblocks TW-2 (editable preview)**, the only
remaining increment of the (paused) top initiative, Teacher Workspace.

## B. Why this matters

The board is otherwise clear: Performance Budget, V2 design, Cabinet Data
Fidelity, Interactive Widgets are Done/Paused, and **Teacher Workspace shipped
all its unblocked increments on 2026-06-07** (TW-1, TW-3a/b, TW-4, TW-5, TW-6,
TW-7 across [#250](https://github.com/openshiksha/openshiksha/pull/250),
[#261](https://github.com/openshiksha/openshiksha/pull/261)–[#266](https://github.com/openshiksha/openshiksha/pull/266)).
Its **last open increment, TW-2 (editable preview), is hard-blocked** on
Authoring Integrity Phase 1. So the single highest-leverage move now is to
**unblock it by building the dependency** — and it stands on its own merit: it
removes a verified silent-data-corruption bug.

**The bug, concretely** (confirmed in code today):
- `grade_submission` reads the **live** set
  ([tasks.py:52](../../backend/openshiksha/apps/core/tasks.py)) and the **live**
  `QuestionSubpart.correct_answer` ([tasks.py:84](../../backend/openshiksha/apps/core/tasks.py)).
- `Assignment.problem_set` is a live FK; `ProblemSet.questions` is a mutable M2M
  ([models.py:686](../../backend/openshiksha/apps/core/models.py),
  [models.py:600](../../backend/openshiksha/apps/core/models.py)).
- So editing a question's text/answer, or adding/removing a question, **changes
  past assignments retroactively** — a student who was correct can become wrong
  on re-grade, and shared (`school=null`) content edits blast across every school.

There is no snapshot, version, or lock anywhere in the chain. Phase 1 (Approach A
in the initiative doc — copy-on-assign snapshot) is the cheapest fix that fully
removes the bug and is a strict subset of the eventual versioning model (AIV-7),
so it is not throwaway.

Initiative doc: [`docs/initiatives/authoring-integrity-versioning.md`](../initiatives/authoring-integrity-versioning.md).

## C. Today's batch — 5 shippable PRs (lowest-risk-first)

1. **AIV-1 — Assignment content snapshot model + capture + backfill** — *New.*
   Backend foundation. `assigned_content` JSONField on `Assignment` (+ migration
   that backfills every existing assignment from its live set), captured at
   assign time in both creation paths. **No reader changes yet → zero behaviour
   change → safest first.** *(foundation; everything else depends on it)*
2. **AIV-2a — Grade from the snapshot** — *Improve.* `grade_submission` sources
   subpart `correct_answer`/`subpart_type`/`variable_constraints` from the
   assignment snapshot instead of the live set. Ships the **golden regression
   test**. **Depends on AIV-1.**
3. **AIV-2b — Serve the snapshot to the student** — *Improve.* The student
   assignment-detail serializer renders questions/options/widget config from the
   snapshot so a student always sees exactly what was assigned. **Depends on
   AIV-1; independent of AIV-2a.**
4. **AIV-3a — Edit-safety read flags on serializers** — *New.* Read-only
   `assigned_count` + `has_graded_submissions` on the problem-set / question
   serializers (drives UX, not safety — integrity is already guaranteed by
   AIV-1/2). **Independent backend; depends only on AIV-1 conceptually, buildable
   in parallel.**
5. **AIV-3b — Edit-safety notice in the teacher UI** — *Improve.* When editing a
   set/question that's already assigned, show a non-blocking notice ("used in N
   assignments; edits apply to future assignments; existing ones keep what
   students were given"). **Depends on AIV-3a.**

> **Build order:** **AIV-1 first** (foundation, no behaviour change). Then
> **AIV-2a ∥ AIV-2b ∥ AIV-3a** (all depend only on AIV-1, independent of each
> other). Then **AIV-3b** (needs AIV-3a's flags). Ordered lowest-risk-first:
> additive model+backfill → reader swaps guarded by a golden test → pure-additive
> serializer fields → frontend notice. This **closes Phase 1 (AIV-1..3)** and
> reaches the initiative's Phase-1 DoD.

## D. Concrete implementation plan

### AIV-1 — Snapshot model + capture + backfill  *(foundation, no behaviour change)*
- **Files:** `backend/openshiksha/apps/core/models.py` (`Assignment`, ~L686),
  a new migration in `backend/openshiksha/apps/core/migrations/`, a small
  helper module e.g. `backend/openshiksha/apps/core/snapshots.py` (new), and the
  two assignment-creation paths:
  `backend/openshiksha/apps/api/views/core.py:687` (`AssignmentViewSet.perform_create`)
  and `_create_remedial_assignment` ([tasks.py:457](../../backend/openshiksha/apps/core/tasks.py)).
  Tests under `backend/openshiksha/apps/api/tests/` (or `apps/core/tests/`).
- **Model:** add `assigned_content = models.JSONField(null=True, blank=True,
  help_text="Frozen copy of the problem set's questions at assign time. Source
  of truth for grading and rendering this assignment.")`. **Purely additive.**
- **Snapshot shape** — `build_assignment_snapshot(problem_set) -> dict`: ordered
  list of questions, each with its subparts capturing **everything the renderer
  + grader need**: `subpart_id` (keep stable — croupier seeds on
  `(student_id, subpart_id)`), `question_text`, `options`, `correct_answer`,
  `subpart_type`, `variable_constraints`, `widget_kind`, `widget_config`, and
  `image_url`/`solution_text`/`hint_text`. Include a `schema_version: 1` and a
  `captured_at`. Verify exact field names against `QuestionSubpart` before
  writing — do not guess.
- **Capture:** call the helper at assign time in **both** paths (regular
  `perform_create` and the remedial auto-creation) and store on the new field.
- **Migration:** data migration backfills every existing `Assignment` from its
  current live set (best-available truth), logging count as "backfilled". Keep it
  idempotent (skip rows that already have content).
- **Legacy reference:** none — legacy had no snapshot/versioning at all.
- **Verify:** pytest — creating an assignment populates `assigned_content`;
  editing the live set/subpart afterward leaves `assigned_content`
  **byte-identical**; remedial creation snapshots too; backfill populates a
  pre-existing assignment; `makemigrations --check` clean.
- **What could go wrong:** snapshot drifts from `QuestionSubpart` field names —
  mitigate by reading the model first and round-tripping a real seeded question.
  JSON must be deterministic (stable key order) so the byte-identical test holds.

### AIV-2a — Grade from the snapshot  *(depends on AIV-1; ships the golden test)*
- **Files:** [tasks.py:20-89](../../backend/openshiksha/apps/core/tasks.py)
  (`grade_submission`), tests.
- **Change:** instead of `problem_set.questions.values_list(...)` +
  `subpart.correct_answer`, read the question/subpart list and each subpart's
  `correct_answer`/`subpart_type`/`variable_constraints` from
  `submission.assignment.assigned_content`. Fall back to the live set only if
  `assigned_content` is null (defensive; backfill should make this unreachable).
  **One grader, one code path** (principle #5) — only the *source* of content
  changes, not the grading math.
- **Verify (the DoD test):** assign a set → student submits → **edit the live
  set's `correct_answer`** → re-grade ⇒ score **unchanged** (graded against the
  snapshot). The *same* edit on a **new** assignment grades against the new
  answer. Also: variable-substitution/croupier path stays deterministic because
  subpart ids are preserved in the snapshot.
- **What could go wrong:** numeric questions with `variable_constraints` evaluate
  per-student — ensure the snapshot carries the constraints so re-grade matches
  the original randomization seed.

### AIV-2b — Serve the snapshot to the student  *(depends on AIV-1; ∥ AIV-2a)*
- **Files:** the student assignment-detail serializer
  (`AssignmentDetailSerializer` / `ProblemSetStudentDetailSerializer` path in
  `backend/openshiksha/apps/api/serializers/core.py`), tests. Confirm the exact
  serializer the student app hits before editing.
- **Change:** render the question list, text, options, and `widget_kind`/
  `widget_config` from `assigned_content` so the student sees exactly what was
  assigned, even after the live set drifts. Keep the response shape identical
  (frontend unchanged) — only the data source moves.
- **Verify:** pytest — student GET of an assignment returns the snapshot's
  questions; after editing the live set, the student response is unchanged;
  widget config round-trips.
- **What could go wrong:** response-shape regressions — assert the serialized
  payload against the pre-change shape with a fixture; snapshot must include
  widget fields or widgets break for the student.

### AIV-3a — Edit-safety read flags  *(additive serializer fields; ∥)*
- **Files:** problem-set + question serializers in
  `backend/openshiksha/apps/api/serializers/core.py`, tests.
- **Change:** add read-only `assigned_count` (number of assignments using this
  set / referencing this question) and `has_graded_submissions` (any submission
  graded against an assignment that uses it). Use annotated querysets to avoid
  N+1. **These drive UX only** — integrity is already guaranteed by AIV-1/2.
- **Verify:** pytest — counts correct for a set used by 2 assignments, one with a
  graded submission; zero for an unused draft; no N+1 (assert query count).
- **What could go wrong:** N+1 on list endpoints — annotate in the queryset, not
  per-row Python.

### AIV-3b — Edit-safety notice in the teacher UI  *(depends on AIV-3a)*
- **Files:** the teacher question/set edit surfaces
  (`CreateQuestionPage` / problem-set edit / `ProblemSetPreviewPage` as
  applicable — confirm which mount the edit forms), reuse `@/shared/ui` for the
  notice, tests.
- **Change:** when `assigned_count > 0`, show a **non-blocking** banner: *"This
  is used in N assignment(s). Your edits apply to **future** assignments;
  existing ones keep exactly what students were given."* Stronger wording when
  `has_graded_submissions`. Nothing is disabled — the snapshot makes editing
  safe; this just makes it *legible*.
- **Verify:** Vitest — banner renders with the count when assigned, absent when
  not; `tsc --noEmit` + ESLint green; entry chunk stays under the PERF-06 160 kB
  budget.
- **What could go wrong:** over-blocking — this must be informational only, never
  a gate (AIV-1/2 already protect integrity).

## F. Legacy analysis & improvement opportunities

- **Content integrity:** legacy (Django 1.11) stored question content in the
  external Cabinet filesystem and graded by fetching it live — it had the *same*
  retroactive-edit hazard, just hidden behind a microservice. The modern DB move
  (content on `QuestionSubpart`) made editing easier and the hazard sharper.
  *Improve:* a per-assignment snapshot gives a guarantee legacy never had —
  "what you were graded against is immutable history."
- **Versioning:** legacy had none. Phase 1's snapshot is deliberately the
  minimum that kills the bug; AIV-7's `ProblemSetVersion` later dedups storage
  and adds audit history. Shipping A-then-B (not C) avoids over-engineering now.
- **Shared content blast radius:** the imported 646-question Cabinet corpus is
  `school=null` shared content; snapshots stop one school's edit from rewriting
  another's assigned material — a real multi-tenant safety win.
