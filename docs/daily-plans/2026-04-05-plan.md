## A. Today's Objective

Activate Croupier Phase 2 (variable substitution for numeric/fill-blank questions), expose question-mistake analytics to teachers, and give students their first view of their adaptive learning path.

---

## B. Why This Matters

**Variable substitution** is the last missing anti-cheating mechanism and the biggest quality-of-life improvement for teachers. Right now every student answers `"Solve 2x² + 3x - 2 = 0"` — identical across the class. With `{{a}}`, `{{b}}`, `{{c}}` substituted per student, assessments become meaningfully harder to copy and the question bank multiplies in effective size. The legacy Croupier's variable engine was the feature teachers loved most. Rebuilding it unlocks the full value of the numeric question type.

**Question mistake analytics** requires zero new backend data collection — `SubjectRoomQuestionMistake` rows are already being written by the grader on every tick, but there's no API endpoint or UI to read them. One serializer, one viewset, one table in the teacher assignment detail page, and teachers get their first data-driven "which questions are hard?" view. The gap between data collected and data shown is a pure UX debt that blocks teacher trust.

**Student learning path** completes the AI activation work started yesterday. `LearningPath` + `LearningPathStep` records are generated after every grading run. The backend builds a full personalized study sequence — but students see none of it. A single page using the already-live `/api/ai/learning-paths/` endpoint turns invisible background work into a visible, motivating student experience.

### Priority 1: Croupier Phase 2 — Variable Substitution

#### What to build

`variable_constraints` is a JSONField that describes named variables, their ranges, and rounding rules:

```json
{
  "a": {"min": 1, "max": 9, "integer": true},
  "b": {"min": -5, "max": 5, "integer": true},
  "c": {"min": 1, "max": 20, "integer": false, "decimals": 1}
}
```

At question-serve time (not storage time), the croupier substitutes `{{a}}`, `{{b}}`, `{{c}}` tokens in:
- `question_text` (displayed to student)
- `options[].text` (for MCQ questions)
- **NOT** `correct_answer` — the correct answer is re-evaluated at grading time

The substitution is **deterministic per (student_id, subpart_id)** using the same seeded PRNG as Phase 1.

#### Files to modify

**`backend/openshiksha/apps/core/models.py`** — Add to `QuestionSubpart`:
```python
variable_constraints = models.JSONField(
    null=True,
    blank=True,
    help_text=(
        'Variable definitions for token substitution. '
        'e.g. {"a": {"min": 1, "max": 9, "integer": true}}. '
        'Tokens {{a}} in question_text/options are replaced per student.'
    ),
)
```

**`backend/openshiksha/apps/api/croupier.py`** — Add:
```python
def substitute_variables_for_student(
    question_text: str,
    options: list[dict] | None,
    variable_constraints: dict | None,
    student_id: int,
    subpart_id: int,
) -> tuple[str, list[dict] | None, dict]:
    """
    Substitute {{var}} tokens in question_text and options with deterministic
    random values for the given student/subpart pair.

    Returns (substituted_text, substituted_options, variable_values)
    variable_values: {"a": 3, "b": -2, ...} — passed to grader for answer re-evaluation
    """
```

The substitution seed: `f"{student_id}:{subpart_id}:vars"` (distinct from Phase 1 MCQ seed).

**Grading integration** — `_grade_subpart` needs to accept `variable_values: dict | None` for numeric/fill-blank types. If the question has variables, the stored `correct_answer["answer"]` may be a Python expression string like `"{{a}} * 2 + 1"` (or a raw constant). The grader evaluates the expression with the student's variable values using a safe `eval` alternative (see below).

**Safe expression evaluation**: Use `simpleeval` library (add to requirements) or implement a small restricted evaluator that only supports basic arithmetic (`+`, `-`, `*`, `/`, `**`, `sqrt`, `abs`). Do NOT use raw `eval()`. Example approach:

```python
import ast
import operator

SAFE_OPS = {
    ast.Add: operator.add, ast.Sub: operator.sub,
    ast.Mult: operator.mul, ast.Div: operator.truediv,
    ast.Pow: operator.pow, ast.USub: operator.neg,
}

def safe_eval_expr(expr: str, variables: dict) -> float:
    """Evaluate a simple arithmetic expression with variable substitution."""
    # Replace variable names with their values first
    for k, v in variables.items():
        expr = expr.replace(f"{{{{{k}}}}}", str(v))  # replace {{a}} with value
    tree = ast.parse(expr, mode='eval')
    return _eval_node(tree.body)
```

**`backend/openshiksha/apps/api/serializers.py`** — `QuestionSubpartSerializer`: add `variable_constraints` to serializer fields. Add a `get_question_text` method that, given a student context, applies substitution. **However**: serializer-level substitution requires access to the requesting student. Better approach: add it at the ViewSet level (see below).

**`backend/openshiksha/apps/api/views.py`** — `AssignmentViewSet` or the submission/question endpoint: when serializing questions for a student, call `substitute_variables_for_student` before returning. The student is `request.user`. The current flow: `GET /api/assignments/{id}/` returns the assignment including the problem set's questions via `ProblemSetSerializer` → `QuestionSerializer` → `QuestionSubpartSerializer`. Add a `to_representation` override on `QuestionSubpartSerializer` that checks context for `student_id` and applies substitution.

**`backend/openshiksha/apps/management/commands/seed_demo_data.py`** — Add one numeric question with `variable_constraints`:

**`CreateQuestionPage.tsx`** (Question Authoring) — Add a "Variable Constraints" collapsible section below the question text area:

#### What could go wrong

- **Safe eval**: Do NOT use Python `eval()` with untrusted strings. Only evaluate answers that came from the admin/teacher (not from student input). Still use a safe evaluator to be safe.
- **Grading correctness**: If `correct_answer["answer"]` is an expression like `"({{c}} - {{b}}) / {{a}}"`, it must be evaluated with the same variable values used during display. - **MCQ with variables**: If question_type is `mcq` AND has `variable_constraints`, both Phase 1 (option shuffle) and Phase 2 (text substitution) apply. The seeds use distinct namespaces (`f"{student_id}:{subpart_id}"` for Phase 1, `f"{student_id}:{subpart_id}:vars"` for Phase 2) so they don't interfere.
- **Migration**: Nullable JSONField with default=None, no data migration needed.

### Priority 2: Teacher Question-Mistake Analytics

#### What to build

`SubjectRoomQuestionMistake` rows are written by `_update_question_mistakes()` on every tick. They accumulate `regression` (marks lost per question, per class). There's no API endpoint or frontend for this data.

**The teacher question is**: "Which questions in this assignment did my class struggle with the most?"

We need:
1. A new API endpoint: `GET /api/question-mistakes/?subject_room=<id>` — returns mistakes sorted by `regression DESC`
2. A "Hardest Questions" table in `TeacherAssignmentDetailPage`

#### Backend

**`backend/openshiksha/apps/api/serializers.py`** — Add:
```python
class QuestionMistakeSerializer(serializers.ModelSerializer):
    question_text = serializers.SerializerMethodField()
    question_type = serializers.SerializerMethodField()

    class Meta:
        model = SubjectRoomQuestionMistake
        fields = ["id", "question_id", "question_text", "question_type", "regression", "updated_at"]

    def get_question_text(self, obj):
        first_subpart = obj.question.subparts.order_by("index").first()
        return first_subpart.question_text if first_subpart else ""

    def get_question_type(self, obj):
        return obj.question.get_question_type_display()
```

**`backend/openshiksha/apps/api/views.py`** — Add:
```python
class QuestionMistakeViewSet(viewsets.ReadOnlyModelViewSet):
    serializer_class = QuestionMistakeSerializer
    permission_classes = [IsAuthenticated, IsTeacher]

    def get_queryset(self):
        qs = SubjectRoomQuestionMistake.objects.select_related(
            "question", "subject_room"
        ).prefetch_related("question__subparts")
        subject_room_id = self.request.query_params.get("subject_room")
        if subject_room_id:
            qs = qs.filter(subject_room_id=subject_room_id)
        # Only show mistakes for subject rooms the teacher teaches
        qs = qs.filter(subject_room__teacher=self.request.user)
        return qs.order_by("-regression")
```

**`backend/openshiksha/apps/api/urls.py`** — Register:
```python
router.register("question-mistakes", QuestionMistakeViewSet, basename="question-mistake")
```

## F. Legacy Analysis & Improvement Opportunities

### Variable Substitution (Croupier Phase 2)

**Legacy did**: The `croupier/` module substituted `{{ variable }}` tokens in question text using a seeded random number generator per (student_id, question_id). Variables were defined in the Cabinet CMS with min/max/step/type. The correct answer was stored as a Python expression evaluated server-side with the generated variable values.

**What was good**: Made numeric questions truly unique per student — completely neutralized copying. Teachers loved it for homework assignments.

**What was limited**: Tightly coupled to Cabinet (variable definitions stored there, not in Django). The expression evaluator used raw Python `eval()` — a security risk. No preview in the authoring UI of what students would see.

**How we improve**:
- Variable constraints stored in Django DB (`variable_constraints` JSONField on `QuestionSubpart`) — no Cabinet dependency
- Safe arithmetic expression evaluator using `ast` module — no `eval()` security risk
- Authoring UI shows live preview: as teacher types `"Solve {{a}}x + {{b}} = 0"` and sets min/max for `a` and `b`, a "Preview" section shows three sample substitutions (student 1, 2, 3) in real time

### Question-Difficulty Analytics

**Legacy did**: The `edge/` app tracked `regression` per question per SubjectRoom (same concept as `SubjectRoomQuestionMistake`). But legacy had no teacher-facing UI for this — it was only queryable via Django admin.

**How we improve**: Surface directly in the assignment detail page. Teachers see difficulty as a progress bar relative to the class maximum. This turns a raw float into immediately actionable insight.

### Adaptive Learning Path

**Legacy did**: Nothing. No learning path concept existed. Students just worked through teacher-assigned problem sets in order.

**How we improve**: The adaptive engine generates personalized step sequences based on mastery, learning gaps, and spaced repetition schedules. The student sees a clear "here's your study roadmap" page. This is a flagship differentiator — no Indian K-12 platform currently offers this.
