## A. Today's Objective

**Build the backend School Admin API (P4, backend half)** — an `IsSchoolAdmin` permission, a school-scoped `ClassRoomViewSet` (CRUD), student enrollment/unenrollment actions, and admin-scoped `SubjectRoom` management. This is the API layer the `/admin` frontend will consume. Ship it as one reviewable PR with full test coverage; the admin frontend follows in the next session.

---

## B. Why This Matters

Every feature shipped so far assumes a populated school: classrooms exist, students are enrolled, subject rooms have teachers. Today that structure can only be created by a developer with Django admin access. A real school admin — the person who decides whether to adopt OpenShiksha — has **no product surface at all**. They cannot:

- Create a classroom for Grade 7-A and set its class teacher.
- Enroll or remove students.
- Spin up a Math subject room and assign Mrs. Rao to teach it.

This is the **gatekeeper feature for self-onboarding**. Teachers are blocked until classrooms and subject rooms exist; students are blocked until they're enrolled. The legacy platform handled all of this through the Django admin too — so this is a genuine *improvement over legacy*, not a port: a real, role-guarded, school-scoped management API that a non-technical admin can drive from a UI.

Doing the backend first keeps the PR atomic and testable: pure API + permissions + tests, no UI churn. The frontend (`/admin` route, role guard, classroom/enrollment pages) is the natural follow-up and ships clean on top of a proven API.

### Priority 1: P4a — `IsSchoolAdmin` permission + school-scoped `ClassRoomViewSet`

**Permission** — `backend/openshiksha/apps/api/views/core.py` (alongside `IsTeacher`, ~line 44):

```python
class IsSchoolAdmin(permissions.BasePermission):
    """Allow only authenticated users with the ADMIN role."""
    def has_permission(self, request, view):
        return bool(request.user and request.user.is_authenticated and request.user.is_admin)
```

`User.is_admin` already exists (`core/models.py:102`) — no model change needed.

**ViewSet** — new `ClassRoomViewSet(viewsets.ModelViewSet)`:
- `permission_classes = [IsAuthenticated, IsSchoolAdmin]`
- **School scoping is the critical invariant**: `get_queryset` returns only `ClassRoom.objects.filter(school=self.request.user.school)`. An admin must never see or mutate another school's classrooms.
- `perform_create`: force `serializer.save(school=self.request.user.school)` — ignore any `school` in the request body (prevents cross-tenant injection).
- Validate `class_teacher` belongs to the same school and has `role=TEACHER`; reject otherwise (400).
- Soft-delete via `is_active=False` rather than hard `DELETE` (preserve historical assignments/submissions) — override `destroy` to set `is_active=False`.
- Register: `router.register(r"classrooms", ClassRoomViewSet, basename="classroom")` in `apps/api/urls.py`.

**Serializer** — `ClassRoomSerializer` (`apps/api/serializers/` or core serializers): `id, standard, division, class_teacher, academic_year, is_active, student_count` (annotated), read-only `school`. Nested-light: return `class_teacher` as `{id, full_name}` and `standard` as `{id, number}` for display.

**Legacy reference**: legacy `ClassRoom` was admin-managed only; relationships preserved exactly (school/standard/division/class_teacher/students). **Change**: expose it as a guarded REST API instead of Django admin.

**Verify**: `pytest openshiksha/apps/api/ -q` — admin can CRUD own-school classrooms; admin of school B gets empty list / 404 on school A's classroom; non-admin gets 403.

- Return the updated roster.

**SubjectRoom admin write path** — extend the existing `SubjectRoomViewSet` (`core.py:330`) OR add an admin-scoped variant:

Add admin create: body `{classroom, subject, teacher, student_ids}`, validate `classroom.school == request.user.school`, `teacher` is a same-school teacher, enforce the `unique_together (classroom, subject)`.

### Priority 3: P4c — Admin roster/read endpoints

**School summary** — `@action(detail=False, methods=["get"], url_path="summary")` on `ClassRoomViewSet` (or a small `SchoolAdminViewSet`):

- `GET users/?role=teacher&school=<own>` and `?role=student` — but **force school scoping server-side** for admins (never trust a client `school` param). Returns `{id, full_name, email}` lists for the UI's add-student / assign-teacher dropdowns.

**Verify**: summary counts match seeded data; teacher/student lists contain only own-school users.

### Dependencies / Blockers

- **No blocker.** All models (`School`, `ClassRoom`, `SubjectRoom`, `User.role`) already exist. No migration required — this is pure API/permission/serializer work.
- `seed_demo_data` already creates a school with classrooms/teachers/students → ready-made test + manual-verification fixture.

### What Could Go Wrong

- **Cross-tenant data leak** — the #1 risk. Every queryset and every write must be scoped to `request.user.school`. Mitigation: a shared `_assert_same_school` helper + an explicit test that school-B admin cannot touch school-A objects (the most important test in this PR).
- **`school` is nullable on some users** (open students have no school). An admin must always have a school; guard with a clear 400 if `request.user.school is None` rather than leaking a global queryset.
- **Soft-delete vs hard-delete** — hard-deleting a classroom would cascade to subject rooms and orphan assignments. Soft-delete (`is_active=False`) avoids this; list defaults to active-only with an `?include_inactive=true` escape hatch.
- **Batch enrollment partial failure** — one bad student ID shouldn't 500 the whole request. Validate-and-report pattern.

## F. Legacy Analysis & Improvement Opportunities

### School / Classroom Administration

**Legacy**: All school structure — creating classrooms, enrolling students, assigning teachers to subject rooms — was done by superusers through the **Django admin**. There was no admin-facing product UI or API. School onboarding was effectively a developer/ops task.

**What was good**: The data model was sound — school → classroom → subject room → students, with class teachers. Django admin gave full control with zero custom code.

**What was limited**:
- **Not self-serve** — a school could not onboard itself; every classroom/enrollment change required a developer with admin credentials.
- **No tenant isolation in the tool** — Django admin shows *all* schools to any staff user; nothing scopes a school admin to their own school.
- **No product surface** — no way to build a polished, role-appropriate admin experience.

**Modern improvement**:
- A **role-guarded, school-scoped REST API** (`IsSchoolAdmin`) that hard-isolates each admin to their own school — true multi-tenant safety the Django admin never had.
- **Self-service onboarding**: a school admin drives classroom/enrollment/subject-room setup from a real UI (next session), no developer in the loop.
- **Soft-delete by default** — year-end archiving without destroying historical assignment/submission data.
- **API-first** — the same endpoints power a future mobile admin app or bulk-CSV enrollment importer.
