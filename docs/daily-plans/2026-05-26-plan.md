## B. Why This Matters

**Natural Language Explanations** closes a fundamental gap in the student learning loop. Right now, a student submits an assignment, gets a score, and has no idea _why_ they were wrong. The backend already generates AI explanations post-grading — but students can't see them. Adding even a simple "Why?" panel after submission turns a passive score into an active learning moment. Every incorrect answer becomes a micro-lesson.

**LLM Question Generation** is the single most powerful teacher productivity feature OpenShiksha can add. Creating a good question set currently requires a teacher to:
1. Think of the question
2. Type it in with KaTeX syntax
3. Define options, correct answer, variable constraints
4. Repeat 10–15 times per problem set

With AI-assisted generation, a teacher types "Generate 5 MCQ questions about quadratic equations for Grade 10" → gets draft cards they can approve or edit. This turns 30 minutes of work into 5 minutes. It's the feature most likely to bring teachers back to the platform.

```ts
// GET /api/v1/ai/explanations/?subpart=<id>&submission=<id>
export function useExplanation(subpartId: number, submissionId: number | null) {
  return useQuery({
    queryKey: ["explanation", subpartId, submissionId],
    queryFn: () => fetchExplanation(subpartId, submissionId),
    enabled: !!submissionId,
    refetchInterval: (data) => (data ? false : 5000), // poll until found
  });
}
```

#### What Could Go Wrong

- **Latency**: LLM calls take 2–5 seconds. Students will submit and see the grade instantly; the explanation arrives a few seconds later. The polling mechanic handles this gracefully.
- **Cost at scale**: Each submission generates one API call per subpart. For a class of 30 with 10 subparts = 300 Claude calls per assignment graded. At ~$0.003/call (Sonnet), that's ~$0.90 per assignment graded. Acceptable for a demo/pilot; needs monitoring at scale. The Google Gemma and Ollama fallbacks reduce cost to zero in dev.
- **Provider not configured**: The stub fallback ensures students always see _something_ — never a broken UI. The stub text is honest ("review the concept and try again") rather than a spinner that never resolves.
- **Grade level logic**: `submission.student.grade` may be null for open students. The task defaults to 8 — reasonable for middle school. Consider adding a `grade` field to user registration forms later.

#### 2a. Backend Endpoint

**File**: `backend/openshiksha/apps/ai/views.py` — new `QuestionGenerationViewSet`

```
POST /api/v1/ai/generate-questions/
```

**Request body**:
```json
{
  "prompt": "Generate 5 MCQ questions about quadratic equations for Grade 10",
  "question_type": "mcq",
  "difficulty": 2,
  "count": 5,
  "chapter_id": 12,
  "subject_id": 3,
  "standard_id": 10
}
```

**Response**:
```json
{
  "questions": [
    {
      "question_type": "mcq",
      "difficulty": 2,
      "subparts": [
        {
          "question_text": "Solve: x² - 5x + 6 = 0. What are the roots?",
          "options": [
            {"key": "A", "text": "x = 2, x = 3"},
            {"key": "B", "text": "x = 1, x = 6"},
            {"key": "C", "text": "x = -2, x = -3"},
            {"key": "D", "text": "x = 2, x = -3"}
          ],
          "correct_answer": {"type": "mcq", "answer": "A"},
          "explanation": "Factor: (x-2)(x-3) = 0, so x = 2 or x = 3."
        }
      ]
    }
  ]
}
```

**Implementation**:
```python
class QuestionGenerationViewSet(ViewSet):
    permission_classes = [IsAuthenticated]

    @action(detail=False, methods=["post"], url_path="generate-questions")
    def generate_questions(self, request):
        if request.user.role != UserRole.TEACHER:
            return Response({"detail": "Only teachers can generate questions."}, status=403)

        serializer = GenerateQuestionsRequestSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        d = serializer.validated_data

        result = generate_questions_via_llm(
            prompt=d["prompt"],
            question_type=d.get("question_type", "mcq"),
            difficulty=d.get("difficulty", 2),
            count=d.get("count", 5),
            chapter_id=d.get("chapter_id"),
            subject_id=d.get("subject_id"),
            standard_id=d.get("standard_id"),
        )
        return Response(result)
```

**`generate_questions_via_llm()`** in `llm_client.py`:

The prompt is structured to elicit JSON output. Key design choices:
- **JSON mode**: Use Anthropic's `{"type": "json"}` response format (Claude 3.5+ supports structured output) — or instruct Claude to return raw JSON and parse it
- **System prompt**: "You are a curriculum question generator for Indian K-12 education (CBSE/ICSE). Always output valid JSON matching the schema exactly."
- **Schema validation**: Parse the JSON and validate against expected structure; return 400 if malformed
- **Stub path**: If no LLM provider, return 2 pre-baked example questions so the teacher sees the UI working

The `explanation` field in the generated subpart is bonus content — not stored on `QuestionSubpart` yet. Store it in `solution_text` once that field is added in P8.

#### What Could Go Wrong

- **JSON parsing failure**: LLM may return malformed JSON. Wrap in try/except; return 500 with a user-friendly message ("AI generation failed — please try again or create manually"). Retry once before giving up.
- **Hallucinated correct answers**: For math questions, the LLM might generate an incorrect "correct answer." Teachers MUST review before accepting. The UI's Edit mode is the safety valve. Consider adding a "verify" step for numeric questions.
- **Rate limiting**: Anthropic free tier has aggressive rate limits. Add a `max_tokens=1500` cap and a `timeout=30s` to the request. If rate-limited, show a "Please wait a moment" message rather than a 500.
- **`ANTHROPIC_API_KEY` not set**: `llm_client.generate_questions_via_llm()` uses the same cascade as explanations — falls back to stub questions. The UI should note "AI generation is using demo mode — set ANTHROPIC_API_KEY for real questions."

## F. Legacy Analysis & Improvement Opportunities

### Natural Language Explanations (Priority 1)

**Legacy**: No equivalent. Students submitted answers and received a binary correct/incorrect. The grader computed a score and stored it. There was no mechanism for the system to explain _why_ an answer was wrong. Teachers were expected to review assignments in class and provide explanations manually.

**Modern improvement**: AI-generated per-subpart explanations stored persistently. Key improvements:
- **Available 24/7**: Student can review at 10pm without a teacher
- **Grade-calibrated**: Std 5 gets "4×2 means 4 groups of 2"; Std 11 gets "factor using the discriminant"
- **Hindi support**: Multi-language (configured via `language` field on `SubpartExplanation`)
- **Cost-transparent**: `input_tokens` + `output_tokens` fields on the model enable cost dashboards
- **Provider-resilient**: 4-provider cascade means the feature degrades gracefully rather than failing

### LLM Question Generation (Priority 2)

**Legacy**: The Sphinx authoring interface was a Django form-based UI for creating questions. Teachers filled in question text, options, and constraints manually. There was no AI assistance. Question creation was slow enough that the OpenShiksha team built content in-house rather than enabling schools to do it themselves.

**Modern improvement**: AI generation dramatically lowers the authoring barrier. Key improvements:
- **Draft cards with Accept/Edit/Discard**: Human-in-the-loop — teachers approve every question
- **Context-aware**: Providing `chapter_id`, `subject_id`, `standard_id` lets the LLM tailor questions to curriculum
- **Bulk generation**: Generate 5 questions at once instead of creating them one by one
- **KaTeX-aware**: Prompt instructs Claude to use LaTeX notation (`$x^2 - 5x + 6 = 0$`) that renders in the KaTeX panel
- **Solution text included**: The generated `explanation` field populates `solution_text` — giving students instant worked solutions without extra teacher effort

### Cabinet Import (Priority 3)

**Legacy**: 679 real questions existed in the Cabinet filesystem in a JSON format with:
- Token syntax: `_{variable}_` for substitution placeholders
- `pow(base, exp)` Python notation for powers
- `solution`: full worked solution text
- `hint`: progressive hint text
- Options as `{"1": "...", "2": "...", "3": "...", "4": "..."}` (integer keys, not A/B/C/D)
- Constraints as `{"var": {"min": 1, "max": 10, "step": 1}}`

**Modern improvement**: Converting to the modern format:
- `_{var}_` → `{{var}}` (Django/Jinja template syntax, already used by Croupier)
- `pow(x, 2)` → `x**2` (Python native)
- Options keyed as A/B/C/D (consistent with MCQ grader)
- `solution` → `solution_text`, `hint` → `hint_text` (new fields added today)
- All in the DB (no Cabinet microservice dependency for serving questions)
