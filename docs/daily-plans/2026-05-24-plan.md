## A. Today's Objective

Fix the duplicate migration conflict introduced by yesterday's two-branch merge, then deepen the gamification layer with a Streak Grace Day mechanic and milestone badges — making the streak system forgiving enough that students maintain streaks through real-world interruptions (weekends, sick days), and rewarding enough that hitting milestones feels meaningful.

---

## B. Why This Matters

- **Migration conflict is a silent blocker**: `core/0006_add_question_subpart_image_url.py` and `core/0006_add_assignment_target_student.py` both depend on `0005` independently. Django will detect multiple leaf migrations and either error during `migrate` (when ambiguous) or produce a broken migration graph. Any new developer cloning and running `docker compose up` will see a migration failure before they can even test the platform. This must be resolved before any new migrations are created.

- **Streak Phase 2 makes streaks worth keeping**: The current streak system (PR #84) is binary — miss one day, lose everything. This is the Duolingo model pre-2022, and it's known to cause frustration: a student who studies Monday through Saturday, sleeps through Sunday, loses a 6-day streak and feels punished rather than rewarded. The grace day mechanic (one missed day = streak paused, not broken) changes the psychological calculus — it rewards consistency over perfection. Combined with visible milestone badges at 7, 30, and 60 days, the streak becomes an aspirational goal rather than an anxiety trigger.

- **Milestone badges close the reward loop**: The current StudentDashboard shows a fire badge when `streak >= 3`. There's no differentiation between day 3 and day 30. A student who has maintained a 30-day streak deserves a different visual signal than one who has maintained a 3-day streak — both for their own satisfaction and to signal status to teachers. Milestone badges (Starter → Week → Month → Champion) give students intermediate goals and a sense of progression that keeps them returning daily.

### Priority 1: Fix core/0006 Migration Conflict

**PR target**: `fix/2026-05-24-migration-dedup`

#### Problem

Both `feat/2026-05-23-question-images` (PR #86) and `feat/2026-05-23-per-student-remedials` (PR #87) were branched from `modernization` at the same commit (`0005_add_student_streak_and_remedial_fields`), each created a `0006` migration independently, then both merged. The result: two files both named `0006` in `core/migrations/`, both with `dependencies = [("core", "0005_...")]`.

Django's migration framework uses lexicographic ordering to detect leaf migrations. With two `0006` files, `manage.py migrate` can't determine the graph unambiguously.

#### Fix

Rename `0006_add_assignment_target_student.py` → `0007_add_assignment_target_student.py` and update its `dependencies`:

```python
# 0007_add_assignment_target_student.py
class Migration(migrations.Migration):
    dependencies = [
        ("core", "0006_add_question_subpart_image_url"),   # ← was 0005_...
    ]
    operations = [...]  # unchanged
```

The ordering makes semantic sense: image_url is on QuestionSubpart (content), target_student is on Assignment (workflow) — content before workflow.

**Steps**:
1. Rename the file (git mv, not OS rename — preserves git history)
2. Edit `dependencies` in the renamed file
3. Run `python manage.py migrate --check` inside Docker to verify no errors
4. Run full backend test suite to confirm nothing regressed

**Edge case**: Any migration that was created after these two (there are none yet on this branch) would need its dependency updated too. Since we're at the leaf, only the rename is needed.

#### What Could Go Wrong

- **Django migration graph still ambiguous**: If some tooling cached the old name. Fix: `python manage.py migrate --run-syncdb` or simply delete `.pyc` cache files.
- **CI fails on migration check**: CI runs `python manage.py migrate --check` — with the rename fixed this should pass. If not, check that `edge/0003_make_tick_submission_nullable` also has no conflict (only one `0003` file in `edge/`, so it's fine).

### Priority 2: Streak Phase 2 — Grace Day + Milestone Badges

**PR target**: `feat/2026-05-24-streak-phase2`

#### 2a. Grace Day Mechanic

**The rule**: If a student misses exactly one day, their streak is paused (not broken) and they get one chance to resume the next day. If they miss two or more consecutive days, the streak resets.

This is equivalent to: a gap of 2 days is treated as a 1-day gap (paused, not broken). A gap of 3+ days resets.

**Model change** — add `streak_grace_used` to `StudentStreak`:

```python
streak_grace_used = models.BooleanField(
    default=False,
    help_text="True if the student has already used their grace day for the current streak."
)
```

Migration: `makemigrations core --name="add_streak_grace_day"`. Non-breaking — all existing rows get `grace_used=False`.

**Update `record_activity()`**:

```python
def record_activity(self, activity_date):
    from datetime import timedelta

    if self.last_activity_date is None:
        self.current_streak = 1
        self.streak_grace_used = False
    elif activity_date == self.last_activity_date:
        return  # same-day no-op
    elif activity_date == self.last_activity_date + timedelta(days=1):
        # Consecutive day — normal increment; reset grace
        self.current_streak += 1
        self.streak_grace_used = False
    elif activity_date == self.last_activity_date + timedelta(days=2) and not self.streak_grace_used:
        # Missed exactly one day, grace available — pause, don't break
        self.current_streak += 1
        self.streak_grace_used = True
    else:
        # Gap too large, or grace already used — reset
        self.current_streak = 1
        self.streak_grace_used = False

    self.last_activity_date = activity_date
    if self.current_streak > self.longest_streak:
        self.longest_streak = self.current_streak
    self.save(update_fields=[
        "current_streak", "longest_streak", "last_activity_date",
        "streak_grace_used", "updated_at"
    ])
```

**Design note**: The grace only applies once per streak run. A student can't "grace-day-hop" across a 5-day gap by having multiple grace days. `streak_grace_used` resets to False on a consecutive-day increment, so each streak run gets one grace.

#### 2d. Frontend — Milestone Badge in StudentDashboard

Replace the current single fire-badge with a tier-aware badge component:

```tsx
// StreakBadge.tsx (new small component)
const TIER_CONFIG = {
  none: null,
  starter: { icon: "🔥", label: "On Fire", color: "text-orange-500" },
  week: { icon: "⚡", label: "Week Warrior", color: "text-yellow-500" },
  month: { icon: "🌟", label: "Month Master", color: "text-amber-500" },
  champion: { icon: "👑", label: "Champion", color: "text-purple-600" },
};

export function StreakBadge({ streak, tier, graceUsed }: {
  streak: number;
  tier: "none" | "starter" | "week" | "month" | "champion";
  graceUsed: boolean;
}) {
  if (streak === 0) return null;
  const config = TIER_CONFIG[tier];

  return (
    <div className="flex items-center gap-1 text-sm font-semibold">
      <span className={config?.color}>{config?.icon || "🔥"}</span>
      <span>{streak} day streak</span>
      {graceUsed && (
        <span className="text-xs text-gray-400 ml-1">(grace day active)</span>
      )}
      {config && tier !== "none" && tier !== "starter" && (
        <span className={`text-xs ${config.color} ml-1`}>{config.label}</span>
      )}
    </div>
  );
}
```

The `graceUsed` indicator is subtle but valuable — students know they've used their lifeline and should study tomorrow.

#### What Could Go Wrong

- **Grace day timezone issues**: `record_activity(activity_date)` is called with `timezone.localdate()`. If the server timezone differs from the student's local timezone, a student studying at 11pm their time might record the next calendar day on the server. Phase 1 solution: use UTC consistently; Phase 2: add user timezone preference.
- **Grace day and signal interaction**: The streak signal fires on `Submission.post_save` and the SRS `mark_reviewed` view both call `record_activity`. If a student submits an assignment and also does a drill on the same grace day, both calls hit the same `StudentStreak` row. The idempotency guard (`activity_date == self.last_activity_date → return`) handles this correctly.

## F. Legacy Analysis & Improvement Opportunities

### Migration Fix (Priority 1)

**Legacy**: N/A — this is a modern artifact from the concurrent-branch merge pattern. The root cause is two PRs both branching from the same commit and both auto-incrementing to `0006`. Going forward, a policy of always merging and rebasing before creating a new migration would prevent this. For today: fix by renaming.

**Process improvement**: After today's fix, establish a rule: any PR that creates a migration must first rebase onto `modernization` (to pick up the latest migration number) before the PR is reviewed. This is a standard Django team practice.

### Streak Phase 2 (Priority 2)

**Legacy**: No gamification existed in the original OpenShiksha. Streaks are entirely new.

**Modern design decision**: The grace day mechanic draws from Duolingo's "streak freeze" (2017+). The difference from Duolingo: Duolingo sells streak freezes as a paid mechanic (or earns them via XP). Here the grace day is automatic — one per streak run, reset on a consecutive day. This is more like GitHub's streak logic (which is actually forgiving by definition since it counts contributions across the day). The automatic grace is more forgiving and appropriate for a K-12 educational context where missing a day due to illness or a school event shouldn't be penalized. Teachers can communicate to students that "one grace day per run" is a feature, not a bug.

**Milestone badge naming**: Chose "starter/week/month/champion" over numbers because tier names are stickier as identity markers — "I'm a Week Warrior" carries more social weight than "I have a 7-day streak badge."

### Email Notifications (Priority 3)

**Legacy**: Pylon SMS notifications existed for specific events (assignment due reminders, etc.) and required a third-party SMS gateway with an Indian telecom provider. SMS was the right choice for the legacy platform (2015-era India, low smartphone penetration, reliable SMS delivery). Today email is more practical as a starting point:
- Zero external dependencies in dev (console backend)
- Free tier in prod (Gmail SMTP, SendGrid, Mailgun)
- Actionable (students can click a link when email clients support it)
- Teachers and parents often have email in school systems

**Future**: Keep the `School.sms_enabled` field — it was planned correctly. When adding SMS in Phase 2, implement it as a separate notification channel alongside email rather than replacing it. Use a service like Twilio or MSG91 (Indian SMS provider).
