# OpenShiksha Daily Plan — 2026-03-31

## A. Today's Objective

Close the loop on the core student workflow: a student must be able to **open an assignment, read questions, enter answers, and submit** — none of that is possible today because questions have no stored text.

---

## B. Why This Matters

Right now the platform has a structural gap: `Question` and `QuestionSubpart` models store metadata (type, difficulty, correct_answer) but **no question content** — no text, no MCQ options, nothing a student can read. This means the assignment detail page cannot be built without first fixing the data model.

Fixing this unlocks the entire core student workflow in one session:
- Students can finally *do* something after logging in, not just see a list
- The grading pipeline (already built) has something real to exercise
- AI recommendations (already built) will have real Tick data to train on
- It makes the platform **demonstrable** for the first time end-to-end

The companion priorities — teacher dashboard and demo seeding — complete the loop so the full cycle (teacher creates → student practices → system grades) can run.

### Priority 1: Question Content + Assignment Detail Page

#### 1a. Backend: Add content fields to QuestionSubpart

**What to add to `QuestionSubpart`** (in `backend/openshiksha/apps/core/models.py`):

```python
question_text = models.TextField(
    blank=True,
    default='',
    help_text='LaTeX/plain text for the question or subpart prompt',
)
options = models.JSONField(
    null=True,
    blank=True,
    help_text=(
        'MCQ choices: [{"key": "A", "text": "Option A"}, ...]. '
        'Null for non-MCQ types.'
    ),
)
```

**Rationale**: Content stored locally eliminates the Cabinet dependency for development and provides a fallback if Cabinet is unavailable. Cabinet can still be the authoritative source — the sync task can populate these fields from Cabinet data. For now, locally-stored text unblocks the frontend.

**Migration**: `makemigrations core --name="add_question_text_options_to_subpart"`

**Serializer fix** (`backend/openshiksha/apps/api/serializers/core.py`):

The current `QuestionSubpartSerializer` exposes `correct_answer` — which a student receiving assignment detail should **not** see (they would know the answer before attempting). Fix:
```python
# For student-facing assignment detail: hide correct_answer
class QuestionSubpartStudentSerializer(serializers.ModelSerializer):
    class Meta:
        model = QuestionSubpart
        fields = ['id', 'index', 'tags', 'question_text', 'options']
        # correct_answer intentionally omitted

# For teacher/admin (existing QuestionSubpartSerializer unchanged — can expose correct_answer)
```

Use `QuestionSubpartStudentSerializer` in `QuestionSerializer` when serving assignment detail to students. The `AssignmentDetailSerializer` already returns nested `problem_set → questions → subparts` — this just swaps in the student-safe serializer.

**Note on security**: Even for teachers and admins, exposing `correct_answer` in the API should be limited to admin tools. For Phase 1, the priority is making sure students can't see it. A more hardened approach (per-role serializer routing) can be added later.

## F. Legacy Analysis & Improvement Opportunities

### Question Content Storage

| Aspect | Legacy | Modern (current gap) | Today's improvement |
|--------|--------|---------------------|---------------------|
| Question text | Stored exclusively in Cabinet (external) | Not stored anywhere in DB | Add `question_text` to `QuestionSubpart` |
| MCQ options | Stored in Cabinet | Not in DB | Add `options` JSONField |
| Cabinet dependency | Required for all renders | Not yet integrated | Local storage as fallback + dev enabler |
| Grading | Cabinet grading only | `correct_answer` stored locally ✅ | Hybrid: grade locally, Cabinet optional |

Legacy was fully Cabinet-dependent — there was no way to render or grade questions without Cabinet being online. The modern approach stores content locally (today's addition) with Cabinet as optional upstream. This is strictly better: it removes a hard dependency and enables offline/development use.

### Assignment Submission Flow

| Aspect | Legacy | Modern |
|--------|--------|--------|
| Answer storage | Cabinet only (external) | `answers` JSONField in `Submission` ✅ |
| Save progress | Yes (legacy had "save" separate from "submit") | Implement today: auto-save on change |
| Math rendering | Cabinet-generated PNG images | KaTeX client-side rendering (better: vector, searchable, faster) |
| Submission UX | Full page reload on submit | React SPA: instant feedback, no reload |

### Teacher Tools

The legacy teacher dashboard was entirely server-rendered Django templates with no AJAX. Teachers had to do full page loads for every action. The modern React version will be significantly more responsive — modals, optimistic updates, real-time counts.
