## A. Today's objective

**Prove the i18n framework scales to a third (regional) language by generalizing
the binary `en|hi` machine into an N-locale registry with a *pilot-coverage*
model, then rolling out Marathi (मराठी) surface-by-surface** — anonymous journey
first, then student core loop, then parent surface — closing **LA-9** and the
Language Access initiative's North Star clause that "a third language must be a
content task, not an engineering task."

## B. Why this matters

The North Star explicitly demands the framework make a third language **a content
task, not an engineering task**. Right now it can't: `Locale = 'en' | 'hi'` is
hardcoded in `i18nContext.ts`, `I18nProvider.tsx` (single `hiDictCache`,
`import('./locales/hi')`), `LanguageSwitcher.tsx` (two literal buttons),
`format.ts`, `dateFnsLocale.ts`, the backend `preferred_language` choices, and the
parity guard compares en↔hi only. Adding a third language today means editing six
files plus a 929-key translation in one shot — exactly the engineering tax the
North Star says we must remove.

LA-9a pays that tax **once**: a single locale registry every consumer reads from,
plus a **pilot-coverage** parity model so a new locale can ship as a *subset*
(English fallback fills the gaps — runtime already does this, principle 3) instead
of demanding all 929 keys before the first PR. After 9a, every Marathi PR is pure
content: translate a key cluster, done. That's the proof.

**Why Marathi:** Devanagari script — it **reuses the existing
`"Noto Sans Devanagari"` font stack** (principle 4), so the pilot isolates the
real framework question (can the switcher / parity / dict-loader handle N>2?) from
font-loading work. 9a still makes the font stack/`intlLocale`/`htmlLang` *data-
driven per locale* so a future non-Devanagari language (Tamil/Bengali — the harder
stress test) is config + content, not a code change. Marathi is also a top-5
Indian language with a large Maharashtra K-12 base — a genuine regional win, not a
toy.

**Why this batch and not a new initiative:** Language Access is the top active
bet; LA-9 is its last unblocked increment. After it closes, the named next seed is
**Mobile shell / PWA-offline**.

## D. Concrete implementation plan

### PR 1 — LA-9a: N-locale framework + pilot-coverage parity (New/hardening)

The only engineering PR. Discipline: **zero behavior change for en/hi** — every
existing i18n test passes unmodified; the diff is mechanical generalization.

- **New file `frontend_modern/src/shared/i18n/locales/registry.ts`** — the single
  source of truth for "what locales exist":
  ```ts
  export interface LocaleMeta {
    code: Locale;            // 'en' | 'hi' | 'mr'
    label: string;           // switcher glyph, e.g. 'EN', 'हिं', 'मरा'
    nativeName: string;      // 'English' | 'हिंदी' | 'मराठी' (aria + a11y)
    htmlLang: string;        // document.documentElement.lang value
    intlLocale: string;      // 'en-IN' | 'hi-IN' | 'mr-IN' (Intl + date-fns)
    coverage: 'complete' | 'pilot'; // complete ⇒ full parity required
  }
  export const LOCALES: LocaleMeta[] = [ /* en (complete), hi (complete) */ ];
  export const localeMeta = (code: Locale): LocaleMeta => /* lookup */;
  ```
  **9a registers only en + hi** (both `complete`) — leaving the empty seat is the
  proof that a third language is now additive. `Locale` stays a string-literal
  union but is **derived/checked against `LOCALES`** so adding `'mr'` later is a
  one-line registry edit + the union.
- **`i18nContext.ts`:** `isLocale` becomes `LOCALES.some(l => l.code === value)`;
  keep `resolveInitialLocale`, `interpolate`, `defaultI18nValue` (still en).
- **`I18nProvider.tsx`:** replace the single `let hiDictCache` + hardcoded
  `import('./locales/hi')` with a **module-level `Map<Locale, LocaleDict>` cache**
  and a generic loader `loadLocale(code)` that does
  `import(\`./locales/${code}\`)` (en stays eager as the fallback). The `useEffect`
  that fetches on switch keys off the active locale generically. English fallback
  in `t()` is unchanged.
- **`format.ts` + `dateFnsLocale.ts`:** replace the `locale === 'hi' ? 'hi-IN' : 'en-IN'`
  ternary with `localeMeta(locale).intlLocale`; `dateFnsLocaleFor` maps via a small
  registry→date-fns map (en→undefined, hi→`hi`; mr added in 9c). Keep the barrel
  comment about not eager-importing date-fns.
- **`LanguageSwitcher.tsx`:** render `LOCALES.map(...)` buttons instead of two
  literals — each button gets `lang={meta.htmlLang}`, `aria-pressed`,
  `aria-label={t('common.languageSwitchTo', { language: meta.nativeName })}`. With
  only en/hi registered the rendered output is **identical** to today (assert in
  the existing switcher test).
- **`parity.test.ts` → pilot-coverage contract:** for each registered locale:
  - `coverage: 'complete'` ⇒ exact key-set parity with en + no blanks (today's
    behavior, applied to en & hi).
  - `coverage: 'pilot'` ⇒ **subset allowed** (English fallback fills gaps), but
    every key it *does* define must (i) exist in en and (ii) match en's `{var}`
    placeholders, and must not be blank. No mr locale exists yet, so this branch is
    dormant until 9b — but the contract ships here.
- **Verify:** all existing `i18n.test.tsx`, `parity.test.ts`, `format.test.ts`,
  switcher tests pass **unedited** (proof of zero behavior change). Add a small
  `registry.test.ts`: every `LOCALES` entry has non-empty fields, `en` is present
  and `complete`, `localeMeta` round-trips. `npm run lint && npx tsc --noEmit &&
  npx vitest run && npm run build` — confirm the entry chunk is unchanged (the
  registry is ~1 kB of metadata; dicts stay lazy; 160 kB guard holds).
- **What could go wrong:** the dynamic `import(\`./locales/${code}\`)` template
  must keep Vite able to statically discover the chunk — Vite supports template
  dynamic imports with a static prefix (`./locales/`), but **verify the hi chunk
  still splits out** in `npm run build` output (it must not fold into the entry
  chunk). If Vite can't analyze it, fall back to an explicit
  `{ hi: () => import('./locales/hi') }` loader map in the registry (same effect,
  still one edit per new locale). Keep en eager.

## F. Legacy analysis & improvement opportunities

- **Legacy (Django 1.11) had no i18n at all** — server-rendered English templates,
  no language preference, no regional support. Pure "new"; nothing to port.
- **Modern advantage being proven:** the whole bet of an in-house i18n module
  (principle 2 — no i18next, defend the 160 kB budget) is that adding a locale is
  cheap. LA-9 is the test of that thesis: after 9a, Marathi ships as plain content
  PRs at zero entry-chunk cost (dict is lazy, registry is ~1 kB, `Intl` is free).
  If this works, every future regional language (Tamil, Bengali, Telugu) is the
  same recipe — config + translation, no engineering.
- **Pilot-coverage is the key improvement:** i18next-style libraries force you to
  think in "complete locale files." Our subset-with-English-fallback model lets a
  regional language launch on the *highest-leverage surface first* (the anonymous
  parent journey) and grow — better product sequencing than all-or-nothing.
