## B. Why This Matters

The Parent Intelligence backend is the single biggest UX leap for parents we have shipped this cycle — a plain-language narrative, urgent alerts, and concrete home activities. **None of it reaches parents today** because there is no UI. An API without a surface is invisible work.

Beyond surfacing one feature, this is also the **first product-grade parent-side AI experience**. Until now parents got proficiency bars and sparklines — useful, but technical. The insights page is the difference between "your child's score in Algebra dropped 12%" (a chart fact) and "Aanya struggled with Long Division this week — try 15 minutes together on it before the weekend" (an action a parent can actually take). That distinction is the entire point of the AI investment.

It is also **atomic and reviewable**: pure frontend (new page, new API hook, two small components, one parent-dashboard link), no backend churn, no migration. Exactly the size of PR we want.

### Priority 1: Insights page scaffolding + data fetch

**Route** — register in the parent area of the React Router config (alongside the existing `/parent/...` routes):
```
/parent/insights              → ParentInsightsLandingPage (child picker)
/parent/insights/:childId     → ParentInsightsPage
```
Both gated by the existing parent role guard (the same one wrapping today's parent dashboard).

**API hook** — `frontend_modern/src/features/parent/api.ts` (extend the existing parent API module; create if absent):
```ts
export function useLatestParentSummary(childId: number) {
  return useQuery({
    queryKey: ["parent-summary", "latest", childId],
    queryFn: () => apiClient.get(`/ai/parent-summaries/latest/?child=${childId}`).then(r => r.data),
    enabled: Number.isFinite(childId),
  });
}

export function useGenerateParentSummary() {
  return useMutation({
    mutationFn: (payload: { child_id: number; language?: "en" | "hi" }) =>
      apiClient.post("/ai/parent-summaries/generate/", payload).then(r => r.data),
  });
}
```

**Page component** — `frontend_modern/src/features/parent/ParentInsightsPage.tsx`:
- Loading state → skeleton card.
- Success → `NarrativeCard` (week range, child name, `model_used` chip, `summary_text` paragraph) + `AlertsPanel` + `HomeActivitiesPanel`.
- Empty (404 / no summary yet) → friendly empty state with a primary "Generate this week's summary" button calling the mutation; on success, invalidate the `latest` query and re-render with the new summary.
- Error fallback for non-2xx that isn't a 404.

**Rationale**: the backend already returns a stub narrative when no LLM is configured, so the happy path is reliable in dev. The "Generate" button gives parents (and us, during demo) on-demand control rather than waiting for a Celery schedule that doesn't exist yet.

**Verify**: log in as the seeded parent, navigate to `/parent/insights/<child-id>`, see narrative; click Generate; re-render shows updated `generated_at` + same week's summary in place (idempotent upsert).

### Priority 2: Alerts + Home Activities panels

**`AlertsPanel`** — `frontend_modern/src/features/parent/components/AlertsPanel.tsx`:
- Maps `alerts: Array<{severity: "info"|"attention"|"urgent", code: string, message: string}>` to styled cards.
- Severity styling via Tailwind: `urgent` → red border + alert icon, `attention` → amber, `info` → blue. Use the same iconography we already use elsewhere (no new icon dependency).
- Empty array → render nothing (do not show an empty "no alerts" block — visual noise).

**`HomeActivitiesPanel`** — `.../components/HomeActivitiesPanel.tsx`:
- Maps `home_activities: Array<{chapter: string, minutes: number, activity: string, kind: "practice"|"celebrate"|...}>` to cards.
- Each card: chapter name (header), suggested minutes (badge), the activity sentence (body).
- One celebratory-tone card when `kind === "celebrate"` (strongest chapter fallback path on the backend).

**Rationale**: keep the two panels dumb-presentational. They take a slice of the summary payload and render. No data fetching, no business logic — so they're trivially testable and reusable on a future mobile parent screen.

**Verify**: with seeded data where weak chapters exist, panel shows targeted home activities; with no weak chapters, the celebrate variant renders; alerts of all three severities (info/attention/urgent) render with the right color treatment. Quick component tests with Vitest + Testing Library: render the panel with a fixture payload, assert text + severity class.

### Priority 3: Parent dashboard wiring + child picker

**Dashboard wiring** — in the existing parent dashboard (likely `frontend_modern/src/features/parent/ParentDashboardPage.tsx`, or wherever today's per-child Progress/Assignments tabs live): add a third tab or a prominent "View Insights →" link per child card that routes to `/parent/insights/:childId`.

- Decision (autonomous): a **prominent secondary button** beside the existing tabs, not a third tab. Reason: insights is a *destination page*, not a peer-view of the same data; a button signals "navigate away to a deeper view." A tab would imply the data is just another lens on the same chart, which it isn't.

**Landing page** — `ParentInsightsLandingPage.tsx`:
- Fetches the parent's children via the existing `/api/v1/users/me/` (or whichever endpoint already drives the parent dashboard).
- Renders a simple child picker (one card per child with a "Open insights →" link).
- For parents with exactly one child, redirect immediately to `/parent/insights/:childId` (skip the picker).

**Verify**: parent dashboard now has an Insights entry point per child; bare `/parent/insights` route works whether the parent has 1 or N children.

### Dependencies / Blockers

- **None.** The backend API is live on `modernization`. The parent dashboard, role guard, axios client, and React Query are all in place from prior sessions.
- LLM provider keys are not required: the deterministic stub guarantees `summary_text` always renders.

### What Could Go Wrong

- **Empty-summary first load** is the common case for any parent whose Monday Celery job has not yet run (we have not scheduled one). Mitigation: the empty state's primary CTA is "Generate this week's summary," which makes the page immediately useful even on a cold install.
- **Mutation queue UX**: the `generate/` endpoint queues a Celery task and returns 202 + a task id. Don't optimistically render a fake summary; show a "Generating… (may take ~30s)" toast and poll `latest` after the mutation succeeds (a short setTimeout-then-refetch is fine — no need for a websocket here).
- **Parent without children** (data hole or open-student-only family): landing page should show an empty state, not crash on `children[0]`.
- **Wrong child ID in URL** (parent tries to deep-link another parent's child): backend already 404s; UI should show a clear "Summary not available" empty state, not a stack trace.
- **i18n token**: the API accepts `language: "en" | "hi"`. We pass `en` by default today; expose a small toggle in the page header for future-proofing but ship `en` only this round if the existing parent dashboard does not yet have a language toggle plumbed through.

## F. Legacy Analysis & Improvement Opportunities

### Parent-Facing Reporting

**Legacy**: Parents received nothing in the legacy product beyond static gradebook-style views — proficiency tables, optionally an email report. No narrative, no alerts, no recommended activities, no on-demand regeneration.

**What was good**: Data accuracy. The proficiency numbers themselves were trustworthy and well-defined.

**What was limited**:
- **No interpretation layer.** Parents had to *infer* meaning from numbers. Most didn't.
- **No proactive surfacing.** A child going inactive for 10 days was visible only if the parent logged in and noticed.
- **No "what do I do about it?"** layer. Parents had data, not next steps.

**Modern improvement (this session, frontend half)**:
- **Narrative-first**: the page leads with a human-readable paragraph generated from real stats.
- **Alerts surface themselves**: urgent items render at the top with red treatment — no exploration required.
- **Action-oriented**: every page exit point is an *activity* the parent can do *this week* with the child.
- **On-demand regeneration**: the parent can press "Generate this week's summary" without waiting for a Monday cron — gives them agency and gives us a clean demo path before Celery beat is wired.

This is a meaningful improvement over what *any* legacy K-12 product gave parents, not just OpenShiksha legacy.
