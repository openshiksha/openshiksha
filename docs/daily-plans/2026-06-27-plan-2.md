## A. Today's objective

Advance **Production Observability & Operational Readiness** into **Batch 3 —
Backups & DR drill**. Batch 1 made a prod incident *seeable*; Batch 2 made the
system *measurable*; Batch 3 makes the data **recoverable**. Ship the data-loss
insurance the live DB completely lacks today: an automated, off-site Postgres
backup, plus a **tested** (not just documented) restore drill, in small,
low-risk, additive PRs.

## B. Why this matters

OpenShiksha is **live in production** (DO droplet, k3s, `openshiksha.org`) with a
**single `postgres:15-alpine` StatefulSet on one 10 Gi PVC and zero backups**
(verified: no CronJob, no `pg_dump` anywhere, no object-storage wiring in
`k8s/`). One bad migration, one `DROP`, one corrupted volume, one droplet loss =
**every teacher's questions, every student's submissions and proficiency
history, gone, unrecoverably.** This is the single highest-severity gap on the
whole board — features don't matter if the data behind them can vanish. Batch 3
closes it and directly unblocks **Batch 4 (alerting)**, which needs a
backup-freshness signal to alert on. Initiative doc:
[`docs/initiatives/2026-production-observability.md`](../initiatives/2026-production-observability.md).

## D. Concrete implementation plan

### BAK-1 — Backup/restore scripts + dump image _(New)_ — **foundation**
- **Image:** `backend/Dockerfile.backup` — `FROM postgres:15-alpine` (gives
  `pg_dump`/`pg_restore`/`psql` at the **exact major version** of the prod server
  — a `pg_dump` older than the server refuses to run, so don't use a generic
  awscli image). Add the static **`mc`** (MinIO client) binary
  (`https://dl.min.io/client/mc/release/linux-amd64/mc`, `chmod +x`) for
  S3-compatible upload — single static binary, far lighter than installing
  `aws-cli` into alpine. `COPY` the two scripts in; default `ENTRYPOINT`
  runs `pg_backup.sh`.
- **`scripts/backup/pg_backup.sh`** (`set -euo pipefail`):
  - Read config from env: `DATABASE_URL` (or discrete `PGHOST/PGUSER/PGDATABASE`
    + `PGPASSWORD`), `S3_ENDPOINT`, `S3_BUCKET`, `S3_PREFIX`
    (default `postgres/`), `S3_ACCESS_KEY`, `S3_SECRET_KEY`,
    `RETENTION_DAYS` (default `14`).
  - `pg_dump --format=custom --no-owner --no-privileges` → pipe through `gzip`
    to a timestamped file `openshiksha-YYYYmmddTHHMMSSZ.dump.gz` in a tmp dir.
  - `mc alias set` from the S3_* env, `mc cp` the file to
    `s3/$S3_BUCKET/$S3_PREFIX`, then prune objects older than `RETENTION_DAYS`
    (`mc rm --older-than` / list+filter).
  - Echo a clear success line (and non-zero exit on any failure — the CronJob
    surfaces it).
- **`scripts/backup/pg_restore.sh`** — inverse: download a named (or `latest`)
  object, `gunzip`, `pg_restore --clean --if-exists --no-owner -d "$TARGET_DB"`.
  Refuse to run without an explicit `CONFIRM=1` (guard against fat-fingered prod
  restore).
- **Legacy reference:** none — the Django 1.11 monolith had no backup story;
  greenfield ops.
- **Verify:** `shellcheck scripts/backup/*.sh` clean; `docker build -f
  backend/Dockerfile.backup .` succeeds; `pg_backup.sh` `--help`/dry path prints
  usage. No live infra touched.
- **What could go wrong:** `pg_dump` version skew (mitigated by pinning
  `postgres:15-alpine`); secrets echoed in logs (never `echo` the URL/keys; rely
  on `mc alias set` reading env). Keep the image lean (don't `apk add` aws-cli).

### BAK-2 — Local tested round-trip drill _(New)_ — depends on BAK-1
- **`scripts/backup/drill.sh`** (`set -euo pipefail`) — runs against the
  **docker-compose** Postgres (no cloud creds), suitable for a developer and for
  a future CI smoke:
  1. Point at the compose DB (`DATABASE_URL` from compose env).
  2. Seed a known fixture (reuse `manage.py seed_demo_data`, or insert a sentinel
     table with N rows) and capture `COUNT(*)` of a couple of core tables
     (`core_user`, `core_submission`).
  3. Run `pg_backup.sh` in **local mode** (write the dump to a local path instead
     of S3 — add an `S3_ENDPOINT=""` ⇒ "skip upload, keep local file" branch in
     BAK-1 so the same script is exercised).
  4. `DROP`/recreate the DB (or restore into a scratch DB
     `openshiksha_drill`), run `pg_restore.sh`.
  5. Re-count and **assert equality**; exit non-zero with a diff on mismatch.
- **Why local-first:** makes the restore path *tested and reproducible* without
  provisioning a bucket — the DoD's "*tested* restore runbook" clause. A later
  CI job can call this (out of scope here; note it in BAK-5).
- **Verify:** `bash scripts/backup/drill.sh` green against `docker compose up
  postgres`; intentionally corrupt the dump → drill fails loudly (negative test
  in the PR description, not committed).
- **What could go wrong:** drill mutates a real dev DB — default to a **scratch
  DB name** and require `DRILL_DB` set, never the developer's main DB; document
  the destructiveness at the top of the script.

### BAK-3 — Prod backup `CronJob` (prod-overlay-only, additive) _(New)_ — depends on BAK-1
- **`k8s/base/backup-cronjob.yaml`** — a `batch/v1 CronJob`
  (`schedule: "0 2 * * *"`, `concurrencyPolicy: Forbid`,
  `successfulJobsHistoryLimit: 3`, `failedJobsHistoryLimit: 3`,
  `backoffLimit: 2`) running the published backup image. Env from the existing
  `openshiksha-secrets` (`DATABASE_URL`) + **new** keys `S3_ENDPOINT`,
  `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`. Small resource
  requests/limits; `restartPolicy: OnFailure`.
- **Additive wiring:** add the file to the **prod overlay's** `resources:`
  (`k8s/overlays/prod/kustomization.yaml`) — **not** to `k8s/base/kustomization.yaml`
  — so `qa`/dev kustomize builds are unchanged (no backup runs there, no creds
  needed). (If base inclusion is cleaner for the kubeconform gate, instead include
  in base but document that qa simply leaves the S3 keys empty and the Job no-ops;
  prefer prod-overlay-only to keep qa truly untouched.)
- **Secret docs:** append the four `S3_*` keys to
  [`k8s/base/secret.example.yaml`](../../k8s/base/secret.example.yaml) (empty,
  with a comment: DigitalOcean Spaces is the intended S3-compatible target;
  server-side only, never commit real values).
- **Image publish:** the CronJob references
  `ghcr.io/openshiksha/openshiksha-backup:prod`. Either (a) extend the CI publish
  step in [`ci-cd.yaml`](../../.github/workflows/ci-cd.yaml) to build+push
  `Dockerfile.backup` alongside backend/frontend, **or** (b) document a manual
  one-off build/push and defer CI publish to a follow-up. Prefer (a) if it stays
  a small additive job; flag clearly if it risks the pipeline.
- **Verify:** `kustomize build k8s/overlays/prod | kubeconform -strict ...`
  (the **existing CI gate** from #459) passes; `kustomize build
  k8s/overlays/qa` is **byte-for-byte unchanged** (diff before/after to prove it).
- **What could go wrong:** breaking the kubeconform gate with a schema typo (run
  it locally first); a CronJob with no creds in qa erroring on schedule — avoided
  by prod-overlay-only inclusion. Don't bake any secret into the manifest.

### BAK-4 — Backup-freshness gauge _(New)_ — reuses the Batch-2 collector
- **Model:** add a tiny `BackupRun` model (`apps/core/models.py`) — `id`,
  `created_at` (auto), `status` (`success`/`failure`), `size_bytes` (nullable),
  `object_key` (nullable). One migration.
- **Writer:** a `manage.py record_backup_run --status success --size … --key …`
  management command the CronJob calls **after a successful `mc cp`** (one extra
  container step or an `&&` in the backup script via `python manage.py`). Keep it
  best-effort — a failure to record must not fail the backup.
- **Gauge:** extend the existing **MET-2 `BusinessMetricsCollector`**
  (`apps/core/metrics.py`) with `openshiksha_backup_age_seconds` (now − latest
  `BackupRun.created_at`, or a large sentinel / absent when none) and
  `openshiksha_backup_last_success_timestamp`. Same gated, on-scrape, read-only
  pattern as the other business gauges — **no new endpoint, no new dep**, off by
  default (`METRICS_ENABLED` unset ⇒ collector not registered).
- **Why it compounds:** Batch 4 alerting can fire on
  `openshiksha_backup_age_seconds > 36h` — a concrete, meaningful SLO derived
  directly from this batch.
- **Verify (`pytest`):** seed a `BackupRun`, scrape `/metrics` with
  `METRICS_ENABLED=True`, assert `openshiksha_backup_age_seconds` present and
  reasonable; assert absent when disabled; `record_backup_run` command writes a row.
- **What could go wrong:** the gauge ships before any writer exists (no rows) —
  handle the empty case (emit a sentinel / omit the family) so it's honest, not a
  misleading `0`. Migration must be additive/backwards-compatible.

  keep names as `<your-spaces-bucket>` placeholders; the operator fills real
  values into the secret out-of-band (same pattern as `SENTRY_DSN`).

## F. Legacy analysis & improvement opportunities

Backups/DR are **greenfield** — the Django 1.11 monolith (now under `legacy/`)
had no automated dump, no off-site copy, and no restore procedure; data integrity
relied on the host's own disk. There is nothing to port. The improvement is
straightforward and overdue: an **off-site, retained, version-matched dump on a
schedule**, plus the discipline that distinguishes real ops from theatre — a
**restore that has actually been run** (BAK-2), not a backup nobody has ever
restored from.
