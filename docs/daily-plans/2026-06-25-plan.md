# OpenShiksha — Daily Plan, 2026-06-25

## A. Today's objective

Promote a **fresh top initiative — Production Observability & Operational
Readiness** — and ship its first batch. The board carried **no unblocked next
bet** (Accessibility — WCAG 2.1 AA closed today; Open-Source Readiness, Mobile

Meanwhile OpenShiksha is **live in production** and effectively **un-observable**.
Batch 1 (OBS-1..5) makes a prod incident *seeable*: a real readiness probe,
error tracking, request correlation, build-info, and frontend crash reporting —
all additive and env-gated.

## B. Why this matters

The platform is feature-complete and **in production** (DO droplet, k3s,
`openshiksha.org`), but operability has not kept pace. The dominant pre-launch
risk is no longer a missing feature — it's a prod incident **nobody can
diagnose**: there is no error tracking, the readiness probe never checks the
DB/cache (a pod with a dead DB still gets traffic), logs are unstructured and
uncorrelated, and a frontend crash is invisible. This batch is the cheapest,
highest-leverage compounding work available — small, low-risk, infra/backend
PRs squarely in the plan/execute lane — and it unblocks every later operability
batch (metrics, backups/DR, alerting). New initiative doc:
[`docs/initiatives/2026-production-observability.md`](../initiatives/2026-production-observability.md).

## C. Today's batch — 5 shippable PRs (lowest-risk-first)

1. **OBS-1 — `/readyz/` deep readiness endpoint + repoint k8s readinessProbe.**
   Build the deep drain-signal probe the `healthz` docstring already specifies;

4. **OBS-4 — Request-correlation id + JSON log option.** Middleware stamps an
   `X-Request-ID` into a contextvar + every log record; opt-in JSON formatter via

5. **OBS-5 — Frontend error reporting, env-gated.** `@sentry/react` wired into
   the existing shared `ErrorBoundary` **only when `VITE_SENTRY_DSN` is set**
   (dynamic import ⇒ entry chunk unchanged). _(New)_

**Build order:** 1 → 2 → 3 → 4 → 5. Independent except the soft OBS-4→OBS-3
edge; one failure does not block the rest.

## D. Concrete implementation plan

### OBS-1 — `/readyz/` deep readiness endpoint + probe repoint _(Improve)_
- **Backend:** add `readyz(request)` next to `healthz` in
  [backend/openshiksha/urls.py](../../backend/openshiksha/urls.py) (or a small
  `apps/api/views/health.py` sibling reused at top level). It performs the
  **same DB + cache check** as the existing
  [`health_check`](../../backend/openshiksha/apps/api/views/health.py) and
  returns `200` healthy / `503` on any failure. Keep it Host-header-cheap and
  `AllowAny` (probes don't auth). Mount `path("readyz/", readyz, name="readyz")`.
  Leave `/healthz/` exactly as-is (cheap liveness).
- **k8s:** in [k8s/base/backend.yaml](../../k8s/base/backend.yaml) change the
  **readinessProbe** `httpGet.path: /healthz/ → /readyz/` (keep the `Host:
  backend` + `X-Forwarded-Proto` headers). **Do not touch the livenessProbe** —
  it stays `/healthz/` so a DB blip drains the pod from the LB instead of
  killing it (restart loop).
- **Legacy reference:** none; this is the intended split documented in the
  `healthz` docstring, never built.
- **Verify:** new `pytest` — `/readyz/` returns 200 when up; returns 503 when DB
  `ensure_connection` raises (mock) and when `cache.set/get` fails; `/healthz/`
  returns 200 without touching the DB (assert no DB query, e.g. via
  `django_assert_num_queries(0)`).
- **What could go wrong:** readiness now flaps if the DB is briefly slow — that's
  *correct* (drain, not crash); `initialDelaySeconds: 10` already covers startup.
  Ensure `/readyz/` is reachable through the same ingress/Host path as
  `/healthz/`.

### OBS-2 — `/api/v1/version/` build-info endpoint _(New)_
- **Backend:** `version_info(request)` (`AllowAny`) returning
  `{"version": settings.APP_VERSION, "git_sha": os.getenv("GIT_SHA","unknown"),
  "built_at": os.getenv("BUILD_TIME","unknown"), "environment": <dev/qa/prod>}`.
  Mount under `apps/api/urls.py` as `path("version/", ...)`. No secrets, ever.
- **Build:** add `ARG GIT_SHA` / `ARG BUILD_TIME` → `ENV` in
  [backend/Dockerfile.prod](../../backend/Dockerfile.prod); pass
  `--build-arg GIT_SHA=${{ github.sha }}` (+ a `date -u` build time) from the CI
  publish step that builds the prod image.
- **Verify:** `pytest` — endpoint returns the four keys; falls back to `"unknown"`
  when env unset; `AllowAny` (works unauthenticated).
- **What could go wrong:** don't leak anything beyond sha/time/env; keep the
  endpoint trivially cheap (no DB).

### OBS-3 — Sentry error tracking (backend), env-gated _(New)_
- **Deps:** add `sentry-sdk[django]` (pin a current 2.x) to
  [backend/requirements.txt](../../backend/requirements.txt).
- **Init:** in [settings/production.py](../../backend/openshiksha/settings/production.py),
  `if os.getenv("SENTRY_DSN"): sentry_sdk.init(dsn=..., integrations=[Django,
  Celery, Redis], traces_sample_rate=float(os.getenv("SENTRY_TRACES_SAMPLE_RATE",
  "0")), send_default_pii=False, environment=..., before_send=_scrub)`. Factor
  the init + `_scrub` into a small `apps/core/observability.py` so it is
  unit-testable without importing the whole settings module.
- **Scrubber:** `_scrub(event, hint)` removes `request.headers.Authorization`/
  `Cookie`, and any data key matching `password|token|secret|api_key|anthropic`.
- **Verify:** `pytest` — `init_sentry()` returns `False`/no-ops when `SENTRY_DSN`
  unset; `_scrub` strips an `Authorization` header and a `password` field from a
  synthetic event. Do **not** make real network calls in tests.
- **What could go wrong:** never init in dev/test (gate strictly on the env var);
  keep `send_default_pii=False`; ensure the Celery integration doesn't
  double-report already-handled task retries.

### OBS-4 — Request-correlation id + JSON log option _(Improve)_
- **Middleware:** `RequestIDMiddleware` (new, in `apps/core/middleware.py`) reads
  `X-Request-ID` (or generates a uuid4 hex), stores it in a `ContextVar`, sets it
  on `request`, and echoes `X-Request-ID` on the response. Add to `MIDDLEWARE`
  **early** (right after `SecurityMiddleware`).
- **Logging:** a `logging.Filter` that injects `record.request_id` from the
  contextvar (default `"-"`); add a `json` formatter (use `python-json-logger`
  if added, else a tiny custom `Formatter` emitting `json.dumps({level, time,
  logger, message, request_id})`) and select it when `LOG_FORMAT=json`. Default
  stays today's text formatters (no behaviour change).
- **Sentry tie-in (soft dep on OBS-3):** if Sentry is active, `scope.set_tag(
  "request_id", ...)` in the middleware — a no-op guard when Sentry absent.
- **Verify:** `pytest` — middleware returns the **same** id supplied in the
  request header; generates a new one when absent; the response carries the
  header; the JSON formatter produces parseable JSON containing `request_id`.
- **What could go wrong:** contextvar leakage across async/threads — reset in a
  `finally`; don't log request bodies/PII; keep the text default intact so CI
  log assertions (if any) don't break.

### OBS-5 — Frontend error reporting, env-gated _(New)_
- **Deps:** add `@sentry/react` to `frontend_modern`.
- **Wiring:** a `src/shared/observability/reporter.ts` with `initErrorReporting()`
  + `reportError(err, info)` that **dynamically imports** `@sentry/react` only
  when `import.meta.env.VITE_SENTRY_DSN` is set (so the entry chunk is unchanged
  when unset — perf budget defended). Call `initErrorReporting()` once at app
  root; have the existing
  [ErrorBoundary](../../frontend_modern/src/shared/ui/ErrorBoundary.tsx)'s
  `componentDidCatch` call `reportError(...)`. Keep the friendly **localized**
  (LA i18n) fallback UI exactly as-is.
- **Verify:** Vitest — with no DSN, the boundary renders its fallback on a child
  throw and `reportError` is a **no-op** (no dynamic import, no crash); assert the
  reporter early-returns when the env var is unset. Confirm `npm run build` entry
  chunk stays under the 160 kB guard when DSN unset.
- **What could go wrong:** a static `import '@sentry/react'` would drag the SDK
  into the entry chunk and fail the perf guard — must be dynamic + gated; don't
  double-report (boundary reports; let Sentry's own global handler stay off or
  deduped).

## F. Legacy analysis & improvement opportunities

Observability is **greenfield** — the Django 1.11 monolith (now under `legacy/`)
had no structured error tracking, no readiness/liveness split, and no request
correlation. There is nothing to port; this is pure modern-stack hardening. The
one "legacy-shaped" lesson: the monolith's failures were diagnosed by SSH +
`grep` over flat logs — exactly the workflow this initiative replaces. The
improvement over both legacy *and* today's modern stack is **correlation**
(request id threaded through logs + errors) and **drain-not-crash** readiness.
