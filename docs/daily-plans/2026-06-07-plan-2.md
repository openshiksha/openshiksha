# OpenShiksha Daily Plan — 2026-06-07 (batch 2)

## A. Today's objective

Advance the now-top initiative, **Teacher Workspace**, by shipping its three
unblocked polish increments — **TW-5 (join-code UX), TW-4 (dashboard
information-architecture), TW-3 (assignment lifecycle: due-date edit +
close/reopen)** — plus a backend lifecycle foundation and an end-to-end smoke
test that locks in the TW-1 continuity flow. The most important outcome: a
teacher can share a join code three ways, see what needs them first on the
dashboard, and **close/reopen or re-date an assignment** instead of being stuck
with a read-only detail page.

## B. Why this matters

The earlier batch today closed **Performance Budget** (PERF-01..06,
[#251](https://github.com/openshiksha/openshiksha/pull/251)–[#256](https://github.com/openshiksha/openshiksha/pull/256)),
so **Teacher Workspace** is the live top initiative (promoted 2026-06-07).
TW-1 already merged ([#250](https://github.com/openshiksha/openshiksha/pull/250)):
*Assign* deep-links now preselect the set/room and a "preview as a student" link
lands before publish. TW-2 (editable preview) is **hard-blocked** on Authoring
Integrity Phase 1 snapshots, so today we pull the three *independent* polish
increments the initiative explicitly lists as the next move:
TW-3 ∥ TW-4 ∥ TW-5.

This serves the core mission directly: teachers are the gatekeepers. Today the
`TeacherAssignmentDetailPage` is **read-only** — a teacher who set the wrong due
date, or wants to stop accepting late work, has no in-product path and must fall
back to Django admin. The join-code widget hides the `expires_at` the backend
already tracks and offers no shareable link. The dashboard mounts everything at
one altitude with no "what needs me first." Each gap is small; together they are
why the surface still feels unfinished (the initiative's framing). Closing them
moves Teacher Workspace materially toward its North Star with no schema risk
beyond one additive field.

Initiative doc: [`docs/initiatives/teacher-workspace.md`](../initiatives/teacher-workspace.md).

## D. Concrete implementation plan

### TW-5 — Join-code UX  *(frontend-only, independent)*
- **Files:** `frontend_modern/src/features/teacher/ClassroomCodeWidget.tsx`
  (extend), optionally a tiny `frontend_modern/src/features/teacher/JoinCodeQR.tsx`
  (new, lazy). Tests: `ClassroomCodeWidget.test.tsx` (new).
- **What to change:**
  - `expires_at` is **already serialized**
    (`backend/.../serializers/core.py:71`) and present on the TS type
    (`frontend_modern/src/types/index.ts:23`) — just render it: a relative
    "expires in N days" (or "No expiry" when null), tinted urgent when < 48 h.
  - **Shareable link:** build `${window.location.origin}/register/school?code=${myCode.code}`
    with its own copy button. (Confirm `RegisterSchoolPage` reads a `?code=`
    query param; if not, add that read so the link prefills the join field —
    small, in-scope.)
  - **Regenerate confirmation:** wrap the existing `generateMutation.mutate()`
    in a confirm (reuse `@/shared/ui` `Modal`/`ConfirmDialog` if present, else a
    minimal inline confirm) warning that the current code stops working.
  - **QR (optional):** render behind a "Show QR" toggle via `React.lazy` so the
    QR generator is a separate chunk. Prefer a dependency-free inline SVG/QR
    approach; if a lib is needed, it must be dynamically imported only inside
    `JoinCodeQR.tsx`.
- **Legacy reference:** none — legacy had no self-service join codes.
- **Verify:** Vitest renders expiry text for both null and dated codes, copies
  link, and shows the confirm before regenerate; `npm run build` keeps the entry
  chunk under the PERF-06 budget (QR must not leak into it).
- **What could go wrong:** QR pulling weight into the entry chunk — guard by
  lazy import + re-run `check:budget`. The generate endpoint currently sets no
  `expires_at` (null); "No expiry" is the correct, honest display until a TTL is
  added (out of scope today).

### TW-4 — Dashboard "needs attention" + empty states  *(frontend-only)*
- **Files:** `frontend_modern/src/features/teacher/TeacherDashboard.tsx`
  (extend, currently 293 LOC), a new
  `frontend_modern/src/features/teacher/NeedsAttentionPanel.tsx`, tests.
- **What to change:**
  - Derive from the assignments the teacher already loads
    (`useTeacherAssignments`): **overdue** (`due_at` past), **ungraded**
    (`average_score === null` after due), **low completion**
    (`completion_rate` below a threshold, e.g. < 0.5 once due). Render a compact
    strip of "X overdue · Y ungraded · Z low-completion" chips that deep-link to
    the relevant assignment detail / room. Hide the strip entirely when nothing
    needs attention (no dead-weight).
  - **Guided empty states** using `@/shared/ui` `EmptyState`: no subject rooms →
    "ask your admin / create a classroom"; rooms but no problem sets → link to
    the problem-set builder; sets but no assignments → link to *Assign* (which,
    post-TW-1, preselects). Each empty state offers exactly one next action.
- **Design rationale:** initiative principle #5 ("lean by default, depth on
  demand") and #6 ("no dead-ends"). Surfacing the few items that need a teacher
  is higher-value than the eager analytics panels #248 already decluttered.
- **Verify:** Vitest with fixtures for (a) a busy teacher with overdue/ungraded
  items → strip lists them with correct counts; (b) a brand-new teacher with no
  rooms → empty state with a next-action link; strip absent.
- **What could go wrong:** double-counting an assignment across categories —
  define precedence (overdue > ungraded > low-completion) and test it.

### TW-3a — Backend: assignment close/reopen lifecycle  *(foundation)*
- **Files:** `backend/openshiksha/apps/core/models.py` (Assignment, ~L686),
  a new migration in `backend/openshiksha/apps/core/migrations/`,
  `backend/openshiksha/apps/api/views/core.py` (`AssignmentViewSet` ~L733,
  `SubmissionViewSet` ~L842), `backend/.../serializers/core.py`
  (Assignment serializers), API tests under `backend/.../apps/api/tests/`.
- **What to change:**
  - Model: add `closed_at = models.DateTimeField(null=True, blank=True,
    help_text="When set, the assignment no longer accepts submissions.")` —
    **purely additive**, no data migration needed. Add a `@property is_closed`
    and a derived `status` helper (`closed` if `closed_at`, else `overdue` if
    `due_at < now`, else `active`).
  - ViewSet: two teacher-only owner-checked actions —
    `POST /api/assignments/{id}/close/` (sets `closed_at = now`) and
    `POST /api/assignments/{id}/reopen/` (clears it). Mirror the existing
    `submissions` action's permission pattern (`request.user.role == TEACHER` +
    object ownership via `get_object`, which already filters by `assigned_by`).
  - Serializer: expose read-only `closed_at` + derived `status` on the detail
    (and list) serializer so the frontend can badge it.
  - `SubmissionViewSet.create`/`update`: reject (HTTP 423/400 with a clear
    `detail`) when the target assignment `is_closed`. **This is the safety
    point** — closing must actually stop late submissions, not just relabel.
- **Legacy reference:** legacy had no explicit close; an assignment was "done"
  only by due date. Adding an explicit close is an **Improve** (teachers asked
  to stop late work without moving the date).
- **Verify:** pytest — close sets `closed_at` + flips `status`; reopen clears
  it; a student POST/PATCH to a closed assignment is rejected; non-owner teacher
  gets 403/404; migration applies cleanly (`manage.py migrate` + `makemigrations
  --check` clean).
- **What could go wrong:** the student assignment queryset still *shows* closed
  assignments (correct — they should see "closed", not have it vanish); ensure
  only *submission writes* are blocked, not reads. Confirm no existing test
  asserts submission succeeds without a due/closed check.

## F. Legacy analysis & improvement opportunities

- **Assignment lifecycle:** legacy (`core/`, Django 1.11) treated an assignment
  as implicitly over at its due date — no teacher control to stop late work or
  re-date without DB surgery. *Good:* simple. *Limited:* no agency for the
  teacher; late submissions silently accepted or silently rejected by date math.
  *Improve:* an explicit `closed_at` + close/reopen makes the state legible and
  teacher-controlled, and the submission-write guard makes "closed" mean closed.
- **Join codes:** no legacy analogue (self-service enrollment is a modern
  addition). The backend already models `expires_at`/`is_active`; the UX just
  needs to surface them and add sharing — pure **Improve**.
- **Dashboard IA:** legacy teacher views were separate server-rendered pages;
  "what needs me first" didn't exist. The SPA can aggregate it cheaply from data
  already fetched — a genuine capability gain, not a port.
