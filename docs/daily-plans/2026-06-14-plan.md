## A. Today's objective

**Make OpenShiksha an installable PWA whose student core loop survives a flaky or
absent connection.** By the end of this batch a phone user can add OpenShiksha to
their home screen, launch it full-screen, and — having loaded an assignment once
online — re-open it offline and read every question, with an honest localized
offline indicator throughout.

## B. Why this matters

OpenShiksha targets K-12 students in India, where intermittent 3G connectivity is
the norm. Today the app is a plain SPA: **no manifest, no service worker, no
offline handling, and an in-memory-only React Query cache that is wiped on every
reload** (verified 2026-06-14). A dropped connection means a white screen or an
infinite spinner, and there is no way to install the app to a home screen.

This is the highest-leverage unbuilt thing left now that Language Access is done.
The mobile *chrome* already exists (M5-01 bottom tabs, V2 safe-area/touch-target
pass) — what's missing is exactly the PWA layer: installability + offline read-
tolerance. It is also cheap against our hard-won perf budget: a Workbox service
worker is a separate out-of-band file and the IndexedDB persister is ~1 kB, so the
entry chunk (~41 kB gzip vs the 160 kB CI guard) is essentially unaffected.

### PR 2 — MSO-2: Network-status hook + offline banner (New) — *independent*

- **New `frontend_modern/src/shared/hooks/useOnlineStatus.ts`:** returns
  `navigator.onLine`, subscribes to `window` `online`/`offline` events, cleans up
  on unmount. SSR/Node-safe default (`true` when `navigator` is undefined, for the
  test env).
- **New `frontend_modern/src/features/layout/OfflineBanner.tsx`:** a slim banner
  rendered in `AppShell` (above `<main>` or pinned under the navbar) shown only when
  offline. `role="status"` + `aria-live="polite"`, V2 styling (warm amber, not a
  harsh red — informational, not error). Copy from i18n: e.g.
  `connectivity.offlineBanner` = "You're offline — showing saved work."
- **i18n:** add a `connectivity.` cluster to `en.ts` + `hi.ts` (complete locales,
  full parity required) and to `mr.ts` (pilot — translate it too since it's a core-
  loop string the parity pilot floor should grow to cover). Keys: `offlineBanner`,
  `backOnline` (optional brief "Back online" flash), `offlineTitle`. Run the
  existing parity guard.
- **Wire into `AppShell.tsx`:** render `<OfflineBanner />` between `<Navbar />` and
  `<main>`; keep the skip-link target intact.
- **Verify:** vitest — mock `navigator.onLine = false`, render `AppShell`, assert
  the banner appears; dispatch a `window` `online` event, assert it hides. Hook unit
  test for the event subscribe/unsubscribe. `npm run lint && npx tsc --noEmit && npx
  vitest run`; parity guard green.
- **What could go wrong:** `navigator.onLine` is famously optimistic (true even on a
  captive portal). That's acceptable for a banner; do **not** gate data fetching on
  it — React Query already handles real fetch failures. Document this limitation in
  the hook's JSDoc.

### PR 3 — MSO-3: Service worker via `vite-plugin-pwa` (New) — *independent*

- **Add dev dep `vite-plugin-pwa`** (pulls Workbox). In `vite.config.ts` add the
  plugin with `registerType: 'autoUpdate'`, `injectRegister: null` (we register
  manually in `main.tsx` to keep it prod-only and behind a flag), and
  `workbox.globPatterns` covering the built `js/css/html/svg/woff2`. **Set
  `manifest: false`** — we already ship a hand-written `manifest.webmanifest` from
  MSO-1; do not let the plugin generate a second one.
- **Runtime caching (Workbox):**
  - The Google Fonts + KaTeX CDN (`fonts.gstatic.com`, `cdn.jsdelivr.net/npm/katex`)
    → `CacheFirst` with an expiration cap, so math + Devanagari render offline.
  - **`/api/*` → `NetworkOnly`** (explicit). The persisted React Query cache
    (MSO-4), not Workbox, owns API read-tolerance; never let Workbox cache API
    responses (principle 2).
  - Navigation fallback to the precached `index.html` so deep links boot offline.
- **`main.tsx`:** register the SW **prod-only** (`import.meta.env.PROD`), via the
  plugin's `virtual:pwa-register` `registerSW({ onNeedRefresh, onOfflineReady })`.
  Wire `onNeedRefresh` to a minimal "New version available — Refresh" banner (no
  toast system exists; reuse the `OfflineBanner` slim-banner pattern from MSO-2 for
  visual consistency). Guard the virtual import so dev + tests don't choke (it's
  prod-only).
- **Budget:** the SW (`sw.js`) and Workbox runtime are emitted as **separate**
  files, not folded into the entry chunk. After `npm run build`, confirm the entry
  chunk size is unchanged against `scripts/check-bundle-budget.mjs` (160 kB guard).
- **Verify:** `npm run build`; serve `dist/` over HTTPS/localhost, load once, then
  toggle DevTools → Network → Offline and reload → app shell still renders. Confirm
  `sw.js` registers (Application → Service Workers). Bundle-budget script passes.
  Add a unit test for the `onNeedRefresh` banner component; SW behavior itself is
  validated manually (document the steps in MSO-5's offline-test doc).
- **What could go wrong:** an `autoUpdate` SW can serve stale assets if precache
  versioning is wrong — Workbox hashes precache entries, so a new build busts them;
  verify by building twice and confirming the update prompt fires. Registering in
  dev causes confusing caching — keep it strictly `import.meta.env.PROD`. The
  virtual module must not break Vitest — alias/stub `virtual:pwa-register` in the
  test setup if needed.

### PR 4 — MSO-4: Persist React Query cache to IndexedDB (New) — *sequence after MSO-3*

- **Add deps** `@tanstack/react-query-persist-client` + `idb-keyval` (tiny). In
  `main.tsx`, replace the bare `QueryClientProvider` with
  `PersistQueryClientProvider` using an `idb-keyval`-backed `AsyncStorage`
  persister.
- **Cache policy:** bump `gcTime` (formerly `cacheTime`) to e.g. 24 h so entries
  survive long enough to be persisted/restored; keep `staleTime` at 5 min so online
  sessions still refetch. Set a `buster` keyed to the app version so a deploy
  invalidates the persisted cache.
- **Scope what persists (principle 2):** use `dehydrateOptions.shouldDehydrateQuery`
  to persist **only GET reads** that are safe + useful offline — assignment detail,
  assignment list, dashboard, due-for-review. **Exclude** anything auth/token-
  bearing and all mutations. JWTs live in the auth store (zustand/localStorage), not
  the query cache — confirm no query key holds a token before shipping.
- **Effect:** combined with MSO-3 (shell boots offline) + MSO-2 (offline banner), a
  student who opened an assignment online can reload it offline and read every
  question from the restored cache.
- **Verify:** vitest — wire a `PersistQueryClientProvider` in a test, hydrate a
  query, assert it restores from the mock persister. Manual: load an assignment
  online → go offline → reload → questions still render. `npm run lint && npx tsc &&
  npx vitest run`; bundle-budget green (`idb-keyval` is ~1 kB and lazy).
- **What could go wrong:** persisting too much (e.g. teacher PII or large question
  banks) bloats IndexedDB — the `shouldDehydrateQuery` allowlist contains this.
  Restoring a stale mutation could double-submit — we persist **reads only**, so
  this can't happen. A cache schema change across deploys is handled by `buster`.

## F. Legacy analysis & improvement opportunities

- **Legacy (Django 1.11) was server-rendered, online-only** — every page was a
  round-trip; a dropped connection meant a dead page. There is nothing to port;
  this is purely a modern-platform capability the SPA architecture makes possible.
- **Why a PWA over a native app:** the target market is cost- and storage-
  sensitive; a PWA installs from the browser with no app store, no large download,
  and updates silently. For practice-based learning on patchy networks, *read-
  tolerance* (re-open and read a loaded assignment offline) captures most of the
  value of a native offline app at a fraction of the cost.
- **Improvement over a naive offline cache:** we deliberately split concerns — the
  service worker owns the static app shell, the persisted React Query cache owns API
  reads, and writes/auth stay NetworkOnly. This avoids the classic PWA failure of a
  service worker silently serving stale API JSON.
