## A. Today's objective

Batch 1 (OACT-1..5) shipped the standalone `k8s/monitoring/` stack and it is now
**actually being wired live** — two follow-up commits landed after the Batch 1
close-out: `#493` exempted `/metrics/` from the HTTPS redirect so Prometheus can
scrape it, and `#494` exposed Grafana at `https://openshiksha.org/grafana`
(login-gated sub-path). The stack has stopped being a drawer artifact and started
being plugged in. This batch **hardens the now-live stack** on the three axes a
just-deployed monitoring stack fails on first: **silent config drift**, **data
loss on pod restart**, and **stale operator docs** — plus gives the monitoring
stack visibility into **its own** liveness.

Most important outcome: the two **verbatim-copied** artifacts embedded in the
manifests (the ALT-1 alert rules and the MET-5 dashboard) can **no longer
silently drift** from their canonical `docs/ops/` sources — enforced in CI, not
by a code comment asking humans to "keep the two in sync."

## B. Why this matters

- The monitoring stack is the platform's only production alarm system. Its two
  most safety-critical files (`prometheus.yaml`'s `prometheus-rules` ConfigMap and
  `grafana.yaml`'s `grafana-dashboard-overview` ConfigMap) are **byte-copies** of
  `docs/ops/prometheus/openshiksha-alerts.yml` and
  `docs/ops/grafana/openshiksha-overview.json`. The only thing keeping them in
  sync today is a comment (`"keep the two in sync — if you edit the rules, edit
  them there and re-copy here"`). Edit one, forget the other, and CI's
  `alerting-lint` still passes (it lints the `docs/` copy) while the **deployed**
  rules are stale — a classic observability failure where the alarm you think you
  changed didn't change. A parity guard is exactly the pattern this repo already
  trusts (widget-schema vendoring parity, LA i18n key-parity) — apply it here.
- Both Prometheus TSDB and Grafana state are `emptyDir` with a `Recreate`
  strategy. Every pod restart (node reboot, image bump, `kubectl rollout`) **wipes
  all metrics history and any Grafana session/annotation state**. That's fine for
  a first-light apply, but the moment the operator relies on a week of trend data
  it's a data-loss trap. The initiative doc names PVC-backed storage as an
  explicit deferred follow-up — deliver it as an **opt-in overlay** so the light
  default stays light.
- The operator-facing docs already lie: `grafana.yaml`'s header says
  **"NO Ingress — reach it via port-forward"**, but `#494` gave it a real ingress
  route and the Deployment already sets `GF_SERVER_ROOT_URL` +
  `GF_SERVER_SERVE_FROM_SUB_PATH`. An operator reading the header will
  port-forward and miss that it's on the public sub-path. Stale ops docs during a
  live bring-up are how mistakes happen.
- Prometheus scrapes only `backend:8000`. It has **no visibility into its own
  targets** — if Alertmanager is down, no alert fires about Alertmanager. Adding
  self/AM scrape jobs closes the "who watches the watcher" gap for free.

## D. Concrete implementation plan

### OACT-6 — Manifest-vs-docs parity guard *(build first — lowest risk)*

**Problem.** `k8s/monitoring/prometheus.yaml` embeds `openshiksha-alerts.yml`
(the ALT-1 rules) and `k8s/monitoring/grafana.yaml` embeds
`openshiksha-overview.json` (the MET-5 dashboard) as block scalars in ConfigMaps,
each a hand-maintained copy of a canonical file under `docs/ops/`. Nothing
enforces the copy.

**Build.** A backend pytest is the cleanest home (it runs on every PR and the repo
already parses YAML in tests). Create
`backend/openshiksha/apps/core/tests/test_monitoring_manifest_parity.py` (a pure
file-parsing test — no DB, no Django models needed, but living in the test suite
gets it into CI for free):

- Locate the repo root from the test file path (walk up to the dir containing
  `k8s/` and `docs/`).
- **Rules parity:** load `k8s/monitoring/prometheus.yaml` with
  `yaml.safe_load_all`, find the ConfigMap named `prometheus-rules`, pull
  `data["openshiksha-alerts.yml"]`, `yaml.safe_load` it, and assert it **equals**
  `yaml.safe_load(open("docs/ops/prometheus/openshiksha-alerts.yml"))`. Comparing
  parsed structures (dicts/lists) tolerates indentation/quote differences the
  block-scalar embed introduces while still catching any real content drift.
- **Dashboard parity:** same shape — ConfigMap `grafana-dashboard-overview`,
  `data["openshiksha-overview.json"]`, `json.loads` both sides, assert equal.
- Add a third assertion that the embedded copies are **non-empty** and parse (so a
  truncated paste fails loudly).

*(If a pure-Python test proves awkward vs. Django test discovery, the fallback is
a `parity` step in the `alerting-lint` CI job that diffs `yq`-normalized output —
but the pytest is preferred: no new CI binary, runs locally.)*

**Legacy reference.** None — new guard. Mirrors the existing repo parity idioms:
the widget-schema vendoring parity guard (`apps/core/data/widget_schemas/` vs the
frontend source) and the LA i18n key-parity guard.

**Verify.** `pytest backend/openshiksha/apps/core/tests/test_monitoring_manifest_parity.py`;
then deliberately edit one embedded threshold, confirm the test goes red, revert.

**What could go wrong.** The block-scalar embed may carry trailing-whitespace or a
final-newline difference — parsing both sides sidesteps that. If `PyYAML`
round-trips `>-` folded scalars in the alert `description` fields differently,
the *parsed string values* still compare equal (folding is resolved at parse
time), so structural equality holds.

### OACT-7 — Reconcile the stale Grafana access docs

**Problem.** `k8s/monitoring/grafana.yaml` lines 1–15 still say **"NO Ingress —
reach it via `kubectl port-forward`"** and "Keeping Grafana off the public
internet avoids a new attack surface," but `#494` added
`k8s/overlays/prod/ingress-patch.yaml` `/grafana` → `grafana` Service and the
Deployment sets `GF_SERVER_ROOT_URL=https://openshiksha.org/grafana` +
`GF_SERVER_SERVE_FROM_SUB_PATH=true`. The header now contradicts the manifest it
heads.

**Build.**
- Rewrite the `grafana.yaml` header comment to state the real access model:
  login-gated at `https://openshiksha.org/grafana` via the **prod-overlay**
  ingress route (`k8s/overlays/prod/ingress-patch.yaml`), while the `grafana`
  **Service itself** only exists once the operator applies `k8s/monitoring` — so
  `/grafana` returns 503 until then (this exact caveat is already in the ingress
  patch comment; mirror it). Keep the `port-forward` line as the **fallback**
  access path, not the primary.
- Update `docs/ops/monitoring-deploy.md`: the "how do I reach Grafana" section and
  the end-to-end checklist should lead with the sub-path URL + the
  `GRAFANA_ADMIN_PASSWORD` login, and note the 503-until-applied ordering between
  the auto-deploying ingress route and the operator-applied Service.

**Legacy reference.** None — doc reconciliation.

**Verify.** Re-read both files; grep for "port-forward" and "NO Ingress" to
confirm no stale primary-access claim remains. No code, no CI risk.

**What could go wrong.** Nothing runtime. Only risk is under-describing the 503
ordering — call it out explicitly.

### OACT-8 — Self-scrape the monitoring stack

**Problem.** `prometheus.yml` has a single scrape job (`openshiksha-backend`). If
Prometheus can't reach Alertmanager, or Prometheus itself is degraded, there is no
`up{}` series to alert on — the monitoring stack is blind to its own health.

**Build.**
- In the `prometheus-config` ConfigMap's `scrape_configs`, add two additive jobs:
  - `job_name: prometheus`, `static_configs: [{ targets: ["localhost:9090"] }]`
    (Prometheus's own `/metrics`).
  - `job_name: alertmanager`, `static_configs: [{ targets: ["alertmanager:9093"] }]`.
- Add one alert rule to the **canonical** `docs/ops/prometheus/openshiksha-alerts.yml`
  (and its test file `openshiksha-alerts.test.yml` if it has cases), then re-copy
  into the `prometheus-rules` ConfigMap in `prometheus.yaml`:
  - `MonitoringTargetDown`: `up{job=~"prometheus|alertmanager"} == 0` `for: 10m`,
    `severity: warning`, summary "A monitoring-stack target is down."
- Because OACT-6 now guards the copy, the manifest edit and the `docs/` edit must
  match — the parity test enforces it.

**Legacy reference.** None. Standard Prometheus self-monitoring.

**Verify.** `promtool check config` / `promtool check rules` on the `docs/` source
(the existing `alerting-lint` job already runs these); the OACT-6 parity test
confirms the manifest copy matches; the monitoring kustomize+kubeconform CI step
still renders clean (ConfigMap data is opaque to kubeconform, so no schema risk).

**What could go wrong.** These targets only resolve once the stack is applied
(they're in-cluster Service/localhost names) — that's fine, `up==0` is precisely
the signal we want pre-apply/on-failure, gated `for: 10m` to avoid boot-time
flaps. Don't scrape Grafana's `/metrics` (needs auth/flag) — skip it.

### OACT-9 — Opt-in persistent-storage overlay

**Problem.** Base manifests use `emptyDir` for both Prometheus `/prometheus` (TSDB,
7d retention arg) and Grafana `/var/lib/grafana`. `strategy: Recreate` + a pod
restart = **all history gone**. The initiative doc lists PVC-backed storage as an
explicit deferred follow-up: *"an operator who wants retention across pod restarts
swaps in a PVC."* Deliver that swap as a ready overlay.

**Build.** New `k8s/monitoring/overlays/persistent/`:
- `kustomization.yaml` with `resources: [../../]`? — no; use `resources` pointing
  at the base (`bases`/`resources: - ../..` per kustomize v5) plus:
  - Two `PersistentVolumeClaim` resources: `prometheus-tsdb` and `grafana-data`
    (e.g. `8Gi` and `2Gi`, `accessModes: [ReadWriteOnce]`, no explicit
    `storageClassName` so k3s's default `local-path` binds — document that a
    non-k3s operator sets their class).
  - A **strategic-merge patch** on the `prometheus` Deployment replacing the
    `tsdb` volume `emptyDir: {}` with `persistentVolumeClaim: { claimName:
    prometheus-tsdb }`, and the same for the `grafana` Deployment's `grafana-data`
    volume → `claimName: grafana-data`.
- Base `k8s/monitoring/` stays `emptyDir` (light default). Operators who want
  retention run `kubectl apply -k k8s/monitoring/overlays/persistent` **instead
  of** `k8s/monitoring`.
- Extend the CI monitoring step (`ci-cd.yaml` ~L91) to **also** render+validate the
  new overlay through kustomize+kubeconform, so both variants are gated.
- Document the choice in `docs/ops/monitoring-deploy.md` (ephemeral vs persistent,
  when to pick which, storageClass note).

**Legacy reference.** None. Standard kustomize base+overlay + PVC.

**Verify.** `kubectl kustomize k8s/monitoring/overlays/persistent | kubeconform
-strict -summary -ignore-missing-schemas`; confirm the rendered Prometheus/Grafana
Deployments reference the PVCs and the base still renders `emptyDir`.

**What could go wrong.** A strategic-merge volume patch must match the volume
`name` exactly (`tsdb`, `grafana-data`) or kustomize appends instead of replacing —
render and grep to confirm exactly one volume entry each. `ReadWriteOnce` + the
`Recreate` strategy is correct for a single-node droplet (no two pods contend).
Don't touch the base's `retention.time=7d` arg — persistence + 7d is the intended
combination; leave retention tuning to the operator.

## F. Legacy analysis & improvement opportunities

Not a port — this is operational hardening of net-new modern infra. The
"improvement over legacy" lens still applies: the Django 1.11 monolith had **no
metrics, no alerting, no dashboards, no backup automation** — operability was
tribal knowledge. This batch takes the modern stack from "deployed" to
"trustworthy under change": drift-guarded (you can't silently ship a stale alarm),
restart-durable (history survives), self-observing (the watcher is watched), and
honestly documented (the runbook matches reality). Each is a property the legacy
system never had at any maturity.
