# OpenShiksha Daily Plan — 2026-05-25

> **Context**: Yesterday shipped three PRs (#88/#89/#90): migration dedup (0006 conflict fixed, 0007 now linear), Streak Phase 2 (grace day mechanic + milestone badge tiers: starter/week/month/champion), and Email Notifications Phase 1 (console backend in dev, `emails.py` helpers, remedial + grading triggers). The platform is now functionally complete for the admin-managed flow — but there is no self-service onboarding. Every student, teacher, and parent account must be created via Django admin. This is the next critical gap to close.

---

## A. Today's Objective

Build self-service onboarding: student and open-student self-registration, a classroom join-by-code flow for school students, and an open-student subject browse interface — so the platform can be used without a superuser creating every account.

---

## B. Why This Matters

- **The platform is currently unusable for new schools without an admin**: Teachers can't onboard students, students can't register themselves, and open students have no entry point. Every account requires Django admin access. This is fine for development but blocks real-world usage.

- **Open students are a growth lever**: Legacy OpenShiksha served a significant number of `open_student` users (students studying independently, outside of school). These users can access the shared question bank and practice freely. The modern platform has the `open_student` role, the SRS engine, and the proficiency tracker — but no registration or browse interface. Enabling this unlocks the platform for self-directed learners.

- **Email notifications are wired but students have no email set**: The grading and remedial emails implemented yesterday depend on `student.email` being non-empty. But there's no way for a student to set their email except through Django admin. A profile settings page closes this loop.

- **Classroom join codes are the industry-standard K-12 enrollment model**: Google Classroom, Remind, Kahoot, Quizlet all use teacher-generated join codes. A teacher shares a 6-character code → students enter it at registration → they're enrolled. This eliminates the need for a school admin to manually create and link every student account.

### Priority 1: Student Self-Registration + Classroom Join Code

**PR target**: `feat/2026-05-25-registration-join-flow`

**Classification**: New — no equivalent existed in legacy (all accounts were admin-created)

#### 1a. ClassroomInviteCode Model

**File**: `backend/openshiksha/apps/core/models.py`

```python
import secrets

class ClassroomInviteCode(models.Model):
    """
    A short join code generated by a teacher for their classroom.
    Students use it at registration to enroll automatically.
    """
    classroom = models.OneToOneField(
        ClassRoom,
        on_delete=models.CASCADE,
        related_name="invite_code",
    )
    code = models.CharField(
        max_length=8,
        unique=True,
        db_index=True,
        help_text="6–8 character alphanumeric code (e.g. 'ABC123')",
    )
    created_by = models.ForeignKey(
        "User",
        on_delete=models.CASCADE,
        limit_choices_to={"role": UserRole.TEACHER},
    )
    is_active = models.BooleanField(default=True)
    expires_at = models.DateTimeField(null=True, blank=True)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        db_table = "classroom_invite_codes"

    def __str__(self):
        return f"{self.code} → {self.classroom}"

    @classmethod
    def generate_code(cls) -> str:
        """Generate a unique 6-char uppercase alphanumeric code."""
        while True:
            candidate = secrets.token_urlsafe(4).upper()[:6]
            if not cls.objects.filter(code=candidate).exists():
                return candidate
```

**Migration**: `makemigrations core --name="add_classroom_invite_code"`

**Design**: `OneToOneField` on `ClassRoom` means one active code per classroom. Teachers can regenerate (deactivate old, create new). `expires_at=None` means no expiry (school year duration).

#### 1b. Registration API Endpoint

**File**: `backend/openshiksha/apps/api/views/auth.py` (new file)

Two distinct registration paths:

**Path A — Open Student Registration** (no code needed):
- `POST /api/v1/auth/register/open/`
- Body: `{username, password, email, first_name, last_name}`
- Creates `User(role="open_student")` — no school, no classroom

**Path B — School Student Registration** (requires join code):
- `POST /api/v1/auth/register/school/`
- Body: `{username, password, email, first_name, last_name, join_code}`
- Looks up `ClassroomInviteCode(code=join_code, is_active=True)`
- Creates `User(role="student", school=classroom.school)`
- Adds student to `classroom.students` and creates `SubjectRoom.students` membership for all active SubjectRooms in that classroom

This second step (auto-enrolling in SubjectRooms) is critical — legacy required a separate admin step. We do it atomically at registration.

```python
# Pseudocode for the school registration action
with transaction.atomic():
    invite = get_object_or_404(ClassroomInviteCode, code=join_code, is_active=True)
    classroom = invite.classroom
    user = User.objects.create_user(
        username=username,
        password=password,
        email=email,
        first_name=first_name,
        last_name=last_name,
        role=UserRole.STUDENT,
        school=classroom.school,
    )
    classroom.students.add(user)
    for subject_room in classroom.subject_rooms.filter(is_active=True):
        subject_room.students.add(user)
```

Both endpoints return a JWT token pair on success (same as login) so the user is immediately authenticated.

**Validation**:
- Username uniqueness (Django default)
- Password strength: minimum 8 chars (Django validators)
- Email uniqueness: optional but log a warning if email already exists
- Join code validity: 404 if not found, 400 if expired/inactive

#### 1c. Teacher — Generate / View Join Code Endpoint

**Add to `UserViewSet`** in `views/core.py`:

```python
@action(
    detail=False,
    methods=["get", "post"],
    url_path="me/classroom-code",
    permission_classes=[IsTeacher],
)
def classroom_code(self, request):
    """
    GET  — returns the teacher's classroom join code (or 404 if not set)
    POST — generates a new code for the specified classroom
    """
    if request.method == "GET":
        # Return all codes for classrooms taught by this teacher
        codes = ClassroomInviteCode.objects.filter(
            classroom__class_teacher=request.user, is_active=True
        ).select_related("classroom")
        return Response(ClassroomInviteCodeSerializer(codes, many=True).data)

    # POST: generate code for a specific classroom
    classroom_id = request.data.get("classroom_id")
    classroom = get_object_or_404(ClassRoom, id=classroom_id, class_teacher=request.user)
    # Deactivate existing code if any
    ClassroomInviteCode.objects.filter(classroom=classroom).update(is_active=False)
    code = ClassroomInviteCode.objects.create(
        classroom=classroom,
        code=ClassroomInviteCode.generate_code(),
        created_by=request.user,
    )
    return Response(ClassroomInviteCodeSerializer(code).data, status=201)
```

#### What Could Go Wrong

- **Race condition in code generation**: `generate_code()` loops until unique. With low collision probability (36^6 = 2.2 billion codes), safe for any school-scale usage.
- **Student enrolled in wrong classroom**: Join code is per-classroom, one-to-one. Teachers control code sharing — if a code is shared incorrectly, "Regenerate" revokes it immediately.
- **Auto-SubjectRoom enrollment**: If a classroom has no SubjectRooms yet (new classroom), the student is enrolled in the classroom but has no SubjectRooms. Their dashboard will show no assignments — correct behavior (teacher creates SubjectRooms after students join).
- **Password sent in plaintext during registration**: Use HTTPS in production (standard Django config). Dev is HTTP but behind localhost only.

#### 2a. Backend — Browse by Chapter Endpoint

**Add to `QuestionViewSet`** (or new `BrowseViewSet`):

```python
@action(detail=False, methods=["get"], url_path="chapters/browse", permission_classes=[permissions.IsAuthenticated])
def browse_chapters(self, request):
    """
    GET /api/v1/questions/browse/
    Returns chapters from the shared question bank with question counts.
    Filtered by ?subject=<id> and/or ?standard=<id>.
    """
    from django.db.models import Count

    qs = Chapter.objects.annotate(
        question_count=Count("questions", filter=Q(questions__school__isnull=True, questions__is_active=True))
    ).filter(question_count__gt=0).select_related("subject", "standard")

    if subject := request.query_params.get("subject"):
        qs = qs.filter(subject_id=subject)
    if standard := request.query_params.get("standard"):
        qs = qs.filter(standard_id=standard)

    data = [
        {
            "id": ch.id,
            "name": ch.name,
            "subject": ch.subject.name,
            "standard": ch.standard.number,
            "question_count": ch.question_count,
        }
        for ch in qs
    ]
    return Response(data)
```

This endpoint is available to all authenticated users (students, open students, teachers). It's a read-only browse.

```python
@action(detail=False, methods=["patch"], url_path="me/profile")
def update_profile(self, request):
    """PATCH /api/v1/users/me/profile/ — update own profile fields."""
    ALLOWED_FIELDS = {"first_name", "last_name", "email", "phone_number"}
    data = {k: v for k, v in request.data.items() if k in ALLOWED_FIELDS}
    serializer = UserProfileUpdateSerializer(request.user, data=data, partial=True)
    serializer.is_valid(raise_exception=True)
    serializer.save()
    return Response(UserSerializer(request.user).data)
```

**New serializer** `UserProfileUpdateSerializer`:
```python
class UserProfileUpdateSerializer(serializers.ModelSerializer):
    class Meta:
```

## F. Legacy Analysis & Improvement Opportunities

### Registration (Priority 1)

**Legacy**: User creation was entirely admin-driven. Schools would request accounts via email/phone; the OpenShiksha team would manually create them. This worked when OpenShiksha had a small number of partner schools with a dedicated account manager. It doesn't scale and isn't appropriate for a revival aimed at broader adoption.

**Modern improvement**: Teacher-generated join codes are the standard K-12 model post-2015 (Google Classroom 2014, Kahoot 2016, Quizlet 2018 all adopted this). Key improvements over legacy:
- **Self-service**: No OpenShiksha team involvement needed for school onboarding
- **Instant**: Student registers → immediately in class → sees assignments
- **Revocable**: Teacher regenerates code, old code stops working
- **Auditable**: `ClassroomInviteCode.created_by` tracks who generated it

### Open Student Browse (Priority 2)

**Legacy**: The legacy open student flow was driven by the Sphinx authoring interface — the same UI that created questions also browsed them. Open students could navigate by board → standard → subject → chapter and see available problem sets. The browse was deeply coupled to Cabinet (question content was on Cabinet, not in the DB), which meant any offline access was impossible.

**Modern improvement**: Since question content is now in the Django DB directly, browse + practice works without any external service. The browse endpoint is a simple annotated queryset — no Cabinet call needed. Open students get true offline-capable practice (if the app is hosted locally or cached).

**Product opportunity**: Open students as a marketing channel. A student who practices independently and gets value from the platform is a future customer when they join a school that uses OpenShiksha. The open student flow is acquisition + retention for future school accounts.

### Profile Settings (Priority 3)

**Legacy**: No profile editing existed for students or teachers. Email addresses were set by admins; phone numbers were used only for SMS notifications (Pylon integration). There was no concept of user-managed preferences.

**Modern improvement**: Students controlling their own contact info closes the notification loop without admin intervention. Future: add notification preferences (email digest vs. instant, weekly reports, etc.) as additional settings fields without changing the profile page structure.
