## B. Why this matters

The brand shell, login, and home page already speak V2 — but the moment a user
logs in, they land on a **Student/Teacher dashboard still painted in legacy
`indigo-600` / `bg-gray-50`** (confirmed: `StudentDashboard.tsx` uses
`text-gray-900`, `text-indigo-600`, `bg-indigo-50` for its empty state). That
visual whiplash — warm paper login → cold blue dashboard — is exactly the
"generic template" feel V2 exists to kill, and it hits on the most-viewed screen
in the app. To migrate those surfaces cleanly (and the rest of M4 after them) we
need the foundation primitives the backlog still lists as unbuilt: `Input`,
`Stat`, `SectionHeading`, `EmptyState`. Building those first turns each later
page migration from "hand-roll warm styles again" into "compose existing `ui/`
parts," which is the whole point of a design system. The global-states PR removes
the last unbranded full-screen moments (spinner / 404 / crash) that any route can
hit.

## D. Concrete implementation plan

### PR 1 — M1-06 — finish `ui/` foundation primitives  *(New)*

**Files to create** (`frontend_modern/src/shared/ui/`):
- `Input.tsx` — text input + optional `label`, `hint`, `error`, `leftIcon`.
  Reuse the existing `.input-brand` CSS class (already in `index.css`) for the
  base; add `aria-invalid`, `aria-describedby` wiring, focus-visible ring,
  `disabled` state. Forward `ref`. Export a matching `Textarea` and `Select`
  with the same chrome if cheap; otherwise just `Input` + `Textarea`.
- `Stat.tsx` — a labelled metric block: big `font-display` value (`text-3xl`),
  `text-sm text-ink-400` label above, optional `delta`/trend slot and optional
  `tone` (uses `Badge` semantics). For dashboard headline numbers.
- `SectionHeading.tsx` — `font-display` section title + optional `eyebrow`,
  `description`, and a right-aligned `action` slot (e.g. a "View all" link).
  Renders a semantic `<h2>` by default with an `as` prop.
- `EmptyState.tsx` — keyhole-motif empty state: `<Logo>` mark or a keyhole glyph,
  `font-display` headline, muted body, optional primary `action` (a `Button`).
  This is the canonical "nothing here yet" surface for lists/dashboards.

**Wiring:**
- Export all from `src/shared/ui/index.ts`.
- Add a labelled section per primitive to
  `features/design/DesignSystemPage.tsx` (every state: Input default/error/
  disabled; Stat with/without delta; SectionHeading with/without action;
  EmptyState with/without action). The `/design` route is how we prevent drift —
  **every new primitive must appear there** (initiative DoD).
- Follow `src/shared/ui/README.md` conventions (tokens only, `clsx`, forwardRef,
  typed props extending the native element).

**Verify:** `npm run type-check && npm run lint && npm run build && npm test`;
open `/design` and confirm each variant renders with brand tokens (no raw hex,
no `primary`/`indigo`). Add a render-smoke test (`*.test.tsx`) for each new
primitive mirroring the existing `RichContent.test.tsx` style.

**What could go wrong:** fast-refresh "component-only exports" rule — keep any
non-component helper in a separate `.ts` file (the M7-01 ledger note documents
this exact gotcha). Don't break the `index.ts` barrel ordering.

## F. Legacy analysis & improvement opportunities

The legacy Django app had **no design system** — each template hand-rolled
Bootstrap-ish markup, and the modern app inherited that ethos as ad-hoc
indigo/gray Tailwind. What legacy got *right* was a clear blackboard/chalk brand
heritage (the orange keyhole cap, the blackboard hero) — V2 deliberately revives
that as `.bg-chalkboard` + the keyhole motif. What it got *wrong* was visual
inconsistency screen-to-screen and zero reusable components. This batch attacks
both: the primitives (PR 1) make consistency cheap, and migrating the
highest-traffic surfaces (PR 3/4/5) replaces the worst offenders first. The
improvement over both legacy *and* the current modern app is a single
token-driven language a new contributor can compose in minutes (the initiative's
"Done looks like").
