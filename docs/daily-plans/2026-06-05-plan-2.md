## A. Today's objective

**Land the backend foundation of the Widgets Framework (IW-3) and stack the
first real widget (IW-2) + the scaffolder DX win (IW-8) on top of IW-1.** After
this batch the data model can carry a widget by `kind` + `config`, the legacy
thermo question has a one-shot migration path off raw HTML, the `TeacherWidget`
table that the Tier-2 Studio (IW-9/10) needs already exists, and a contributor
can scaffold a new widget with one command.

## B. Why this matters

The initiative's North Star is *three tiers of authoring, one runtime*. IW-1
(plan 1) lays the **render contract**; this batch lays the **data + authoring**
contract underneath and beside it:

1. **IW-3 (backend) is the keystone.** Until `QuestionSubpart` can store
   `widget_kind` + `widget_config`, every frontend widget is a showcase toy
   with nowhere to live. Shipping it now — independently of IW-1 — means the
   moment IW-1 + IW-2 land, real questions can carry real widgets.
2. **It de-risks the critical path.** Three of five PRs here are backend-only
   and don't touch the unshipped IW-1 runtime, so the batch compounds even if
   IW-1 slips.
3. **DX compounds early.** The backlog explicitly says ship `npm run
   widget:new` *right after IW-2* so every later widget (number-line,
   function-plotter, fraction-bar) is cheaper to build. We seed that here.
4. **The Studio table is cheap now, expensive later.** Adding the
   `TeacherWidget` model as a quiet model-only migration today means IW-9/IW-10
   start from "wire the endpoints + UI", not "design the schema".

## D. Concrete implementation plan

### PR 1 — IW-3a · backend data model (New, independent)

- **`backend/openshiksha/apps/core/models.py`** — on `QuestionSubpart`, add:
  - `widget_kind = models.CharField(max_length=64, blank=True, default="",
    help_text="Registry key of an interactive widget (e.g. 'thermo-piston'). "
    "Blank = no widget. The kind-based path supersedes the legacy "
    "interactive_html escape hatch.")`
  - `widget_config = models.JSONField(default=dict, blank=True,
    help_text="Per-widget config validated against the kind's params schema. "
    "May contain {{var}} tokens substituted per student.")`
- **`backend/openshiksha/apps/core/widgets.py`** (new) — the server-side source
  of truth for known kinds: `KNOWN_WIDGET_KINDS = {"thermo-piston",
  "number-line", "function-plotter", "fraction-bar", "studio-scene",
  "custom-html"}` plus a tiny `validate_widget_config(kind, config)` that, for
  now, just (a) rejects an unknown `widget_kind`, (b) requires `widget_config`
  to be a dict. Per-kind JSON-Schema validation lands with each widget in
  IW-2/IW-4/IW-6; this file is where that registry of schemas will hang. Use
  **pydantic** (already in `requirements.txt`, v2.10.5) if a structured
  validator is convenient — but a plain dict guard is acceptable for IW-3a.
- **Migration** — `makemigrations core`; both fields are additive + nullable/
  defaulted, so it is a zero-downtime add.
- **`apps/core/admin.py`** — surface `widget_kind` in the `QuestionSubpart`
  inline/admin (readonly JSON for `widget_config` is fine).
- **`apps/api/serializers/core.py`** — expose `widget_kind` + `widget_config`
  on **both** the teacher and student subpart serializers. On **write**
  (teacher), call `validate_widget_config` in `validate()` and raise
  `serializers.ValidationError` with a clear message on an unknown kind.
- **Legacy reference:** none — the modern DB-as-source-of-truth model has no
  legacy analogue (legacy stored everything in Cabinet). This is pure *New*.
- **Test:** `apps/core/tests/test_widget_fields.py` — round-trips a subpart
  with `widget_kind="thermo-piston"` + a config; asserts the API returns both
  fields; asserts an unknown kind is rejected `400`; asserts a non-dict config
  is rejected.
- **What could go wrong:** a serializer that over-eagerly validates blank kinds
  — guard with `if not widget_kind: return`. Keep `is_interactive` /
  `interactive_html` (M7-11) **untouched** — the legacy path must stay green.

### PR 2 — IW-3b · legacy-thermo migration + per-student substitution (New, dep PR 1)

- **`apps/core/management/commands/migrate_legacy_thermo_widget.py`** (new) —
  finds the thermo subpart (the one with `is_interactive=True` /
  non-empty `interactive_html`, or matched by question identity
  `1/1/11/3/44/22`) and sets `widget_kind="thermo-piston"` +
  `widget_config={...}` derived from the known initial-volume / max-heat
  constants. **Idempotent** (`--dry-run` flag; safe to re-run). It does **not**
  delete `interactive_html` — IW-7 deprecates that field; this command only
  *adds* the kind-based path so both render identically once IW-2 ships.
- **Student serializer** (`apps/api/serializers/core.py`) — extend the existing
  per-student `{{var}}` substitution (the one already applied to
  `question_text` / `options` via the croupier seed) to **also** walk
  `widget_config` and substitute tokens in string leaves. Reuse the existing
  substitution helper — do **not** introduce a second code path. The host
  (IW-1) then posts the already-substituted config into the sandbox `init`.
- **Test:** `test_widget_fields.py` (extend) — a `widget_config` with
  `{"initialVolume": "{{a}}"}` and a seeded variable returns the substituted
  numeric value for a given student; the migration command sets the expected
  kind+config on the thermo subpart (use a fixture row).
- **What could go wrong:** double-substitution or substituting non-string leaves
  — only touch `str` values; leave numbers/bools/nested dicts walked
  recursively. Confirm the croupier seed is deterministic per
  `(student_id, subpart_id)` as elsewhere.

### PR 3 — IW-9-backend · `TeacherWidget` model scaffold (New, independent)

> The **model-only** slice of IW-9. Endpoints + serializer + scene-schema
> validation stay in IW-9 proper (after IW-3 + IW-1). Shipping the table now is
> a cheap, low-risk migration that unblocks the Studio later.

- **`apps/core/models.py`** — new `TeacherWidget`:
  `name` (CharField), `description` (TextField, blank), `school` (FK → School,
  `null=True` for personal), `created_by` (FK → User), `visibility`
  (CharField choices `personal` / `school` / `pending_review`, default
  `personal`), `scene_version` (PositiveIntegerField, default 1), `scene`
  (JSONField, default dict), `created_at` / `updated_at`. `__str__` →
  `f"{self.name} ({self.visibility})"`.
- **Migration** + **`admin.py`** registration (list_display: name, school,
  visibility, created_by, updated_at).
- **No endpoints, no serializer** this PR — explicitly note in the PR body that
  `GET/POST/PATCH /teacher-widgets/` come in IW-9 to keep this slice trivial.
- **Test:** `apps/core/tests/test_teacher_widget_model.py` — create + `__str__`
  + default visibility `personal`; school-null personal widget allowed.
- **Legacy reference:** none — Tier-2 teacher authoring is net-*New*; legacy had
  no teacher-composed interactive content at all.
- **What could go wrong:** nothing functional (no API surface). Keep the
  `school` FK nullable so personal widgets don't require a school.

### PR 4 — IW-2 · `defineWidget()` + `thermo-piston` (Improve/Port, **gated on IW-1**)

> **Do not start until IW-1 (plan 1) is merged** — needs `_sdk/host.ts`,
> `_sdk/runtime.ts`, and `registry.ts`.

- **`frontend_modern/src/widgets/_sdk/defineWidget.ts`** (new) — the factory:
  `defineWidget<TConfig, TAnswer>({ id, version, meta, schema, render }):
  WidgetModule`. `meta` = `{ title, description, kind, answerProducing }`.
  `render(ctx)` receives the SDK hooks (`useVariables`, `reportValue`,
  `requestResize`) from IW-1's runtime.
- **`frontend_modern/src/widgets/thermo-piston/`** —
  - `index.tsx` — the legacy Class-11 thermodynamics piston/First-Law sim
    re-implemented as a **React** component using SDK hooks. **No jQuery, no
    bespoke `<script>`.** Slider drives piston position; ΔU / Q / W readouts
    update; values substitute through `useVariables`. *Explanatory* widget
    (no `reportValue`).
  - `params.schema.json` — `initialVolume`, `maxHeat`, etc. (JSON Schema).
  - `README.md` — "anatomy of a widget" excerpt born from this PR.
- **`registry.ts`** — register `thermo-piston`.
- **Showcase** — extend the `/design` "Interactive Widgets" section (added by
  IW-1c) to render `thermo-piston` beside the hello-widget.
- **Legacy reference:** `openshiksha-cabinet/questions/raw/1/1/11/3/44/22.json`
  — preserve the *physics and the visual layout*; **change** the *delivery*
  (React + SDK, not raw HTML + jQuery). The data flip (pointing the real
  question at the registry) is **IW-3** territory — PR 2's migration command +
  the IW-3 fields make it possible, but IW-2 only proves the widget renders in
  the showcase.
- **Test:** vitest render test (slider → readout updates; variable
  substitution); the showcase route mounts it in the sandbox.
- **What could go wrong:** porting the physics math 1:1 from the legacy inline
  JS — keep the formulae identical; this is a *skin swap*, not a redesign.
  Keep bundle impact small (React-only; no chart lib needed for the piston).

### PR 5 — IW-8-early · scaffolder + playground + anatomy doc (New, **gated on IW-1 + PR 4**)

> The DX win the backlog says to ship right after IW-2 so later widgets are

  hello-widget (IW-1) as examples. (`build-your-first-widget.md` — the full
  10-min tutorial — is IW-8 proper; this PR ships the reference half.)
- **Test:** running `node scripts/create-widget.mjs color-picker` on a clean
  tree produces a compiling widget registered in `registry.ts` (manual + a
  smoke assertion that the four files exist). `npm run type-check` / `build`

- **What could go wrong:** the scaffolder's registry edit is brittle if it

## F. Legacy analysis & improvement opportunities

- **Thermo sim (the *one* legacy widget).** *Legacy did:* bespoke raw HTML +
  SVG + inline jQuery embedded in question content — insecure, unreusable,
  unauthorable. *Good:* the physics model + the piston visualisation were
  genuinely useful. *Limited:* one-off; DOMPurify silently strips its
  `<script>` in the modern renderer. *Improve:* IW-2 re-expresses it as a
  React widget over the SDK; IW-3 gives it a typed home in the DB; the M7-11
  sandbox keeps the raw-HTML path alive only as a deprecated escape hatch.
- **Teacher-authored interactivity.** *Legacy did:* nothing — only repo
  contributors could hand-write a widget. *Improve:* the `TeacherWidget` table
  (PR 3) is the first brick of Tier-2 *Compose*, letting any teacher build a
  widget with no code (IW-9/10).
