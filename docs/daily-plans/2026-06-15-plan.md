## A. Today's objective

**Make the student core loop write-tolerant offline: a student on a dropped
connection can keep answering, auto-saves and final submit are queued durably, and
they replay automatically — exactly once, without double-grading — when the network
returns.** Batch 1 made offline *reading* work; Batch 2 closes the loop so offline
*work is never lost*.

## B. Why this matters

Today (verified 2026-06-15) the assignment page's auto-save and submit are plain
React Query `useMutation` calls (`patchSubmission`, `createSubmission` in
[AssignmentDetailPage.tsx](../../frontend_modern/src/features/student/AssignmentDetailPage.tsx)).
When the network is down these mutations **fail silently or error** — the debounced
2 s auto-save throws, and a student who finishes an assignment underground on a
train, in a low-signal classroom, or on patchy rural 3G **loses their answers or
cannot submit at all**. Batch 1 ensures they can *read* the questions offline; it is
a cruel half-measure if the answers they then type evaporate.

This is the named, highest-leverage next increment of the current top initiative and
it completes the North Star's spirit ("the student core loop survives a flaky or
absent connection") — Batch 1 covered read-tolerance; write-tolerance is the other
half. It also **compounds directly** on Batch 1's foundation: the
`PersistQueryClientProvider` + `idb-keyval` persister
([main.tsx](../../frontend_modern/src/main.tsx),
[shared/query/persist.ts](../../frontend_modern/src/shared/query/persist.ts)) is
already mounted and currently sets `shouldDehydrateMutation: () => false` — Batch 2
turns that knob on for an allowlist of replay-safe mutations and adds
`onlineManager`-driven `resumePausedMutations()`. React Query has **first-class
offline-mutation support** (`networkMode: 'offlineFirst'`, paused mutations, mutation
persistence), so we are wiring existing primitives, not inventing a queue.

The one real risk — replaying a write twice, or replaying an auto-save after a submit
and **re-triggering grading** — is handled first, server-side, in MSO-6 (lowest-risk,
backend-only) before any client queue exists.

## D. Concrete implementation plan

### PR 1 — MSO-6: Replay-safe / idempotent submission writes (Improve) — *build first*

**The bug this prevents.** The grading trigger is a `post_save` signal
([core/signals.py](../../backend/openshiksha/apps/core/signals.py#L13)):
`grade_submission.delay()` fires whenever `submitted_at` is non-null **and**
(`update_fields is None` **or** `'submitted_at' in update_fields`). DRF's
`ModelSerializer.update()` calls `instance.save()` **without** `update_fields`, so
`update_fields is None` on every PATCH. That means **any PATCH to an
already-submitted submission re-fires grading** — including a stale offline auto-save
replayed after the student already submitted. The frontend currently hides this by
blocking edits post-submit (`if (isSubmitted) return` in `handleAnswerChange`), but
an offline replay queue removes that guarantee. Fix it server-side, once.

- **Serializer guard** in `SubmissionSerializer.validate()`
  ([serializers/core.py:861](../../backend/openshiksha/apps/api/serializers/core.py#L861)):
  if `self.instance` is already submitted (`self.instance.submitted_at is not None`):
  - If the incoming payload would set `submitted_at` again (re-submit): **do not
    error** — make it a no-op success. Drop `submitted_at` (and `answers`/`completion`
    if present) from `attrs` so the update is idempotent and returns the existing
    record + score with HTTP 200. (A queued offline submit that the student also
    managed to submit online must not 400 on replay.)
  - If the payload is a plain answers/`completion` auto-save after submission: strip
    those fields too (post-submission answers are immutable — the graded snapshot is
    already pinned by Authoring Integrity's `ProblemSetVersion`). Net: a replayed
    stale auto-save becomes a harmless no-op, never a re-grade.
- **Signal hardening** (defense in depth, independent of the serializer): in
  `trigger_grading_on_submit`, only queue grading when the submission **transitions**
  into submitted. Simplest robust approach: track the prior state. Since `post_save`
  lacks the old value, gate on `score is None` for the grade trigger —
  `grade_submission` should only run when `submitted_at` is set **and** `score is
  None` (ungraded). A re-save of an already-graded submission (`score` populated) then
  never re-grades. Keep the existing `update_fields` guard as the first filter. (The
  resync re-grade path at [views/core.py:1093](../../backend/openshiksha/apps/api/views/core.py#L1093)
  deletes ticks + nulls score *before* re-queuing, so it still works — it explicitly
  resets `score`.)
- **Verify (pytest):** add `test_submission_replay.py`:
  (a) PATCH `submitted_at` once → graded once (assert `grade_submission.delay` called
  once via mock); (b) PATCH `submitted_at` again → **no** second grade call, response
  is 200 with the same score; (c) PATCH `answers` after submission → 200, answers
  unchanged, **no** grade call; (d) the normal first-submit path is unchanged. Run the
  existing `test_assignment_api.py` submission suite to confirm no regression.
- **What could go wrong:** the resync re-grade path must still work — it nulls
  `score` before re-queuing, so the `score is None` gate is satisfied; assert this in
  a test that re-runs an existing resync test. Don't change list/read behavior — the
  guard is write-path only.

### PR 2 — MSO-7: Offline mutation queue foundation (New)

- **Keyed mutation defaults.** In `main.tsx` (or a new
  `src/shared/query/offlineMutations.ts` imported there), register
  `queryClient.setMutationDefaults(['submission', 'patch'], { mutationFn, networkMode:
  'offlineFirst', retry: 3 })` and likewise for `['submission', 'create']`. The
  `mutationFn` calls the same `api` submission endpoints used today. Move the actual
  fetch out of the component hook into these defaults so a **rehydrated** paused
  mutation (which has no closure) can still execute its `mutationFn` after a reload.
- **Use keyed mutations in the component.** In `AssignmentDetailPage`, change
  `patchSubmission`/`createSubmission` to `useMutation({ mutationKey: ['submission',
  'patch'] })` etc. (no inline `mutationFn` — it comes from the defaults). Behavior
  online is unchanged; offline, the mutation **pauses** instead of failing.
- **Persist paused mutations.** In `shared/query/persist.ts`, flip
  `shouldDehydrateMutation` from `() => false` to an **allowlist**: dehydrate a
  mutation only when it is **paused** and its `mutationKey[0] === 'submission'`. Never
  persist auth or any token-bearing mutation. (Reads dehydrate allowlist from MSO-4
  is untouched.)
- **Resume on reconnect.** Wire the `PersistQueryClientProvider`'s `onSuccess`
  (fires after the cache restores on boot) to call
  `queryClient.resumePausedMutations()`, and add an `onlineManager.subscribe` (or rely
  on React Query's built-in auto-resume on `online`) so queued mutations flush when
  connectivity returns mid-session. Confirm `onlineManager` uses the browser online
  events already (it does by default).
- **Verify (vitest):** simulate offline (`onlineManager.setOnline(false)`), fire a
  patch mutation, assert it is **paused** (not failed) and is captured by
  `shouldDehydrateMutation`; set online, assert `resumePausedMutations` drives the
  `mutationFn` and it resolves. A persist round-trip test: dehydrate → rehydrate a
  paused submission mutation against a mock persister, resume, assert `mutationFn`
  runs. `npm run lint && npx tsc --noEmit && npx vitest run`; `npm run build` +
  bundle-budget green (no new runtime dep — all primitives already shipped in Batch 1).
- **What could go wrong:** a rehydrated mutation with an inline closure `mutationFn`
  cannot run after reload — **that's why** the `mutationFn` must live in
  `setMutationDefaults`, keyed, registered before `restoreClient`. Order matters:
  register defaults *before* `PersistQueryClientProvider` restores. The `create`
  submission case is subtle (the server assigns the id the later patches need) — for
  Batch 2 scope, only **patch/submit of an already-created submission** needs offline
  durability (a submission row is created online on first open); document that
  creating a *brand-new* submission while offline-from-cold is out of scope for this
  batch (the student must have opened the assignment online once, which Batch 1
  already requires for offline read).

### PR 3 — MSO-8: "Saved offline · will sync" status UX (New) — *depends on MSO-7*

- **New `src/features/student/SyncStatus.tsx`** (or fold into the assignment page): a
  slim inline indicator driven by `useMutationState({ filters: { mutationKey:
  ['submission'] } })` and `useOnlineStatus()` (the Batch 1 hook). States:
  `synced` (idle, online) → nothing or a quiet "Saved"; `queued` (paused, offline) →
  "Saved on this device · will sync when you're back online"; `syncing` (pending,
  online) → "Syncing…"; `error` (last replay failed) → "Couldn't sync — will retry".
  `role="status"`, `aria-live="polite"`.
- **Global pending count (optional, small):** a tiny badge near the offline banner in
  `AppShell` showing the number of queued submission mutations
  (`queryClient.getMutationCache().getAll().filter(isPaused).length`) so the signal is
  visible even off the assignment page. Keep it unobtrusive.
- **i18n:** add a `sync.` cluster to `en.ts` + `hi.ts` (full parity) and `mr.ts`
  (pilot — core-loop string, translate it): `savedOffline`, `syncing`, `synced`,
  `syncFailed`, `pendingCount` (plural via the `*One`/`*Many` pattern). Run the
  parity guard.
- **Verify (vitest):** render with a mocked paused submission mutation + offline →
  assert "will sync" copy; transition to pending+online → assert "Syncing…"; mocked
  error → assert retry copy. Parity guard green for `sync.` keys. lint + tsc + vitest.
- **What could go wrong:** flicker between states on fast reconnect — debounce the
  "Syncing…"→"Synced" transition or just let "Synced" be the quiet default. Don't
  claim "Saved to server" while merely queued — the copy must be honest (principle 4
  of the initiative): "Saved on this device".

### PR 4 — MSO-9: Offline final-submit (New) — *depends on MSO-7 + MSO-6*

- **Allow submit while offline.** Today `handleSubmit` calls `patchSubmission.mutate`
  with `submitted_at`; offline that pauses (MSO-7). Add **optimistic** local state so
  the UI flips to a submitted view immediately with copy "Submitted — will be graded
  when you're back online" (no score yet). On the mutation's eventual `onSuccess`
  (after replay), set the real `submitScore` and swap to the graded score card.
- **Guard the score card:** the post-submit card currently reads `submitScore` (the
  graded result). When submitted offline, `score` is `null` until grading runs
  server-side post-replay — show a "pending grade" variant (reuse the neutral
  `brand-50` style) instead of the red/amber/green bands, and resolve to the real band
  when the score arrives (the student may need to revisit; a one-line "we'll grade
  this once you reconnect" is honest).
- **Server contract:** because grading is async (Celery) even online, the PATCH
  response `score` is already frequently `null` on submit until the task runs — verify
  the current online flow's handling and mirror it; offline just widens the existing
  "score not yet available" window. MSO-6 guarantees the replayed submit grades
  exactly once.
- **i18n:** `assignmentDetail.submittedOfflineTitle` /
  `assignmentDetail.gradePending` keys in en/hi/mr.
- **Verify (vitest):** offline + submit → assert optimistic submitted view + queued
  mutation; resume online → assert `onSuccess` sets score and the card updates. Assert
  the answer inputs lock after the optimistic submit (no edits to a submitted set).
  lint + tsc + vitest.
- **What could go wrong:** double-submit if the student taps submit, goes online, and
  the replay races a manual re-submit — MSO-6's idempotent guard makes the second a
  no-op returning the same score. Optimistic state desync if replay ultimately fails
  (assignment closed while offline) — surface the `syncFailed` state from MSO-8 and
  re-enable the submit button.

## F. Legacy analysis & improvement opportunities

- **Legacy (Django 1.11) was online-only, server-rendered** — a dropped connection
  mid-assignment lost everything; there is nothing to port. Offline write-tolerance is
  a capability the SPA + service-worker architecture makes possible for the first
  time.
- **Improvement over a naive "retry on error":** we use React Query's *paused
  mutation* model — the write is durably persisted to IndexedDB and replayed on
  reconnect even across a full reload/app-kill, not just retried in memory. And we make
  the **server** idempotent (MSO-6) rather than trusting the client to dedupe, which is
  the correct place for an at-least-once delivery queue to land safely.
- **Honesty over magic (initiative principle 4):** the UI says "Saved on this device ·
  will sync", never pretending a queued write reached the server. Submit-offline shows
  "will be graded when back online" rather than a fake score.
