### Priority 3: Croupier Phase 1 — Deterministic MCQ Shuffling

**Problem**: Every student gets MCQ options in the same order (A, B, C, D as stored). This enables trivial cheating — one student tells another "it's B" and they're done. The legacy Croupier solved this with seeded randomization.

**Approach:**

When a student fetches `/api/assignments/{id}/` (assignment detail with questions), the `AssignmentDetailSerializer` returns `QuestionWithSubpartsStudentSerializer` which renders `options` as stored. We need to shuffle the `options` list for each MCQ subpart, seeded by `(student_id, subpart_id)`.

**Key principle**: The shuffle must be:
1. **Deterministic** per `(student_id, subpart_id)` — same student always sees same order (so auto-save persists correctly, "A" means the same thing on refresh)
2. **Different per student** — two students see different orders
3. **Only for MCQ/multi-select** subparts where `options` is a non-empty list

**Backend implementation:**

No model changes needed. Implement as a view-level transformation in `AssignmentViewSet.retrieve()`.

```python
# views/core.py
import hashlib
import json

def _shuffle_options_for_student(options: list, student_id: int, subpart_id: int) -> list:
    """Deterministically shuffle MCQ options seeded by (student_id, subpart_id)."""
    if not options or len(options) <= 1:
        return options
    seed_str = f"{student_id}:{subpart_id}"
    seed = int(hashlib.sha256(seed_str.encode()).hexdigest(), 16) % (2**32)
    rng = random.Random(seed)
    shuffled = list(options)
    rng.shuffle(shuffled)
    return shuffled
```

Apply in `AssignmentDetailSerializer` or as a post-processing step in the view. The cleanest approach: override `to_representation()` in `QuestionSubpartStudentSerializer` to inject shuffled options when a student context is present.

```python
class QuestionSubpartStudentSerializer(serializers.ModelSerializer):
    def to_representation(self, instance):
        data = super().to_representation(instance)
        request = self.context.get('request')
        if request and request.user.is_authenticated and data.get('options'):
            student_id = request.user.id
            data['options'] = _shuffle_options_for_student(
                data['options'], student_id, instance.id
            )
        return data
```

**Important detail — correct_answer compatibility:**

The `correct_answer` field stores the key (`"A"`, `"B"`, `"C"`, `"D"`). When options are shuffled, the keys must move WITH the options (not just the text). So `options` is a list of `{"key": "A", "text": "..."}` dicts. The `key` on each option object must be re-assigned after shuffling to match the new position.

Example:
```
Original: [{"key": "A", "text": "x=2"}, {"key": "B", "text": "x=-2"}, ...]
correct_answer: "A"  (x=2 is correct)

After shuffle for student 42:
Shuffled list (by text): [{"key": "B", "text": "x=-2"}, {"key": "A", "text": "x=2"}, ...]
Re-key to positions: [{"key": "A", "text": "x=-2"}, {"key": "B", "text": "x=2"}, ...]
Now correct_answer: "B"  (x=2 is now at position B)
```

But wait — `correct_answer` is NOT sent to the student (`QuestionSubpartStudentSerializer` omits it). So we need to track the key mapping without exposing the answer. The approach: reshuffle the `options` list but **reassign keys to new positions** so the student's submitted key maps back correctly on grading.

For grading compatibility: the grader (`grade_submission` Celery task) currently compares `submitted_answer` to `question_subpart.correct_answer`. If the student submits `"B"` (the new position-B after shuffle) and the DB stores `"A"`, grading will fail.

**Two options:**
1. **Store original key in Submission, undo shuffle at grading time** — complex, requires Croupier context at grading time
2. **Re-key options so keys move with the option text** — student submits `"B"`, meaning they selected `"x=2"` (which is the correct answer regardless of position). Grader must compare the *submitted option's text* to the *correct option's text*, not just the key.

Actually the cleanest is: **shuffle the list but preserve keys with their original options**. Return the shuffled list with the *original* key attached to each option object. Student selects `"A"` meaning "the thing labelled A in what they see". Grader needs to know that option A in the shuffled view maps to option X in the original. This requires passing the shuffle seed to the grader.

**Simplest correct approach (ship this):**

Rather than re-keying, store the shuffle as a **positional mapping** in the `Submission` model, or alternatively: when grading, re-apply the same shuffle (same seed) and map the student's answer back to the original key.

For Phase 1, use the re-grading approach:
- Grade: when comparing `submitted_answer` (e.g., "B") against `correct_answer`, apply the same shuffle to reconstruct the student's option list and look up what key "B" maps to in the original.
- Add a utility `get_original_key(student_id, subpart_id, submitted_key, original_options) -> original_key` that deterministically reverses the shuffle.

This keeps the model clean (no new fields) and is fully deterministic.

**Files to create/modify:**
- `backend/openshiksha/apps/api/views/croupier.py` — new module for shuffle/unshuffle logic
- `backend/openshiksha/apps/api/serializers/core.py` — `QuestionSubpartStudentSerializer.to_representation()` override
- `backend/openshiksha/apps/grader/tasks.py` (or wherever `grade_submission` lives) — import and use `get_original_key` when grading MCQ answers
- Tests: shuffled options are different per student, deterministic per student, grading still correct after shuffle

**Classify**: **Port + Improve** — Legacy Croupier did this per-HTTP-request using Cabinet. Modern: pure Python, in-process, no external service dependency.

**What could go wrong:**
- If `options` is stored as a list of strings (not dicts with `key`), the key remapping approach won't work cleanly. Check actual `QuestionSubpart.options` format in seed data / migrations.
- Grading must use the same logic path. If grading short-circuits early (e.g., for non-MCQ questions), ensure the shuffle undo only applies when `question_type == "mcq"`.
- Ensure the shuffle logic is in a shared utility module importable by both the serializer and the grader task, not duplicated.

## F. Legacy Analysis & Improvement Opportunities

### Teacher assignment detail (legacy had none)
- **Legacy did**: Django admin filtering only. No teacher-facing page to view per-student submissions for an assignment.
- **How we improve**: Native teacher page with structured table, sortable columns, score visualization. Future: question-level mistake breakdown per student using `SubjectRoomQuestionMistake`.

### Problem Set builder (legacy existed as admin-only)
- **Legacy did**: Problem sets were created via Django admin using the `AssignmentQuestionsList` model. Teachers had no UI to build problem sets themselves. In practice, the platform admin created all content.
- **What was limited**: Hard dependency on an admin for any new content. Teachers couldn't manage their own question banks.
- **How we improve**: Teacher-facing React form with question picker (searchable, filterable by subject/chapter). Direct DB storage (no Cabinet dependency). Allows teachers to assemble problem sets from their authored questions immediately.

### Croupier (port with improvement)
- **Legacy did**: The `croupier/` module fetched a question's content from Cabinet, applied variable substitution (fill in numeric variables seeded by user ID), and shuffled MCQ options. Also re-ordered sub-questions. Ran server-side on every page load.
- **What was good**: True per-student unique question content. Seeded — reproducible. Enabled per-variable difficulty tuning.
- **What was limited**: Tied to Cabinet (external HTTP service). Variable constraints were stored in Cabinet's custom format. Brittle.
- **How we improve**: Pure Python, deterministic hash-based seed (no RNG state to store), in-process (no HTTP). Phase 1: MCQ shuffling. Phase 2: variable substitution stored as JSON in `QuestionSubpart.variable_constraints` field (can add later without migration risk since it's additive).
